作业一：inc2l 工具补丁

1.1 工具简介

inc2l 是 MASM32 SDK 自带的工具，用于将 .inc 包含文件转换为 .lib 静态库。工作流程：

1. 读取 .inc 文件，生成对应的 .asm 和 .def 文件 2. 调用 ml.exe 编译 .asm → .obj 3. 调用 link.exe 链接 .obj + .def → .lib（及 .dll） 4. 清理临时文件

1.2 问题描述

inc2l 内部硬编码了 ml 和 link 的路径为 \masm32\bin\ml 和 \masm32\bin\Link，该路径从当前盘符根目录开始查找。当 MASM32 未安装在默认路径时，工具无法找到 ml.exe 和 link.exe。

1.3 逆向分析

目标环境：

  • 文件：inc2l_dump_SCY.exe（Delphi 编写）
  • 调试器：x32dbg
  • MASM32 安装路径：E:\RadASM\masm32\

由于目标程序为 Delphi 编写，Delphi 的字符串常量通过间接方式引用，x32dbg 的"字符串引用"搜索无法找到。改用 Ctrl+B 二进制搜索，搜索 \masm32 对应的十六进制字节序列 5C 6D 61 73 6D 33 32，在 .rdata 段中找到 4 处匹配：

| 编号 | 地址 | 原始内容 | 前缀长度 | 占位符 | |------|------|---------|---------|--------| | 字符串1 | 004055E2 | \masm32\bin\ml /c /coff ) | 12字节 | ) (0x29) | | 字符串2 | 004055FC | \masm32\bin\Link /SUBSYSTEM:WINDOWS /OUT:/ | 12字节 | / (0x2F) | | 字符串3 | ~00405627 | \bin\Link /SUBSYSTEM:WINDOWS /WARN:1 /DLL /DEF:6 | 5字节 | 6 (0x36) | | 字符串4 | 00405658 | \masm32\bin\Link /SUBSYSTEM:WINDOWS /WARN:1 /DLL /DEF: + 0x04 | 12字节 | 0x04 |

四条字符串末尾的特殊字符（)、/、6、0x04）是占位符。程序运行时通过固定偏移定位占位符，将其替换为实际的文件名（如 kernel32.asm、kernel32.def）。这意味着：

  • 不能改变字符串长度——否则占位符偏移变化，替换失败
  • 不能改变占位符之前的内容布局——必须保持等长替换

在 00404834（call edx）处发现 CreateProcessA 的调用包装函数：


00404805 | mov eax, FFFFFFFF        ; spinlock init
0040480A | xchg [405010], eax       ; atomic swap
00404810 | test eax, eax            ; check lock
00404812 | jne 404805               ; spin if locked
00404814 | pop [405020]             ; save return addr
0040481A | push edx                 ; save func ptr
0040481B | push 8001                ; SetErrorMode flags
00404820 | call [SetErrorMode]
0040482B | push 0
0040482D | call [SetLastError]
00404833 | pop edx                  ; restore func ptr
00404834 | call edx                 ; ← calls CreateProcessA
00404836 | push [405020]            ; restore return addr

在 CreateProcessA 入口下断点，观察到实际命令行：


第1次调用: \masm32\bin\ml /c /coff kernel32.asm
第2次调用: \masm32\bin\Link /SUBSYSTEM:WINDOWS /WARN:1 /DLL /DEF:kernel32.def kernel32.obj
第3次调用: dir kernel32（清理临时文件）

本次测试仅命中字符串1（ml 编译）和字符串4（Link DLL 链接），字符串2和3未被调用。

字符串3 的特殊性：前缀为 \bin\（5字节）而非 \masm32\bin\（12字节），该字符串在运行时由程序动态拼接 MASM32 安装路径（从环境变量或注册表读取）到前方。因此不能修改字符串3。

1.4 失败的尝试

| 方案 | 做法 | 结果 | 原因 | |------|------|------|------| | 空格填充 | 将12字节前缀替换为 0x20 | CreateProcessA 返回失败（EAX=0, ERROR_INVALID_PARAMETER=87, LastStatus=STATUS_NO_SUCH_FILE） | lpApplicationName=NULL 时，Windows 不跳过 lpCommandLine 的前导空格，将空字符串解析为可执行文件名 | | NULL截断 | 将前缀首字节改为 0x00 | 命令行为空 | strlen 遇到首字节为0直接返回0，命令行长度为0 | | 左移填充 | 将内容左移到字符串开头，末尾补0 | 占位符偏移变化，ml 收到 ml /c /coff ) 而非 ml /c /coff kernel32.asm | 占位符位置改变，替换机制失效 |

空格填充的详细调试过程——CreateProcessA 断点处的堆栈分析：


0019FBF8  00404836  ← [esp] 返回地址
0019FBFC  00000000  ← [esp+4]  lpApplicationName = NULL
0019FC00  0019FC80  ← [esp+8]  lpCommandLine = "            ml /c /coff kernel32.asm"
0019FC04  00000000  ← [esp+0C] lpProcessAttributes = NULL
0019FC08  00000000  ← [esp+10] lpThreadAttributes = NULL
0019FC0C  00000000  ← [esp+14] bInheritHandles = FALSE
0019FC10  00000000  ← [esp+18] dwCreationFlags = 0
0019FC14  00000000  ← [esp+1C] lpEnvironment = NULL
0019FC18  00000000  ← [esp+20] lpCurrentDirectory = NULL
0019FC1C  0019FC38  ← [esp+24] lpStartupInfo (cb=0x44)
0019FC20  0019FC28  ← [esp+28] lpProcessInformation

所有参数均合法，但 lpCommandLine 前导空格导致 Windows 解析出空的可执行文件名，返回 ERROR_INVALID_PARAMETER。

1.5 最终方案：./ 路径替换

将 \masm32\bin\（12字节）替换为 ././././././（12字节，即 0x2E 0x2F 重复6次）。原理：

  • . 在 Windows 路径中表示当前目录
  • ./ 重复多次仍等价于当前目录
  • ././././././ml 解析为 .\ml，即当前目录下的 ml.exe
  • 长度完全一致（12字节），占位符偏移不变
  • 不含空格，CreateProcessA 能正确解析第一个 token

1.6 修改明细

仅需修改2处：

| 地址 | 原始字节 | 修改后字节 | 修改后内容 | |------|---------|-----------|-----------| | 004055E2 | 5C 6D 61 73 6D 33 32 5C 62 69 6E 5C | 2E 2F 2E 2F 2E 2F 2E 2F 2E 2F 2E 2F | ././././././ml /c /coff ) | | 00405658 | 5C 6D 61 73 6D 33 32 5C 62 69 6E 5C | 2E 2F 2E 2F 2E 2F 2E 2F 2E 2F 2E 2F | ././././././Link /SUBSYSTEM:WINDOWS /WARN:1 /DLL /DEF: + 0x04 |

字符串2（004055FC）和字符串3（~00405627）不修改。

1.7 测试验证

  • 工作目录：E:\RadASM\masm32\tools\inc2l\
  • 该目录下放置：ml.exe、link.exe、mspdb50.dll
  • CreateProcessA 断点验证命令行：
  • 第1次命中：././././././ml /c /coff kernel32.asm（正确）
  • 第2次命中：././././././Link /SUBSYSTEM:WINDOWS /WARN:1 /DLL /DEF:kernel32.def kernel32.obj（正确）
  • 成功生成 kernel32.lib 和 kernel32.dll

1.8 环境依赖

  • link.exe 运行时需要 mspdb50.dll（VS 的程序数据库支持库），需一并放置在同一目录
  • 使用 x32dbg 的 Ctrl+P（修补文件）功能保存补丁后的 exe

作业二：PEB 隐藏模块

2.1 作业要求

使用 32 位汇编实现一个隐藏指定模块的函数，并写出测试示例。老师提供了 C 语言参考代码，要求用汇编重写。

2.2 原理

Windows 的 CreateToolhelp32Snapshot + Module32First/Module32Next 内部遍历的是 PEB（Process Environment Block）中的 InLoadOrderModuleList 双向链表。将该链表中目标模块的节点摘除（unlink），即可让模块从枚举结果中消失。

2.3 核心数据结构链路


TEB (fs:[30h])
  └→ PEB
       └→ PEB_LDR_DATA (+0Ch)
            └→ InLoadOrderModuleList (+0Ch, LIST_ENTRY)
                 └→ Flink → 第一个 LDR_DATA_TABLE_ENTRY
                      └→ InLoadOrderLinks (+0h, LIST_ENTRY)
                           ├→ Flink → 下一个 Entry
                           └→ Blink → 上一个 Entry

2.4 双向链表脱链操作

找到目标模块后，执行经典的脱链：


Entry->Flink->Blink = Entry->Blink    ;  下一个节点.Blink = 当前节点.Blink
Entry->Blink->Flink = Entry->Flink    ;  上一个节点.Flink = 当前节点.Flink

对应的汇编（4条 mov 指令）：


mov eax, curEntry
mov ecx, [eax]      ; ecx = Flink (下一个)
mov edx, [eax+4]    ; edx = Blink (上一个)
mov [ecx+4], edx    ; 下一个.Blink = 上一个
mov [edx], ecx      ; 上一个.Flink = 下一个

2.5 踩过的坑

坑1：assume fs:ERROR。MASM32 的 windows.inc 里有 assume fs:ERROR，禁止直接访问 fs 段寄存器。使用 fs:[30h] 前必须加 assume fs:nothing：


.code
assume fs:nothing        ; 在 .code 开头加一行搞定

坑2：mov vs lea 取 BaseDllName 地址。BaseDllName 是 UNICODE_STRING 结构体内嵌在 LDR_DATA_TABLE_ENTRY 中（偏移 +0x2C），不是指针：


; 错误：mov 取了 Length 字段的值当指针
mov ecx, [ecx+2Ch]      ; 读到的是 Length+MaximumLength 拼成的 DWORD，不是地址

; 正确：lea 取结构体的地址
lea ecx, [ecx+2Ch]      ; ecx = &BaseDllName (UNICODE_STRING 结构体地址)
mov edx, [ecx+4]        ; edx = BaseDllName.Buffer (+4 = Buffer 字段)

坑3：BaseDllName.Buffer 为 NULL。链表中有些模块的 BaseDllName.Buffer 为空，lstrcmpiW 解引用 NULL 直接崩溃，需要加 NULL 检查：


.if edx != 0
    invoke lstrcmpiW, offset wszTarget, edx
    .if eax == 0
        ...
    .endif
.endif

2.6 最终代码

完整汇编代码见 HideModule.asm，核心结构：

  • GetProcessModule — 用 CreateToolhelp32Snapshot 枚举模块，sprintf 写入缓冲区
  • HideModule — fs:[30h] 走 PEB 链表，找到目标后 4 条 mov 脱链
  • main — 枚举前 → 隐藏 → 枚举后，用 wsprintfA 写空行间隔，一次 MessageBoxA 弹窗显示

2.7 MASM 伪指令与 C 代码对照

| 老师 C 代码 | MASM 伪指令 | |------------|------------| | do { ... } while (Entry != FirstEntry) | .repeat ... .until eax == firstEntry | | if (lstrcmpi(...) == 0) | .if eax == 0 | | break; | .break | | Entry->InLoadOrderLinks.Flink->Blink = ... | 4 条 mov（无法用伪指令简化） |

关键知识点整理

Delphi 程序的逆向特征

  • 字符串使用 AnsiString 运行时管理，有引用计数和长度字段
  • 字符串常量存在 .rdata 段，通过间接方式引用
  • x32dbg 的"字符串引用"搜索找不到，必须用 Ctrl+B 二进制搜索
  • 字符串末尾可能有占位符字符，通过固定偏移替换

CreateProcessA 参数分析


BOOL CreateProcessA(
  LPCSTR lpApplicationName,      // [esp+4]  NULL = 从命令行解析
  LPSTR lpCommandLine,          // [esp+8]  命令行
  LPSECURITY_ATTRIBUTES,        // [esp+0C] 通常 NULL
  LPSECURITY_ATTRIBUTES,        // [esp+10] 通常 NULL
  BOOL bInheritHandles,         // [esp+14] 通常 FALSE
  DWORD dwCreationFlags,        // [esp+18] 通常 0
  LPVOID lpEnvironment,         // [esp+1C] NULL = 继承父进程
  LPCSTR lpCurrentDirectory,    // [esp+20] NULL = 继承父进程
  LPSTARTUPINFOA lpStartupInfo, // [esp+24] cb=0x44
  LPPROCESS_INFORMATION         // [esp+28] 输出
);

当 lpApplicationName = NULL 时，Windows 从 lpCommandLine 解析可执行文件名，但不跳过前导空格。

Windows 路径解析

  • \masm32\bin\ml — 从当前盘符根目录开始
  • .\ml 或 ././././././ml — 从当前目录开始
  • ./ 重复多次仍等价于当前目录

MASM 调用 C 库函数

  • msvcrt.lib（动态链接 msvcrt.dll）不需要 CRT 初始化，end main 即可
  • libc.lib（静态链接）需要 mainCRTStartup 调 _initterm 初始化
  • sprintf 写缓冲区不依赖 stdout，不需要 CRT 初始化
  • printf 写 stdout，依赖 CRT 初始化

MASM 伪指令

| MASM 伪指令 | 对应 C 代码 | |------------|------------| | .while condition ... .endw | while (condition) { ... } | | .repeat ... .until condition | do { ... } while (!condition) | | .if eax == 0 ... .endif | if (eax == 0) { ... } | | .break | break; | | invoke func, arg1, arg2 | func(arg1, arg2) | | assume fs:nothing | 允许访问 fs 段寄存器 |

mov vs lea


mov ecx, [ecx+2Ch]   ; 读取 [ecx+2Ch] 处的值（4字节）
lea ecx, [ecx+2Ch]   ; 计算 ecx+2Ch 的地址，不读内存

当目标字段是内嵌结构体（如 UNICODE_STRING BaseDllName）时，用 lea 取结构体地址。当目标字段是指针时，用 mov 取指针值。

GetCommandLine A 版本兼容问题

低版本 Windows SDK / MASM32 的 kernel32.inc 中可能没有 GetCommandLineA 的声明，只有 GetCommandLine（无 A/W 后缀）。修复方法：

1. 更新 MASM32 库文件到较新版本 2. 或手动在代码中声明：GetCommandLineA PROTO STDCALL

压缩壳原理与脱壳实战

压缩壳工作机制

加壳阶段（静态修改 PE 文件）：

1. 将原始 PE 的代码段（.text）、数据段等压缩存储 2. 修改 PE 头的 AddressOfEntryPoint 指向壳代码（解压 stub） 3. 壳代码通常放在新增的节（section）中 4. 原始 OEP 被保存在壳代码的数据区

解压阶段（运行时）：

1. 程序从壳代码入口开始执行（不是原始 OEP） 2. 壳代码在内存中解压原始代码和数据，写回到原始的虚拟地址 3. 修复导入表（IAT）——壳运行时可能用自己的 IAT 替换了原始的 4. 跳转到原始入口点（OEP），程序从此正常执行

OEP（Original Entry Point）

原始程序的真正入口点。加壳后入口点被改为壳代码地址，OEP 被隐藏在壳代码的解压逻辑中。

快速定位 OEP

原理：壳代码解压完成后跳回 OEP 时，通常会先进行栈平衡恢复（如 mov esp, ebp / pop ebp / ret 或直接 jmp OEP）。通过硬件访问断点监控栈区域，可以在这个时刻停下来。

操作步骤（x32dbg）：

1. 运行加壳程序，让壳代码开始执行解压 2. 在壳代码运行过程中观察栈状态 3. 设置硬件访问断点（ba 等价操作：Debug → Hardware Breakpoint），监控栈平衡恢复时的内存访问 4. 断点触发时，单步执行，找到跳回 OEP 的 jmp 或 call 指令 5. 跟随跳转，记录目标地址即为 OEP

Dump 内存

定位到 OEP 后，使用 x32dbg 的 Scylla 插件 Dump：

1. 打开 Scylla（Plugins → Scylla） 2. 设置 OEP 地址 3. 点击 Dump，将进程内存导出为新的 PE 文件

修复 IAT

脱壳后程序无法运行的原因：IAT 可能被壳修改或损坏。修复步骤（Scylla）：

1. IAT AutoSearch — 自动查找 IAT 在内存中的位置 2. Get Imports — 获取导入函数列表 3. Fix Dump — 选择刚才 Dump 出的 PE 文件，修复其 IAT

脱壳后修复硬编码路径

脱壳后的程序可能还有硬编码路径问题（如 inc2l 的 \masm32\bin\），需要用补丁作业中的方法（二进制搜索 + 等长替换）修复。
