内存映射与地址转换

PE 结构

内存映射与地址转换

PE 加载的核心是建立文件空间与内存空间的对应：节表把 FOA 空间中的原始数据安排到 RVA 空间中的节，加上模块基址后才得到 VA。

遍历节表映射到内存

老师给出的"简化 PE 加载器"模型：


读取 PE 头
  ↓
读取 NumberOfSections
  ↓
遍历节表，计算各节内存范围
  ↓
检查/准备 SizeOfImage
  ↓
申请一整块连续内存并先清零
  ↓
复制 SizeOfHeaders 指定的头部字节
  ↓
逐节从 PointerToRawData 复制到 ImageBase+VirtualAddress
  ↓
按 Characteristics 设置最终页权限

整块连续内存使每个节的 RVA 稳定映射为 实际地址 = 映像基址 + 节 VirtualAddress + 节内偏移；预先清零自然处理 VirtualSize > SizeOfRawData 的情况——文件没提供的内存尾部保留为零。

"把节的内存大小加起来再和 SizeOfImage 比较"是教学上的范围检查，更严格的思路是找最高节末端：


最高节末端 = max(VirtualAddress + VirtualSize)
需要的镜像范围 = AlignUp(最高节末端, SectionAlignment)

SizeOfImage 应至少覆盖这个范围。

课堂算例

假设 ImageBase=00400000h、FileAlignment=200h、SectionAlignment=1000h、SizeOfHeaders=200h、SizeOfImage=3000h：


文件：0000h~01FFh PE 头 / 0200h~03FFh 代码节 / 0400h~05FFh 数据节
内存：00400000h~00402FFFh 总范围 3000h
      00400000h~00400FFFh 头部页
      00401000h~00401FFFh 代码页
      00402000h~00402FFFh 数据页

| 文件范围 | 真正复制的内容 | 内存目标 | 页级结果（示例） | |---|---|---|---| | 0000h~01FFh | 200h 字节 PE 头 | 00400000h~004001FFh | 所在页 00400000h~00400FFFh，通常 R | | 0200h~03FFh | 200h 字节代码原始数据 | 00401000h~004011FFh | 所在页通常 RX，剩余部分为 0 | | 0400h~05FFh | 200h 字节数据原始数据 | 00402000h~004021FFh | R 或 RW，取决于节属性，剩余部分为 0 |

笔记中常见的简写：


3000 RWE
00400000~00403000
00000000~00000200 => 00400000~00401000 R
00000200~00000400 => 00401000~00402000 RE
00000400~00000600 => 00402000~00403000 R

应读成"先准备一个 3000h 的连续范围，再按页设置属性"，而不是每个 200h 文件块真复制成 1000h 内容——实际有意义的复制范围仍各只有 200h。

注意：

  • "一口气申请、全部 RWE、复制完再改权限"是手动映射的教学模型；真实 Windows 加载器用映像节映射机制，不能等同为用户代码的 VirtualAlloc + memcpy
  • 3000h 不是三个 200h 原始数据相加，而是内存页和最高节末端对齐后的镜像范围
  • SizeOfHeaders=200h 时只复制 200h 个头部字节；头部所在页覆盖到 1000h，但页面余下不代表真实头字段
  • 页权限按页落地，Characteristics 是节级描述；两节共享同一页时权限分离变复杂
  • 真实加载还要处理导入、重定位、TLS 等，这里只解释"复制/映射"这一步

VA、RVA、FOA 地址转换

| 名称 | 全称 | 所在空间 | |---|---|---| | VA | Virtual Address | 进程运行时的实际虚拟地址 | | RVA | Relative Virtual Address | 相对模块基址的内存偏移 | | FOA | File Offset Address | 文件从开头数的偏移 |

| 地址 | 计算 | |---|---| | FOA | PointerToRawData + 节内偏移 | | RVA | VA - ImageBase | | VA | ImageBase + RVA |

PE 头中的数据目录给的是 RVA 不是磁盘偏移；磁盘按 FileAlignment 排列，内存按 SectionAlignment 排列，节头负责建立两者对应。

转换公式


FOA = RVA - 节 VirtualAddress + PointerToRawData

特例：RVA < SizeOfHeaders 时 FOA = RVA（头部布局的特殊情况，不应替代节表算法）。

正向 VA → FOA：


1. RVA = VA - 实际模块基址
2. 找到包含该 RVA 的节（VirtualAddress <= RVA < VirtualAddress + 映射范围）
3. delta = RVA - 节 VirtualAddress
4. 检查 delta 是否仍落在 SizeOfRawData 的文件内容范围内
5. FOA = PointerToRawData + delta

反向 FOA → VA：


1. 找到满足 PointerToRawData <= FOA < PointerToRawData + SizeOfRawData 的节
2. delta = FOA - PointerToRawData
3. RVA = VirtualAddress + delta
4. VA = 实际模块基址 + RVA

课堂算例

VA=0040100Ch、ImageBase=00400000h，代码节 VirtualAddress=1000h、PointerToRawData=200h：


RVA      = 0040100Ch - 00400000h = 100Ch
节内偏移  = 100Ch - 1000h = 0Ch
FOA      = 0200h + 0Ch = 020Ch

反算同一例子：FOA=020Ch → delta=0Ch → RVA=100Ch → VA=0040100Ch。

注意：

  • 节头字段 VirtualAddress 是 RVA 起点，不是最终 VA；FOA 不能直接加 ImageBase，两个空间不同
  • RVA 落在 VirtualSize > SizeOfRawData 的零填充尾部时，内存中有此 RVA 但文件中没有对应 FOA
  • 严格意义上的 Overlay 若没被任何节纳入，不能套用普通节转换公式
  • ASLR 下要用运行时实际模块基址，用首选基址可能算出错误 VA

解析器实现要点

解析目录前先把 DataDirectory 的 VirtualAddress 转成 FOA，再用 m_fileData.constData() + FOA 读取结构。解析器基本流程：


ReadFile
  -> ParserHeader
  -> parserSections
  -> RVA/FOA 转换
  -> 解析数据目录
  -> PEParser 保存结果
  -> MainWindow 显示
  • RvaToFov/FovToRva 最好返回成功/失败，否则转换失败会留下旧值，调用者继续用错误偏移
  • GetPE 的输出参数直接把成员赋给输出：dosHeader = m_dosHander; ntHeader = m_ntHander; sections = m_sections;
  • DataDirectory[5].Size 是目录长度，不是重定位起始地址
  • 对齐计算函数只能算对齐值，不能让读取无条件超过实际文件大小

SizeOfHeaders 与 Overlay

SizeOfHeaders 的规范含义：DOS Stub、PE 头和节表组合后按 FileAlignment 对齐的头部大小。

Overlay 是位于最后一个节的文件范围之外、没有被节表记录的尾部数据。正常布局下，纯 Overlay 不会因为在文件末尾就自动成为内存节。

关于"改大 SizeOfHeaders 把 Overlay 带进内存"的条件化结论：只有当追加数据的文件偏移落在加载器/课堂映射逻辑实际纳入的 SizeOfHeaders 文件前缀范围内、且布局被接受时，扩大它才可能把这部分内容带进内存。课堂假设 Overlay 文件偏移=0800h、SizeOfHeaders=1000h 的紧凑布局下，文件前 1000h 字节可能被当作头部范围纳入内存，Overlay 内容可在 模块基址 + 0800h 观察到；但 Overlay 文件偏移=3500h 时单改 SizeOfHeaders 覆盖不到它。


文件（FileAlignment=200h）：
0000h~01FFh：实际 PE 头
0200h~03FFh：代码原始数据
0400h~05FFh：数据原始数据
0600h 以后 ：可能是 Overlay

内存（SectionAlignment=1000h）：
RVA 0000h~0FFFh：头部所在页
RVA 1000h~1FFFh：代码节
RVA 2000h~2FFFh：数据节

正常 SizeOfHeaders=200h 时头部实际复制文件 0000h~01FFh；课堂把它改成 1000h 应理解为扩大"被当作头部前缀处理的范围"，而不是真正的 PE 结构凭空变大。

注意：

  • 改大 SizeOfHeaders 可能越过第一个节边界、覆盖布局或触发加载失败；"不超过 1000h"只是第一节从 1000h 开始的课堂示例边界，不是普遍上限
  • 映射不等于执行：控制流必须跳到那里，且页面要有执行权限。头部页通常不是代码执行页，即使字节像指令，也必须同时满足"控制流到达"和"页面可执行"
  • "程序还能跑"不代表修改无影响：原入口、代码节、导入仍正常，额外数据未被使用而已；不代表畸形字段普遍安全
  • 以上 Overlay 数值均为课堂/手动映射模型假设，待用具体样本验证

结构层级与术语对比

PE 各层结构职责不同：

| 层级 | 主要内容 | 作用 | |---|---|---| | DOS Header / DOS Stub | MZ、e_lfanew 等 | 文件开头，帮助找到 NT 头 | | NT Signature | PE\0\0 | 标记 PE 映像 | | IMAGE_FILE_HEADER（文件头） | Machine、NumberOfSections、SizeOfOptionalHeader 等 | 文件级信息，决定节表数量和位置计算 | | IMAGE_OPTIONAL_HEADER（可选头） | ImageBase、对齐、SizeOfImage、SizeOfHeaders、目录数量等 | 装载和运行参数 | | Section Header（节头） | 每节 40 字节，文件/内存位置、大小、权限 | 描述每个节如何从文件进入内存 | | Data Directory（数据目录） | 多个 RVA + Size 项 | 指向导入、导出、资源、重定位等特殊表，不是节头本身 |

同一个 PE 在不同空间的描述：


文件头/可选头：告诉加载器整体规则
节头：告诉加载器每一块数据的搬运规则
数据目录：告诉加载器特殊表在哪里
文件偏移：在磁盘文件中找字节
RVA：在模块映像中找相对位置
VA：程序运行时用的实际地址

| 术语 | 含义 | 备注 | |---|---|---| | Overlay | 所有节文件范围之外的尾部数据 | 默认不等于映射节 | | Padding / 对齐填充 | 为 FileAlignment/SectionAlignment 补出的空隙 | 只在对齐和零填语境出现 | | Code Cave | 已映射节内可利用的空闲字节 | 待确认，无独立样本 | | AddressOfEntryPoint | 可选头中开始执行的 RVA | 控制流必须到达注入代码才有意义 | | OEP / AEP | 逆向术语：原始入口/入口点 | 未正式展开 |

遇到 PE 字段先问三个问题：属于哪一层（文件头/可选头/节头/数据目录）？描述文件空间、内存空间还是两者的索引？是单个值、对齐后的大小还是按位标志？

注意：

  • "节必须连续"指 PE 规范要求 VA 按升序、通常按 SectionAlignment 相邻排列；不是把文件原始字节和内存节地址当成同一条连续线
  • "文件大小 0、内存大小 1000h"表示零填；"文件有大小、内存大小 0"依赖具体加载器对零 VirtualSize 的兼容处理，不是普遍定律
  • 把代码数据复制到头部页只是多一个内存副本，CPU 不会因字节出现就扫描执行
  • "属性改了通常没事"必须附条件：代码节执行位、数据节写位、NX/DEP 和页边界都影响结果
  • NumberOfSections 在文件头，SizeOfHeaders/SizeOfImage 在可选头，不能因都参与装载就混为一层；DOS 头、NT 头、File Header、Optional Header、Section Header 和 Data Directory 处在不同层次
