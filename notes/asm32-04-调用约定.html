调用约定

调用约定（Calling Convention）是函数调用者与被调用者之间的一份二进制级契约，约定了参数如何传递、栈由谁清理、返回值如何存放、寄存器谁负责保存。不同的编译器/语言/平台有各自的默认约定，但在 x86 Win32 汇编中可以自由选择。

四种调用约定总览

| 调用约定 | 参数传递 | 压栈顺序 | 谁清栈 | ret 形式 | 典型用途 | |---|---|---|---|---|---| | __stdcall | 全部压栈 | 右到左 | 被调用者 | ret N | Win32 API | | __cdecl | 全部压栈 | 右到左 | 调用者 | ret | C 标准库、可变参数函数 | | __fastcall | 前两个参数走 ecx/edx，其余压栈 | 右到左 | 被调用者 | ret N | 编译器优化 | | __pascal | 全部压栈 | 左到右 | 被调用者 | ret N | 已废弃，早期 Pascal / Windows 16 位 |

stdcall

Win32 API 的标准约定。被调用者（函数本身）负责清栈，用 ret N 一步完成返回 + 清理参数。


; MessageBoxA(NULL, "Hello", "Title", MB_OK)
push 0                    ; MB_OK（最后一个参数最先压）
push offset szTitle
push offset szMsg
push 0                    ; NULL
call MessageBoxA@16       ; 函数内部 ret 16，自动清 4 个参数
; 调用后 ESP 已恢复，不需要做任何事

对应的函数定义（MASM）：


MyFunc proc stdcall, arg1:dword, arg2:dword
    ; ... 函数体 ...
    ret                   ; MASM 自动展开为 ret 8
MyFunc endp

MASM 在检测到 proc stdcall 时，会根据参数列表自动在 ret 指令后附加参数总字节数，生成 ret 8。

cdecl

C 标准约定。调用者负责清栈，函数只做 ret，调用方之后手动 add esp, N。可变参数函数（printf、wsprintf）必须用 cdecl，因为只有调用者知道压了多少参数，被调用者无法在编译时确定参数个数。


; wsprintfA(szBuf, "x=%d y=%d", x, y)
push eax                  ; y（最后一个参数最先压）
push edx                  ; x
push offset szFmt
push offset szBuf
call wsprintfA            ; 函数内部只做 ret，不清栈
add esp, 16               ; 调用者手动清：4 个参数 x 4 = 16

fastcall

编译器优化约定。前两个参数通过寄存器 ecx、edx 传递，避免栈操作开销，其余参数仍压栈、仍从右到左。


; fastcall foo(1, 2, 3)
mov  ecx, 1               ; 第 1 个参数走 ecx
mov  edx, 2               ; 第 2 个参数走 edx
push 3                    ; 第 3 个参数压栈
call foo@12               ; @N 计入全部 3 个参数（12 字节）；ret 4 只清栈上的 1 个参数
  • 优点：减少栈访问次数，提升调用密集型代码的性能
  • 缺点：调用方必须保证 ecx/edx 的值不被其他操作覆盖

pascal

左到右压栈 + 被调用者清栈，与主流方向相反。这导致被调函数无法确定第一个参数的位置（因为参数个数变化时偏移量也会变化），已彻底淘汰。了解即可。

为什么参数从右向左压栈


; foo(a, b, c) 压栈顺序：c -> b -> a
push c
push b
push a
call foo

压栈完成后的栈布局（默认 ebp 已保存）：


[ebp+8]   -> a（第 1 个参数）
[ebp+12]  -> b（第 2 个参数）
[ebp+16]  -> c（第 3 个参数）

核心原因：固定偏移。 第 1 个参数永远在 [ebp+8]，与参数总个数无关。这意味着：

  • 被调函数可以用硬编码的偏移量访问每个参数
  • 可变参数（...）成为可能——va_start 宏就是通过第 1 个参数的地址 + 固定偏移来依次取出后续参数的
  • 如果是从左到右压栈（pascal），参数个数变化后 a 的偏移会变，导致无法实现可变参数

为什么 Win32 API 选择 stdcall

Win32 API（如 CreateWindow、GetMessage）有成千上万个导出函数，被成百上千个应用程序调用。选择 stdcall 的考虑：

1. 代码体积优化：清理栈的 ret N 指令（2-3 字节）位于函数内部，只出现一次；如果由每个调用者分别清理（cdecl 的 add esp, N），每个调用点都要多 3 字节。对于 Kernel32、User32 这种被大量调用的 DLL，stdcall 节省了可观的总体代码体积。 2. 减少调用者心智负担：调用者只需 call，不必关心有多少个参数需要清理。忘记 add esp, N 是 x86 汇编最常见的崩溃原因之一。 3. 统一规范：所有 API 使用同一约定，避免了混用出错的可能。

为什么 cdecl 必须用于可变参数


printf("%d %d %d", a, b, c);  // 3 个参数
printf("hello");               // 1 个参数

同一个 printf 在不同调用点接受的参数个数不同。如果采用 stdcall，函数内部的 ret N 无法在编译时确定 N 的值——因为 printf 的实现看不到调用者压了多少参数。只有调用者知道自己压了多少参数，所以必须由调用者来清栈。

底层机制：printf 通过 va_start、va_arg 宏遍历栈上的参数。va_start 的底层实现大致是：


// 简化实现
#define va_start(ap, last) (ap = (char*)&last + sizeof(last))
#define va_arg(ap, type)   (*(type*)((ap += sizeof(type)) - sizeof(type)))

它从最后一个已知参数（格式化字符串）的地址向后遍历栈，依次取出不定数量的参数。这就要求参数在栈上从右到左连续排列，且调用者负责清栈。

为什么 stdcall 需要 @N 后缀（名称修饰）

由于被调用者执行 ret N 来清栈，链接器必须知道参数的总字节数，否则无法验证调用是否正确，也无法在重定位时修正符号。


MessageBoxA@16    -> 4 个 DWORD 参数 = 16 字节
ExitProcess@4     -> 1 个 DWORD 参数 = 4 字节
  • 对 stdcall：名称修饰为 _FunctionName@N（MASM/TASM 下有时省略前导下划线）
  • 对 cdecl：名称修饰为 _FunctionName（仅前导下划线，无 @N）
  • 对 fastcall：名称修饰为 @FunctionName@N（前导 @）

链接器通过符号名中的 @N 就能知道该函数期望的栈清理量，类型不匹配时会报 unresolved symbol 或链接错误，起到一定的静态检查作用。

为什么 fastcall 走 ecx/edx

ecx 和 edx 是 x86 架构中最适合传递参数的通用寄存器：

  • 它们不是"被调用者保存"寄存器（callee-saved），不需要函数 prolog 保存
  • eax 专门用于返回值，ebx 常被用作基址，esi/edi 用于串操作——ecx/edx 最适合临时传递参数
  • 编译器在 fastcall 模式下可以省略对前两个参数的 push/pop 操作，减少栈访问带来的延迟

栈帧结构（stdcall 为例）

调用 foo(1, 2) 后的栈布局：


高地址
+----------+----------+
|    2     | [ebp+12]  参数 2
+----------+----------+
|    1     | [ebp+8]   参数 1
+----------+----------+
| 返回地址  | [ebp+4]   call 指令自动压入
+----------+----------+
| 旧 EBP   | [ebp]     push ebp 保存的前一帧基址
+----------+----------+
| 局部变量1 | [ebp-4]   sub esp, N 分配的局部空间
+----------+----------+
| 局部变量2 | [ebp-8]
+----------+----------+
低地址      <- ESP

栈帧构建步骤：

1. 调用者 push 参数（从右到左） 2. call 指令将返回地址压栈（这一步自动完成） 3. 被调用者 push ebp 保存旧基址 4. 被调用者 mov ebp, esp 建立新帧基址 5. 被调用者 sub esp, N 分配局部变量空间 6. 函数体执行 7. 被调用者 mov esp, ebp / pop ebp 恢复 8. 被调用者 ret N（stdcall）或 ret（cdecl）

不同约定的调用流程对比


stdcall 流程：
  调用者  push 参数（右 -> 左）
  调用者  call（自动压入返回地址）
  被调者  push ebp / mov ebp, esp
  被调者  sub esp, N（分配局部变量）
  被调者  ... 函数体 ...
  被调者  mov esp, ebp / pop ebp
  被调者  ret N（返回 + 清栈）
  调用者  ESP 已恢复，无需操作

cdecl 流程：
  调用者  push 参数（右 -> 左）
  调用者  call
  被调者  标准 prolog / epilog
  被调者  ret（只返回，不清栈）
  调用者  add esp, N（调用者手动清栈）

关键差异：stdcall 的清栈指令嵌入在函数结尾，而 cdecl 的清栈指令分散在每个调用点之后。

逆向识别调用约定

看函数结尾指令是 ret 还是 ret N：


; stdcall 函数结尾（被调用者清栈）
    ret 8              ; ← 带 N，说明是 stdcall，N=参数总字节数

; cdecl 函数结尾（调用者清栈）
    ret                ; ← 不带 N，说明是 cdecl
; 且调用点后面必然紧跟：
; call bar
; add esp, 8           ; ← 调用者手动清栈

注意：看到 ret N → 被调用者清栈 → stdcall（Windows API）；看到裸 ret 且调用点后有 add esp, N → 调用者清栈 → cdecl（C 库函数/可变参数）。这是判断函数约定的第一信号。

链接器符号名里的 @N 直接编码了参数字节数，是调用约定的静态指纹：


MessageBoxA@16    → stdcall，4 个 DWORD 参数（16 字节）
ExitProcess@4     → stdcall，1 个 DWORD 参数
_wsprintfA        → cdecl（仅前导下划线，无 @N）
@foo@8            → fastcall（前导 @ + 结尾 @N）

注意：在 PE 导出表或 .idata 里看到带 @N 后缀的符号，立刻判定为 stdcall，且 N 就是参数字节数（32 位下除以 4 即参数个数）。dumpbin /exports user32.dll 可直接看到这些修饰名。

计算 add esp, N 中的 N


N = 参数个数 x 4（每个 DWORD 参数占 4 字节）

3 个参数 -> add esp, 12
4 个参数 -> add esp, 16
5 个参数 -> add esp, 20

注意：如果参数中包含 8 字节的 __int64 或结构体，需手动计算实际字节数。

声明外部函数（MASM）


; stdcall：使用带 @N 的名称
extrn MessageBoxA@16   : PROC
extrn ExitProcess@4    : PROC

; cdecl：名称前加下划线，无 @N 后缀
extrn _wsprintfA       : PROC

定义自己的函数


; 定义一个 stdcall 函数
AddTwo proc stdcall, a:dword, b:dword
    mov  eax, a
    add  eax, b
    ret                     ; MASM 自动 => ret 8
AddTwo endp

; 定义一个 cdecl 函数
AddTwoCdecl proc cdecl, a:dword, b:dword
    mov  eax, a
    add  eax, b
    ret                     ; MASM 生成 ret（无 N）
AddTwoCdecl endp

; 定义一个 fastcall 函数
AddTwoFast proc fastcall, a:dword, b:dword
    mov  eax, ecx           ; a 来自 ecx
    add  eax, edx           ; b 来自 edx
    ret                     ; MASM 自动 => ret 0（栈上无参数）
AddTwoFast endp

调用约定选择决策树


需要决定调用约定
  是用来调用 Win32 API？
    是 → stdcall
    否 → 被调函数有可变参数？
           是 → cdecl
           否 → 追求极致的调用性能？
                  是 → fastcall
                  否 → 与 C 交互 → cdecl
                        纯汇编   → stdcall

快速判断既有函数采用哪种约定

  • Win32 API（CreateWindow、GetMessage、TextOut、DispatchMessage 等）→ stdcall，调用后不用清栈
  • 格式化字符串函数（wsprintfA、_sprintf、printf 等）→ cdecl，调用后必须 add esp, N
  • 函数名末尾有 @N → stdcall
  • 函数名以 @ 开头 → fastcall
  • 不确定 → 查 MSDN（Windows SDK 文档）或看头文件声明中 WINAPI 宏（展开为 __stdcall）

常见汇编指令速查

| 指令 | 作用 | 字节数 | |---|---|---| | ret | 返回，不清栈 | 1 | | ret N | 返回，然后 ESP += N | 3 | | add esp, N | 手动调整 ESP（清理参数） | 3-6 | | push r32 | 32 位寄存器/内存压栈 | 1-2 | | call addr | 压入返回地址并跳转 | 5 |
