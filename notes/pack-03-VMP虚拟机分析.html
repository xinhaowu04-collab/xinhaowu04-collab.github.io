VMP 虚拟机分析

环境：Windows 11 x64 主机、x32dbg 调试器、VMProtect 3.5.1 保护的 32 位控制台 crackme。目标是 32 位程序运行在 64 位 Windows 上，进程属于 WOW64。文中地址和解密常数均来自本次样本，不可直接套到别的样本。

分析目标与源码范围

最初卡在反调试阶段，老师提示「源码是公开的，可以从源码下手」。「从源码下手」不是先把整个 VMProtect 工程编译出来，而是用源码回答三个问题：

1. 样本启动时具体检查了哪些调试状态； 2. 这些检查走普通 ntdll API，还是直接系统调用； 3. 调试器插件为什么显示注入成功，却仍可能过不了反调试。

从 SetupImage() 源码中抽取的用户态核心链路：


解析系统调用号
    → PEB->BeingDebugged
    → ProcessDebugPort
    → ProcessDebugObjectHandle
    → ThreadHideFromDebugger

删减原则：保持原版语句、判断顺序和变量用法，只删除与核心链路无关的代码；不以能够单独编译为目标；注释改成中文。它应称为「原版源码摘录」，既不是可编译的最小项目，也不是教学重写。

删减边界：

1. 保留 sc_close、sc_query_information_process、sc_set_information_thread 的解析； 2. 保留 WOW64 下对系统调用号的截断和参数编码； 3. 保留 LOADER_OPTION_CHECK_DEBUGGER 下的四个核心检查； 4. 保留普通 API 回退分支，系统调用号解析失败时会走这里； 5. 删除无关的映像加载、解密、重定位、导入修复等加载器业务； 6. 完整性检查、异常类反调试等暂未逐行分析的部分只登记，不假装已分析完。

直接盯着加壳后的入口单步，会同时面对重叠指令、虚拟机初始化、滚动密钥和反调试异常。源码先提供一张检查清单，再回到动态调试逐项验证。但源码只能说明「可能有哪些路径」，实际走哪条仍要由寄存器、返回值和断点命中确认。

容易误解的点：

| 容易误解的说法 | 修正 | |---|---| | 「源码公开，所以不用动态分析了」 | 源码只帮助列出机制；实际分支、系统调用号和插件覆盖情况仍需动态确认 | | 「删减版就是重新写个同功能示例」 | 保留原版代码仅删无关内容；教学重写会改变源码结构，不能冒充原版删减 | | 「不考虑编译，所以代码顺序可以随便改」 | 可以缺少声明和外围上下文，但核心语句的顺序、条件和异常判断应保持原版 | | 「只剩四项，因此原版只有四种反调试」 | 四项只是优先抽取的用户态核心；完整源码还有异常、断点、硬件调试寄存器、完整性等检查 |

系统调用号与 WOW64

原版代码先从一份复制出来的 ntdll 中查找函数，再从函数入口解析系统调用号：


sc_query_information_process = LoaderParseSyscall(
    LoaderGetProcAddress(
        (HMODULE)copy_ntdll,
        reinterpret_cast<const char *>(FACE_NT_QUERY_INFORMATION_PROCESS_NAME),
        true));

sc_set_information_thread = LoaderParseSyscall(
    LoaderGetProcAddress(
        (HMODULE)copy_ntdll,
        reinterpret_cast<const char *>(FACE_NT_SET_INFORMATION_THREAD_NAME),
        true));

| 变量 | 对应系统服务 | 反调试用途 | |---|---|---| | sc_query_information_process | NtQueryInformationProcess | 查询当前进程的调试端口和调试对象 | | sc_set_information_thread | NtSetInformationThread | 对当前线程设置 ThreadHideFromDebugger | | sc_close | NtClose | 四项核心之外，被后续异常行为检查和 WOW64 编码条件使用 |

LoaderGetProcAddress 是 VMProtect 自己实现的导出表查找；LoaderParseSyscall 从函数入口机器码取得系统调用号。copy_ntdll 是从磁盘映射或复制的干净 ntdll，区别于当前进程里可能已被插件 Hook 的那份。

普通调用路径与直接系统调用路径：


普通：保护代码 → 当前进程 ntdll!NtQueryInformationProcess → 内核
直接：保护代码 → 自己准备的 syscall stub + 系统调用号 → 内核

用户态反反调试插件常在 ntdll 入口安装 Hook 并伪造无调试器的结果；直接系统调用可完全绕过这些用户态 Hook。因此日志中的「Hook injection successful」只表示插件 DLL 注入并安装了部分 Hook，不代表直接系统调用已被覆盖。

当 sc_query_information_process 或 sc_set_information_thread 为零时，代码才用 LoaderGetProcAddress 查找普通 API 作为回退。手工绕过的思路之一就是把相关 sc_* 置零，强制程序走较容易 Hook 的普通 API 路径。

WOW64 编码：


#ifndef _WIN64
if (is_wow64) {
    sc_close = static_cast<uint16_t>(sc_close);
    sc_query_information_process = static_cast<uint16_t>(sc_query_information_process);
    sc_set_information_thread = static_cast<uint16_t>(sc_set_information_thread);
}
#endif

#ifndef _WIN64
if (is_wow64 && sc_close) {
    sc_close |= WOW64_FLAG;
    sc_set_information_thread |= WOW64_FLAG | (0x02 << 24);
    sc_query_information_process |= WOW64_FLAG | (0x03 << 24);
}
#endif

分两步理解：

1. static_cast：先只保留系统调用号的低 16 位； 2. |=：再在高位加上 VMProtect 的 WOW64 标志和参数类别信息。

引用的 Windows 10 22H2 分支原始值（来自源码分支，不是本次运行时实测的寄存器值）：

| 分支 | NtQueryInformationProcess | NtSetInformationThread | |---|---:|---:| | 原生 32 位分支 | 0x00B9 | 0x004D | | x64/WOW64 所用原始 ID | 0x0019 | 0x000D |

引用的 Win11/WOW64 文章给出的编码结果：


sc_query_information_process = 0x03008019
sc_set_information_thread    = 0x0200800D

可按「参数类别高位 + WOW64 标志 + 低位系统调用号」来读。文章值只能作为定位参考，当前样本应在赋值后观察变量确认。

注意：分析中一度只保留 Windows 10 22H2 分支，随后纠正——主机是 Win11，不能把源码分支值当成当前实测值。

注意：sc_close 虽不是四项核心检查的主角，但原版 if (is_wow64 && sc_close) 用它作为编码条件，机械删除会改变外围逻辑。

容易误解的点：

| 说法 | 正确理解 | |---|---| | 「WOW64 就是 32 位」 | WOW64 特指 32 位进程运行在 64 位 Windows 的兼容层中；32 位 Windows 上的 32 位进程不是 WOW64 | | 「_WIN64 表示当前系统是不是 Win64」 | _WIN64 是编译目标宏，表示这份代码是否编译成 64 位程序，不是运行时操作系统版本 | | 「转成 uint16_t 是因为系统调用号永远只有 16 位」 | 是先清掉高位编码，再由 VMProtect 按自己的 WOW64 调用约定重建高位 | | 「Win11 可以删掉所有 Win10 分支」 | 不编译的源码摘录可以省略无关分支；真实程序仍可能依赖动态解析和兼容回退 | | 「直接系统调用就是函数地址」 | sc_* 保存的是调用号或编码后的调用描述，不是普通函数地址 |

四项核心反调试

核心代码由选项位控制，只有 LOADER_OPTION_CHECK_DEBUGGER 被设置才执行：


if (data.options() & LOADER_OPTION_CHECK_DEBUGGER) {
    // 各项检查
}

| 检查 | 信息来源 | 目的 | |---|---|---| | PEB->BeingDebugged | 用户态 PEB 字段 | 快速判断调试标志 | | ProcessDebugPort | NtQueryInformationProcess | 判断进程是否关联调试端口 | | ProcessDebugObjectHandle | NtQueryInformationProcess | 判断进程是否关联调试对象，并检查返回行为是否合理 | | ThreadHideFromDebugger | NtSetInformationThread | 请求内核将当前线程对调试器隐藏 |

PEB->BeingDebugged


if (peb->BeingDebugged) {
    LoaderMessage(mtDebuggerFound);
    return LOADER_ERROR;
}

进程被常规用户态调试器创建或附加时，BeingDebugged 通常会被设置。它读取快、没有 API 调用，但也最容易被插件修改。

清空 Instrumentation Callback


if (peb->OSMajorVersion > 6) {
    PROCESS_INSTRUMENTATION_CALLBACK_INFORMATION info;
    info.Version = 0;
    info.Reserved = 0;
    info.Callback = NULL;

    if (tNtSetInformationProcess *set_information_process =
        reinterpret_cast<tNtSetInformationProcess *>(
            LoaderGetProcAddress(
                ntdll,
                reinterpret_cast<const char *>(FACE_NT_SET_INFORMATION_PROCESS_NAME),
                true)))
        set_information_process(
            process,
            ProcessInstrumentationCallback,
            &info,
            sizeof(info));
}

把回调地址设为 NULL，目的是关闭 Windows 10/11 上可用于用户态插桩、监控系统调用返回路径的 Instrumentation Callback。它不是「调用 NtSetInformationProcess 实现系统调用隐身」——系统调用绕过用户态 Hook 的能力来自直接系统调用路径，这里是删除一个回调机制，二者不要混为一谈。

peb->OSMajorVersion > 6 覆盖主版本大于 6 的系统，包括 Windows 10 和 Windows 11；源码注释写「Windows 10」只是当时的简写。

ProcessDebugPort


HANDLE debug_object;
if (NT_SUCCESS(
        reinterpret_cast<tNtQueryInformationProcess *>(
            syscall | sc_query_information_process)(
                process,
                ProcessDebugPort,
                &debug_object,
                sizeof(debug_object),
                NULL))
    && debug_object != 0) {
    LoaderMessage(mtDebuggerFound);
    return LOADER_ERROR;
}

检查的是「当前进程是否被调试设施关联」，不是代码里有没有名为 DebugPort 的字段。只改 PEB 的 BeingDebugged 并不能解除内核为被调试进程建立的关联，多个信息源交叉检查比只查一个字节更难伪造。

ProcessDebugObjectHandle

直接系统调用路径中的判断较特殊：


debug_object = 0;
if (NT_SUCCESS(
        reinterpret_cast<tNtQueryInformationProcess *>(
            syscall | sc_query_information_process)(
                process,
                ProcessDebugObjectHandle,
                &debug_object,
                sizeof(debug_object),
                reinterpret_cast<PULONG>(&debug_object)))
    || debug_object == 0) {
    LoaderMessage(mtDebuggerFound);
    return LOADER_ERROR;
}

同一块 debug_object 内存既作为输出缓冲区，又作为 ReturnLength 参数。它不仅看「有没有调试对象」，还利用未调试进程在这一信息类上的特定返回状态和参数副作用，识别插件是否进行了过于简单的伪造。

| 返回现象 | 判断 | |---|---| | 查询成功，并返回有效调试对象 | NT_SUCCESS 为真，报调试器 | | 插件粗暴返回「失败」，同时把输出维持为 0 | debug_object == 0，仍报调试器 | | 无调试器时返回预期失败状态，同时别名参数产生源码期待的非零副作用 | 两个条件均为假，才继续 |

普通 API 回退路径则较直接：


if (NT_SUCCESS(query_information_process(
        process,
        ProcessDebugObjectHandle,
        &debug_object,
        sizeof(debug_object),
        NULL))) {
    LoaderMessage(mtDebuggerFound);
    return LOADER_ERROR;
}

这就是为什么「插件把句柄改成 0」未必够用：保护代码可能同时验证 NTSTATUS、输出参数和 ReturnLength 的组合。

ThreadHideFromDebugger


if (sc_set_information_thread)
    reinterpret_cast<tNtSetInformationThread *>(
        syscall | sc_set_information_thread)(
            thread,
            ThreadHideFromDebugger,
            NULL,
            0);
else if (tNtSetInformationThread *set_information_thread =
    reinterpret_cast<tNtSetInformationThread *>(
        LoaderGetProcAddress(
            ntdll,
            reinterpret_cast<const char *>(FACE_NT_SET_INFORMATION_THREAD_NAME),
            true)))
    set_information_thread(
        thread,
        ThreadHideFromDebugger,
        NULL,
        0);

系统调用号存在就直接进内核，否则走普通 ntdll API。成功后，当前线程产生的异常和调试事件可能不再按调试器预期交付，单步、断点和异常控制流会受到影响。

分析反调试代码的记录顺序

1. 信息类：如 ProcessDebugPort； 2. 调用路径：直接系统调用还是普通 API； 3. 输出缓冲区初值； 4. NTSTATUS 的期望值； 5. 输出值和 ReturnLength 的期望副作用； 6. 被判定为「发现调试器」的布尔条件。

把逻辑还原为条件表，而不是只给函数名做注释：


BeingDebugged != 0
    → 发现调试器

DebugPort 查询成功 && DebugPort != 0
    → 发现调试器

DebugObjectHandle 查询成功 || 别名输出仍为 0
    → 发现调试器或发现返回伪造

最后执行 ThreadHideFromDebugger
    → 隐藏当前线程

手工绕过的思路：

1. 把 sc_query_information_process、sc_set_information_thread 置零； 2. 强制保护代码走普通 API 回退路径； 3. 在 LoaderGetProcAddress 附近干预 NtQueryInformationProcess、NtSetInformationThread、NtClose 的解析结果。

注意：修改 [ESP+4] 栈参数的说法必须在实际调用点核对——常见 x86 函数入口中 [ESP] 是返回地址，[ESP+4] 通常是第一个显式参数，不能机械地称为「第二个参数」。

容易误解的点：

| 容易误解 | 修正 | |---|---| | NtQueryInformationProcess 是「查某一个东西」 | 它根据 ProcessInformationClass 查询不同信息；本次同一 API 分别查 DebugPort 和 DebugObjectHandle | | 检查 DebugPort 是看「有没有打开调试端口文件」 | 不是文件端口，而是进程与调试设施的内核关联 | | ProcessDebugObjectHandle 只需返回句柄 0 | 原版还检查状态码与参数副作用，粗糙伪造可能反而触发 | | NtSetInformationProcess 这段是在「隐藏系统调用」 | 它清除 Instrumentation Callback；直接系统调用绕 Hook 是另一段机制 | | ThreadHideFromDebugger 会让整个进程彻底不可调试 | 它针对指定线程；插件仍可能拦截或内核层修正 | | 直接系统调用路径与普通 API 路径检查内容完全一样 | 信息类相同，但直接路径的 ProcessDebugObjectHandle 特意加入了返回行为校验 |

实测状态：已确认源码中存在直接调用与普通 API 回退两条路径；插件成功注入后仍被检测，与直接系统调用绕过 ntdll Hook 的机制相符；原版后部还重复检查过 ProcessDebugPort 和 ThreadHideFromDebugger，说明一次伪造不一定覆盖所有时机。完整源码中的外围机制（内核调试器状态、CRC/补丁完整性、入口 INT3 字节、PAGE_GUARD/PAGE_NOACCESS、无效 CloseHandle(0xDEADC0DE) 的异常行为、DRx/线程上下文、Trap Flag、RDTSC/CPUID 及异常检查）未全部完成动态验证，状态为待继续。

ScyllaHide、SharpOD 与 AntiVmp

两类工具职责不同，不能混为一谈：

1. 反反调试插件：让程序看不到调试器，如 ScyllaHide、SharpOD、HyperHide、TitanHide； 2. VMP 分析插件：帮助追踪、收集和分析虚拟机，如 AntiVmp。

| 工具 | 主要定位 | 与本次 VMP 3.5.1 的关系 | |---|---|---| | ScyllaHide | 用户态反反调试 | 有 VMProtect x86/x64 Profile，但直接系统调用可能绕过用户态 Hook | | SharpOD | x32dbg/x64dbg 反反调试插件，部分版本带驱动功能 | v0.6d 更新说明专门提到 VMP 3.5.1；本次实际使用 v0.6b 也通过了样本 | | AntiVmp v1.1 | x32dbg 下的 VMP 3.5.1 分析辅助 | 偏一键分析、跟踪和补丁，不是独立「只隐藏调试器」开关 | | HyperHide | Hypervisor/内核层反反调试 | 能覆盖多种内核可见状态；风险高，只建议隔离 VM | | TitanHide | 通用内核驱动反反调试 | 可覆盖类似检查，但 Win11 兼容性与稳定性需单独验证 |

ScyllaHide 的 Profile 应按目标程序和保护类型选，而不是按主机系统位数选。当前目标是 VMP 保护的 32 位程序，选择 VMProtect x86/x64 Profile 合理。

日志 Hook injection successful, image base 01830000 只说明插件 DLL 已加载并完成它认为成功的 Hook 初始化，不能证明 PEB、直接系统调用、DebugObject、线程隐藏、早期 TLS 或异常路径都已覆盖。

全选并不等于覆盖更完整。多个插件或多层 Hook 可能重复修改同一 API、异常或调试寄存器，造成崩溃、卡死、错误返回，内核选项甚至可能导致蓝屏。

ScyllaHide 使用要点

1. 给 32 位目标使用 x32dbg 对应插件； 2. 选择 VMProtect x86/x64 Profile； 3. 观察注入日志，但把「注入成功」和「反调试已通过」分开验证； 4. 若仍失败，根据源码逐项判断是 PEB、普通 API、直接系统调用还是异常路径未覆盖。

SharpOD 使用要点

1. 从作者原帖取得压缩包，文件名为 SharpOD x64 v0.6b-password[123].rar，压缩密码 123； 2. Chrome 曾提示「已屏蔽危险的下载内容」。不要全局关闭安全浏览；应在隔离虚拟机中核对来源、扫描压缩包和解压后的 .dp32、.dp64、.sys； 3. x32dbg 使用 .dp32；包名中的 x64 主要表示适配 x64 系统/调试器套件，不代表只能调试 64 位目标； 4. 不要同时叠加 ScyllaHide 与 SharpOD，先用最小配置验证； 5. 本次最终由 SharpOD v0.6b 成功通过反调试，属于本样本实测结果。

入口重叠反汇编与 AEP

反调试通过后，x32dbg 在入口附近最初显示：


0105FE25  38 49 68                 cmp byte ptr ds:[ecx+68],cl
0105FE28  63 92 1E 01 E8 50        arpl word ptr ds:[edx+50E8011E],dx
0105FE2E  5A                       pop edx
0105FE2F  42                       inc edx
0105FE30  00 66 0F                 add byte ptr ds:[esi+0F],ah
0105FE33  B6 46                    mov dh,46
0105FE35  02 8A 16 81 EE 02        add cl,byte ptr ds:[edx+02EE8116]
0105FE3B  00 00                    add byte ptr ds:[eax],al
0105FE3D  00 F6                    add dh,dh
0105FE3F  EA ...                   jmp far ...

出现 arpl、奇怪的远跳和不合理内存地址，首先应怀疑反汇编起点错位、代码与数据重叠或刻意的反反汇编，而不是立即断言「外面又加了一层加密壳」。

真实 EIP 是 0105FE27，位于 x32dbg 显示的第一条指令内部。该处字节为 68 63 92 1E 01，重新解码得到：


0105FE27  68 63 92 1E 01    push 011E9263

x86 指令是变长的，同一组字节从不同地址开始可以形成完全不同的指令流。线性反汇编从 0105FE25 开始，就把 0105FE27 的 68 吃进了前一条 cmp；CPU 却只按 EIP 指向的 0105FE27 解码。

push imm32 长度为 5 字节（1 字节 opcode 68 + 4 字节立即数），小端还原立即数 63 92 1E 01 → 0x011E9263，所以下一条地址是 0105FE27 + 5 = 0105FE2C。这正是按 F7 单步后 EIP 直接来到 0105FE2C 的原因，不是调试器跳过了代码。

接下来是：


0105FE2C  E8 50 5A 42 00    call 01485881

E8 使用相对下一条指令的有符号位移：


下一条地址 = 0105FE31
rel32      = 00425A50
目标       = 0105FE31 + 00425A50 = 01485881

call 的等价动作：


push 0105FE31
jmp  01485881

进入 01485881 后的栈布局：


ESP     → 0105FE31    CALL 自动压入的返回地址
ESP+4   → 011E9263    前一条 PUSH 压入的 VM 参数

入口出现明显乱码时的处理顺序：

1. 先看真实 EIP，而不是只相信反汇编窗口的行首； 2. 在 EIP 处重新反汇编； 3. 读取原始字节并手算变长指令长度； 4. 对 E8 rel32 用「下一条地址 + 位移」计算目标； 5. 进入目标后检查栈，验证 CALL 返回地址和显式参数是否符合推导； 6. 只有发现另一个完整解压/解密加载器、第二个 OEP 等证据时，才考虑双层壳。

容易误解的点：

| 误解 | 修正 | |---|---| | 反汇编窗口显示 arpl、jmp far，说明一定还有第二层壳 | 更常见的原因是错位或重叠指令；先从真实 EIP 重解码 | | 注释里的 edx:EntryPoint 表示 EIP 在 EDX | 通常只是调试器识别出 EDX 的值指向名为 EntryPoint 的地址 | | F7 从 FE27 到 FE2C 是跳转 | push imm32 自身正好 5 字节，是正常顺序执行 | | Push RETADDR 是源码中显式的 push | 它是 CALL 指令的隐式压栈效果 | | E8 后面的四字节就是绝对地址 | 它是相对下一条指令的 rel32 位移 |

实测数据：


真实 AEP/EIP：0105FE27
入口参数：    011E9263
CALL 地址：   0105FE2C
CALL 下一条： 0105FE31
CALL 位移：   00425A50
VM 入口：     01485881

本次现象证明入口处存在重叠/错位反汇编设计；「是否还有额外加密壳」没有独立证据，不能仅凭乱码下结论。

VMEntry 初始化与寄存器角色

进入 01485881 后，代码先保存宿主机上下文：


01485881  push ebx
01485882  push edx
01485883  pushfd
01485884  push eax
01485885  push esi
01485886  push ebp
01485887  push edi
01485888  push ecx
01485889  mov ecx,00890000
0148588E  push ecx
0148588F  mov edi,dword ptr ss:[esp+28]

八次保存后又压入模块基址 00890000，此时：


[ESP+24] = 0105FE31    返回地址
[ESP+28] = 011E9263    VM 入口参数

所以 mov edi,[esp+28] 取得的是 011E9263。

VMEntry 完成三件事：

1. 保存原生寄存器和 EFLAGS，建立虚拟机上下文； 2. 把入口参数解码成虚拟字节码地址和初始滚动密钥； 3. 从加密字节码中解出第一个 Handler 的相对地址并跳转。

入口参数变换：


mov edi,[esp+28]     ; EDI = 011E9263
dec edi              ; 011E9262
bswap edi            ; 62921E01
rol edi,10h          ; 1E016292
dec edi              ; 1E016291
ror edi,19h          ; 00B1488F
add edi,ecx          ; +00890000 = 013A488F

随后：


mov ebp,esp
sub esp,0C0h
mov ebx,edi
mov edx,00890000
sub ebx,edx

得到 EBX = 013A488F - 00890000 = 00B1488F。sub esp,0C0h 为虚拟寄存器/临时区预留 0xC0 字节，EBP 用作虚拟栈指针，ESP 附近作为虚拟寄存器区。

第一个 Handler 的地址不是明文读取，而是解密相对偏移：


lea esi,dword ptr ds:[014858B0]
mov eax,dword ptr ds:[edi]
add edi,4
xor eax,ebx
add eax,655C3CA0
bswap eax
sub eax,76CD7325
bswap eax
xor ebx,eax
add esi,eax
jmp esi

流程：


从 [EDI] 取 4 字节密文
    → 用 EBX 和多组算术/位变换解出 Handler 相对增量
    → EBX ^= 增量，更新滚动密钥
    → ESI = 014858B0 + 增量
    → jmp ESI，进入第一个 Handler

当前样本的寄存器角色表：

| 寄存器 | 当前 VM 中观察到的角色 | |---|---| | EDI | 加密虚拟字节码指针，即 VIP | | EBP | 虚拟栈指针，即 VSP | | ESP | 虚拟寄存器/临时区的基准 | | EBX | 滚动解密密钥 | | ESI | 当前或下一 Native Handler 地址 | | EAX/ECX/EDX | 操作数、解密增量和临时计算 |

进入每个 Handler 时记录 Handler 地址、EDI、EBX、EBP、ESI，离开前再记录一次，就能分开回答：当前虚拟指令消费了多少字节、虚拟栈如何变化、解出的下一 Handler 增量是多少、滚动密钥如何更新。

容易误解的点：

| 误解 | 修正 | |---|---| | EDI 是普通 PE 的 OEP | 当前它是 VM 加密字节码指针 | | ESI 指向下一条虚拟指令数据 | ESI 指向要执行的原生 Handler；虚拟字节码由 EDI 读取 | | sub eax,user32.76CD7325 调用了 user32 | 只是调试器把立即数 0x76CD7325 符号化成了落在 user32 地址范围的名字；仍是立即数运算 | | sub esp,C0 是普通局部变量，与 VM 无关 | 在这里它用于构造 VM 的虚拟寄存器/临时上下文 | | 第一 Handler 地址在表里明文保存 | 当前是由 VMEntry 从 [EDI] 读取密文并解出相对增量 |

实测数据：


模块基址常数：00890000
入口参数：    011E9263
解码后 VIP： 013A488F
初始 EBX：    00B1488F
Handler 基准：014858B0

Handler 结构与滚动密钥

观察到的普通 Handler 大多由两部分组成：虚拟指令语义核心 + 解密下一 Handler 并跳转的调度尾。

典型 VM_PopVR32：


mov edx,dword ptr ss:[ebp]       ; 从虚拟栈弹出 DWORD
add ebp,4

movzx eax,byte ptr ds:[edi]      ; 读取加密的虚拟寄存器偏移
add edi,1
xor al,bl
rol al,6
xor al,C4
ror al,6
xor bl,al                        ; 更新低 8 位滚动密钥
mov dword ptr ss:[esp+eax],edx   ; 写入虚拟寄存器区

mov ecx,dword ptr ds:[edi]       ; 读取下一 Handler 的加密增量
add edi,4
xor ecx,ebx
ror ecx,13h
xor ecx,3C164F4E
rol ecx,0Fh
not ecx
xor ebx,ecx                     ; 更新完整滚动密钥
add esi,ecx                     ; 当前 Handler + delta
jmp esi                         ; 跳到下一 Native Handler

近似伪代码：


value = VPop32();
reg_offset = decrypt_byte(*VIP++, key);
VReg[reg_offset] = value;

delta = decrypt_dword(*(uint32_t *)VIP, key);
VIP += 4;
key ^= delta;
handler = handler + delta;
goto handler;

当前结构是直接线程化的链式调度：每个普通 Handler 完成自身语义后，自己解密并计算下一 Handler，而不是统一返回一个中心 Dispatcher：


VMEntry 解出 H1
    → H1：执行语义，解出 delta2，跳到 H2
    → H2：执行语义，解出 delta3，跳到 H3
    → H3：执行语义，解出 delta4，跳到后续 Handler 或 VMExit

关键区别：


EDI → 加密虚拟字节码
ESI → 原生 Handler 代码地址

Handler 不是「去 ESI 取下一条虚拟指令」。它先从 [EDI] 读取本条指令的操作数，再从后续 [EDI] 读取下一 Handler 选择信息的密文，解出相对增量，更新 ESI，最后跳转。它也不是一次解密两条完整虚拟指令：当前指令的操作数、下一条指令的 Handler 选择值分两步解；下一条指令自己的操作数要进入下一 Handler 后才解密。

滚动密钥使解密具有前后依赖：


VMEntry 解出 H1
H1 使用当前 EBX 解操作数和 H2，并更新 EBX
H2 使用更新后的 EBX 解操作数和 H3
……

没有正确的 EDI + EBX + ESI 状态，通常不能从字节码中间随便开始离线解码。

分析一个 Handler 按两层拆：

1. 虚拟语义：只看它对 VSP、虚拟寄存器、内存、标志位做了什么； 2. 调度尾：记录它如何消费字节码、更新密钥、计算下一个 Handler。

然后整理成「虚拟指令 → 等价汇编 → 合并后的业务语义」，例如：


VM_PopVR32
    → value = [VSP]; VSP += 4; VReg[index] = value
    → 等价于把虚拟栈顶保存到某个虚拟寄存器

某个 Handler 尾部跳回同一个原生入口，不必立即判断死循环：只要 EDI、EBP 或 EBX 已改变，同一段原生代码仍可处理下一份虚拟数据，例如连续执行多个 PopVR32。

实测中曾在不同位置看到相同的 $+... FF E6 jmp esi，后一处跳回同一段 VM_PopVR32 起点，原因就是下一条虚拟指令仍为同一语义且 EDI/EBP/EBX 已更新。

还观察到共享跳板：


010531B9  lea edx,dword ptr ss:[esp+60]
010531BD  cmp ebp,edx
010531BF  jnbe 010531E7
010531E7  jmp esi

它更像 push 类 Handler 使用的 VSP 边界检查跳板。到达它之前 Handler 已经算好了 ESI，因此它不是覆盖所有虚拟指令的总 Dispatcher，固定在 010531E7 下断只能捕获一部分路径。

容易误解的点：

| 误解 | 修正 | |---|---| | 每个 Handler 的调度代码完全字节相同 | 职责相似，但解密常数、位变换、寄存器和跳转形式可能不同 | | 所有 Handler 都必定有同一套尾巴 | 只对「大多数普通 Handler」成立；VMExit、异常或特殊 Handler 可能不同 | | jmp esi 就是公共 Dispatcher | 它只是最终的间接跳转指令；真正的目标计算分散在各 Handler 内 | | 下一 Handler 地址没有解密 | xor/rol/ror/not 等就是解密过程，结果是相对增量而非完整指令字节 | | Handler 跳回自己就是无限循环 | 若 VM 状态已改变，它可能是在复用同一语义 Handler | | 找不到固定表就无法分析 | 可以动态构造「地址—语义」映射并按语义去重；固定明文表不是必要条件 |

Handler 表与语义归类

传统解释器可能有明文表 jmp dword ptr [HandlerTable + opcode*4]，本次 trace 没有观察到这种固定的 opcode→Handler 表。「找 Handler 表」更现实的含义是由分析者动态建立：

| Handler 地址 | 语义名称 | 消费字节数 | VSP 变化 | 备注 | |---|---|---|---|---| | 某地址 | VM_Add32 | 待具体尾部确认 | 按语义变化 | 可能存在多个克隆地址 |

由于 VMProtect 会克隆/变形 Handler，不应只按地址计数，更应按归一化后的语义去重。

直接线程化结构里没有一个固定地址能抓住所有 Handler，但所有已执行的 native 指令仍要被 CPU 执行，因此可以让调试器逐条 Trace，只在执行到机器码 FF E6（jmp esi）时记录。FF E6 在内存中是小端 WORD，即 word(cip) == 0xE6FF。这不是在固定地址下断，而是在整个执行路径中识别指令模式。

条件跟踪记录全部 Native 指令

x32dbg「条件跟踪步进」填写：


暂停条件：0
日志文本：{p:cip} {i:cip}
日志条件：1
命令：留空
最大单步次数：500、5000 或 10000
模块筛选器：仅用户

若要恢复虚拟指令的具体操作数，日志中必须包含寄存器：


{p:cip} {i:cip} EAX={p:eax} EBX={p:ebx} ECX={p:ecx} \
EDX={p:edx} EBP={p:ebp} EDI={p:edi} ESI={p:esi}

「运行跟踪」记录更详细的寄存器/内存变化，体积更大，但比纯文本地址更适合恢复立即数和虚拟寄存器偏移。跟踪时使用 Trace Into，Trace Over 可能把内部 Handler 调用或跳转整体跨过。

只记录 jmp esi


暂停条件：0
日志文本：HandlerTail={p:cip} NextHandler={p:esi} {i:cip}
日志条件：word(cip)==E6FF

调试器仍逐条执行每条 native 指令，只是只在 jmp esi 处打印日志：日志精简了，但执行速度仍受逐条 Trace 限制。

500 步 Trace 的语义归类

本次 500 条 native 指令中识别出 25 次完整 Handler 实例、7 类语义，没有出现 VMExit：

| 语义 | 观察到的原生地址 | 次数 | 核心作用 | |---|---|---:|---| | VM_PushImm32 | 01380EC1、0145EDF6、013B3A25 | 3 | 解密 DWORD 立即数并压入 VSP | | VM_PushVR32 | 00FC6373、01020ED3 | 2 | 读取虚拟寄存器 DWORD 并压栈 | | VM_Add32 | 00F941DC、0138726A、01382EB7、01494E34、014657E5、013753E4、014307FC | 7 | 两个虚拟栈 DWORD 相加，并保存结果/EFLAGS | | VM_PopVR32 | 0107CF55、01039341、0138CA4A、0102B355、01438C65、0146D0E8、0143B1AC、00FB8144 | 8 | 虚拟栈顶写入虚拟寄存器 | | VM_ReadMem32 | 01356723、0148C9D2 | 2 | 把 VSP 顶部地址替换为该地址处 DWORD | | VM_PushVSP | 0148FFF2、01028659 | 2 | 把旧 VSP 值压入虚拟栈 | | VM_NAND32 | 01400DE9 | 1 | 计算 NAND 语义并保存结果/标志 |

25 条虚拟指令顺序：


01 PushImm32   02 PushVR32   03 Add32      04 PopVR32    05 ReadMem32
06 Add32       07 PopVR32    08 Add32      09 PopVR32    10 PushVSP
11 PushImm32   12 PushImm32  13 PushVR32   14 Add32      15 PopVR32
16 ReadMem32   17 Add32      18 PopVR32    19 Add32      20 PopVR32
21 NAND32      22 PopVR32    23 Add32      24 PopVR32    25 PushVSP

核心语义伪代码：


// PushImm32
VSP -= 4;
*(uint32_t *)VSP = decrypted_imm32;

// PushVR32
VSP -= 4;
*(uint32_t *)VSP = VReg[decrypted_offset];

// PopVR32
VReg[decrypted_offset] = *(uint32_t *)VSP;
VSP += 4;

// ReadMem32
*(uint32_t *)VSP = (uint32_t )VSP;

// PushVSP
old_vsp = VSP;
VSP -= 4;
*(uint32_t *)VSP = old_vsp;

// NAND32
result = ~(a & b);   // 等价于 (~a) | (~b)

注意：VM_Add32 常见行为是把结果和 EFLAGS 都留在虚拟栈上。它后面紧跟 PopVR32 时，后者可能是在保存 EFLAGS，而不一定是把算术结果保存到寄存器；没有具体 VSP/寄存器状态时不能提前下结论。

容易误解的点：

| 误解 | 修正 | |---|---| | 25 个地址就是 25 种 Handler | 归一化后只有 7 类语义，说明存在克隆和变形 | | 找到 010531E7 jmp esi 就能收集全部 Handler | 500 步中只有部分 push 类路径经过共享跳板，其他 Handler 直接 jmp esi | | 只记录反汇编文本就能完整还原原始 x86 | 文本中没有进入时寄存器和解密结果，无法恢复立即数和虚拟寄存器偏移 | | 500 步没出现 VMExit，说明 VM 没有出口 | 只能说明这 500 条 native 指令还没走到出口 | | NAND32 的 ~a \| ~b 与 ~(a&b) 不同 | 由德摩根定律，两者相等 | | 条件日志只打印 jmp esi，调试器就不用执行中间指令 | 条件跟踪仍逐条执行，只是减少了输出量 |

实测结论：500 条 native 指令 → 25 次完整 Handler 实例 → 归一化为 7 类虚拟语义；本段没有 VMExit，仍处在同一个 VM 块中；共享跳板 010531E7 在这段 trace 中只覆盖部分 Handler；日志没有完整寄存器快照，立即数、虚拟寄存器编号和最终业务汇编仍为待确认。

长程序分析策略

控制台 crackme 的虚拟化路径很长，逐条 F7 并手工翻译每个克隆 Handler 会把时间耗在重复的 VM 框架代码上。更有效的目标不是翻译完整个 VM 的每条 native 指令，而是：


收集并归一化独特 Handler 语义
    + 定位输入到成功/失败分支的数据流
    + 只翻译相关 VM 块

地址级去重没有处理 Handler 克隆；全程序线性翻译也没有利用 crackme 的目标特征。验证程序最终必然存在「输入 → 变换/比较 → 条件结果 → 成功或失败输出」，因此可以先从输入缓冲区、比较结果、成功/失败字符串或 VMExit 边界切入，反向缩小需要翻译的虚拟指令范围。

VMExit 是 VM 块边界，不应自动解释为一次 call 或业务 API。只有把出口前后的原生栈、参数和控制流连起来，才能还原业务汇编。

推荐路线：

1. VMEntry 只完整手算一次，确认 EDI/EBX/EBP/ESI 角色； 2. 用条件 Trace 收集 Handler 进入与跳转； 3. 按「虚拟语义」去重，建立自己的 Handler 字典； 4. 记录 EDI/EBX/EBP，恢复当前虚拟操作数； 5. 寻找 VMExit，把虚拟块划分开； 6. 从输入缓冲区、比较、失败输出附近做数据切片； 7. 对相关块执行「虚拟指令 → 等价汇编 → 合并语义」； 8. AntiVmp 可用于自动收集和分类，但人工抽查关键 Handler，避免把插件输出直接当结论。

整理给老师的提问：

整理给老师的提问，较严谨的版本是：使用 SharpOD 通过反调试后，从 VMEntry 进入第一个 Handler。目前观察到的大多数常规 Handler 都由「本条虚拟语义 + 滚动密钥解密下一 Handler 相对地址 + jmp esi」组成，属于分散式链式调度；没有观察到固定公共 Dispatcher，也没有看到传统的明文 opcode→Handler 表。程序较长，逐条单步建表和翻译效率很低。请问更合适的路线，是用条件 Trace/脚本动态收集并按语义去重 Handler，还是先通过输入缓冲区、成功失败分支和 VMExit 定位校验路径，只翻译相关 VM 块？

容易误解的点：

| 误解 | 修正 | |---|---| | 「所有 Handler 都确定包含同一调度」 | 目前只能说「大多数已观察到的常规 Handler」；VMExit 和特殊 Handler 需保留例外 | | 「没有公共 Dispatcher 就只能手工 F7 到底」 | 可以按指令模式 Trace、记录运行状态，并以数据流切片缩小范围 | | 「找 Handler 表是最终目标」 | 表只是辅助；真正目标是理解验证路径的虚拟语义和分支条件 | | 「AntiVmp 一键分析后就不需要学习」 | 插件节省重复收集工作，但仍需人工验证寄存器、操作数和关键业务块 | | 「程序长，所以必须翻译所有虚拟指令」 | 对 crackme 优先翻译输入到判定分支的相关路径 |

实测状态：已确认当前样本没有观察到固定公共调度点；500 步 trace 证明同一语义可对应多个原生地址；尚未遇到 VMExit，25 条虚拟指令还未合并成最终业务汇编；下一阶段重点从「继续扩充地址表」转向「补寄存器状态 + 找验证数据流」。

控制台输入定位与失败实验纠正

目标是控制台程序，原先针对窗口程序的 GetDlgItemTextA/W、GetWindowTextA/W 等输入断点不适用。控制台输入可能经过：


kernelbase!ReadConsoleA/W
kernelbase!ReadFile
ucrtbase/msvcrt!scanf
ucrtbase/msvcrt!fgets
ntdll!NtReadFile
ntdll!NtDeviceIoControlFile
静态链接 CRT 或自定义输入逻辑

实际没有命中最初猜测的 API 断点，说明不能只靠函数名猜路径。最稳的方法是在程序等待输入时暂停，查看调用栈：无论内部经过哪个 CRT/Kernel API，输入函数最终都要返回到 crackme 自己的模块继续校验。给调用栈中第一个属于 crackme3_pack 的返回地址下软件断点，就能停在「输入刚返回、校验将开始」的位置。

堆和栈地址只对本次进程实例有效；程序重启后 ASLR、堆分配、栈布局和 VMP 工作区都可能变化。

同一次运行流程

1. 让程序停在等待输入的界面，先不要按回车； 2. 在调试器中暂停； 3. 打开 Call Stack，找到第一个返回到 crackme3_pack 模块的地址； 4. 在该返回地址下软件断点； 5. 继续运行，输入唯一字符串并回车； 6. 输入函数返回后立即断下，此时校验尚未走远； 7. 在同一个进程执行全内存搜索； 8. 对当前搜索结果设置硬件访问断点； 9. 继续运行，观察谁读取或复制输入； 10. 如果先停在系统库/CRT 的复制逻辑，跟踪目标缓冲区，直到命中 crackme 或 VM 相关代码。

findallmem

本次命令：


findallmem 0,51374D324B395834

含义：从地址 0 开始，扫描当前进程的全部可搜索内存区域，寻找指定字节序列。输入字符串 Q7M2K9X4 的 ASCII 字节：


Q  7  M  2  K  9  X  4
51 37 4D 32 4B 39 58 34

若程序使用 UTF-16，还要搜索：


51 00 37 00 4D 00 32 00 4B 00 39 00 58 00 34 00

结果出现在 References/引用视图，不一定显示在当前 Dump 窗口，可用 ? ref.count() 查看结果数量。手工在 Dump 中「二进制搜索」通常只搜索当前选中的内存区或页面；findallmem 跨模块、堆、栈、私有映射区搜索，所以手工搜索可能找不到而它能找到。

异常日志


DLL已载入：76A20000 C:\Windows\SysWOW64\imm32.dll
INT3 断点“入口断点”于 0105FE27

EXCEPTION_DEBUG_INFO:
    dwFirstChance: 1
    ExceptionCode: 80000004 (EXCEPTION_SINGLE_STEP)
    ExceptionAddress: 01391FF2

DLL已载入：76FC0000 C:\Windows\SysWOW64\sechost.dll

0x80000004 是单步异常。VMP 可能把它作为故意的控制流/反调试机制；硬件断点也依赖单步异常。因此只能在确认当前不是自己设置的 DRx 命中时，临时选择一次「运行并传递异常」，不能把所有 0x80000004 永久忽略。

失败实验：旧地址硬件断点假命中

搜索结果：


地址 = 018C5FF0    反汇编 = push ecx
地址 = 015AFB3C    反汇编 = push ecx

push ecx 只是把以 0x51（ASCII Q）开头的数据当作代码解码的显示结果，不代表输入成了代码。

随后重启程序并在旧地址设置断点，命中：


01376A94  mov edx,dword ptr ss:[ebp]
01376A98  add ebp,4
01376A9E  xor edx,ebx
01376AA0  not edx
01376AA2  bswap edx

当时一度把它当成「读取输入」的证据，后来被实验否定。正确结论：旧的堆/栈地址在新进程中已不再代表原输入缓冲区，硬件断点命中了新的 VMP 工作数据或无关内存。这是假命中，不能用于推导校验算法。

动态地址必须按类别区分：

| 地址类型 | 重启后能否直接复用 | |---|---| | 模块内地址，已换算成「模块基址 + RVA」 | ASLR 后重新计算通常可复用 | | 堆地址 | 通常不可复用 | | 栈地址 | 通常不可复用 | | VMP 私有工作区 | 需重新确认内存映射，不能凭旧值复用 |

容易误解的点：

| 误解 | 修正 | |---|---| | findallmem 找到的位置反汇编为 push ecx，说明输入成了代码 | 字节 0x51 既是 ASCII Q 也是 push ecx；数据窗口被反汇编不代表它真是代码 | | 搜到地址后重启程序，原地址仍是输入缓冲区 | 堆、栈和私有区地址通常不稳定；必须在同一次进程运行中搜索和下断 | | 输入回车后报错，再搜索也一定能找校验代码 | 此时校验可能已结束，只能看到残留副本；应在输入函数返回前后提前布置断点 | | EXCEPTION_SINGLE_STEP 一定是 VMP 反调试 | 硬件断点命中也产生它，必须结合 DRx、EIP 和日志判断 | | 两个搜索结果都是原始输入缓冲区 | 可能分别是控制台/CRT 缓冲区、程序副本或 VMP 工作区，需要看访问者和内存归属 |

当天结论与下一步

当天从「过不了反调试」推进到「进入 VM、确认入口解码和 Handler 链式调度、完成一段 trace 的语义去重」，但还没有恢复最终口令算法，也没有翻译到成功/失败分支。

最关键的三次认知变化：

1. 从「插件注入成功却仍被检测」转为用源码解释直接系统调用和返回行为校验； 2. 从「入口乱码可能是另一层壳」转为用真实 EIP 和字节长度证明重叠反汇编； 3. 从「找一个固定断点抓所有 Handler」转为认识分散式链式调度，并按语义去重。

下一次实验顺序：

1. 保持已能通过反调试的最小插件配置，不再随意叠加插件； 2. 在同一次运行中定位控制台输入返回地址； 3. 输入唯一字符串后立刻 findallmem； 4. 对当前地址设置硬件访问断点并确认内存区域归属； 5. 条件 Trace 日志加入全部关键寄存器； 6. 继续扩充「Handler 语义字典」，但不重复翻译克隆； 7. 找到 VMExit 或输入比较相关块； 8. 按「虚拟指令 → 等价汇编 → 合并语义」恢复验证路径； 9. 每个结论至少用一次栈、寄存器或内存变化验证。

注意区分几组「不等于」：

  • 「过了反调试」不等于「已经脱壳」，当前仍在 VMP 虚拟机中；
  • 「能识别 Handler 名称」不等于「已恢复业务逻辑」，还缺具体操作数和数据流；
  • 「找到许多 Handler 地址」不等于「找到了传统 Handler 表」；
  • 「插件能自动分析」不等于插件输出永远正确，关键路径仍要人工核对；
  • 「今天没有得到口令」不等于没有进展；入口、寄存器角色、调度模型和 7 类语义是后续切片的基础。
