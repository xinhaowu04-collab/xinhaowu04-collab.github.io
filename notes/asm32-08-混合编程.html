32 位汇编

C 与汇编混合编程

本笔记聚焦 32 位 Win32 平台下 C 与 MASM 汇编的混合编程机制。混合编程是指在同一个项目中，C 源文件和汇编源文件各自独立编译，最后由链接器拼接成一个可执行文件——C 可以调用汇编写的函数，汇编也可以调用 C 写的函数。

核心机制：编译和链接是分开的

C 编译器和汇编器各自独立工作，互不知道对方存在。链接器在最后把多个 .obj 拼成一个 .exe。


main.c  ──C编译器──→  main.obj  ─┐
                                  ├──链接器──→ program.exe
add.asm ──汇编器──→  add.obj   ─┘

C 编译器不需要看到汇编代码，只需要一个函数声明（extern），就能生成 call 指令，目标地址先空着，留给链接器填。

三个工具各干一件事

| 工具 | 输入 | 输出 | 职责 | |------|------|------|------| | C 编译器 (cl.exe) | .c | .obj | 把 C 代码翻译成机器码 | | 汇编器 (ml.exe) | .asm | .obj | 把汇编代码翻译成机器码 | | 链接器 (link.exe) | 多个 .obj + .lib | .exe | 符号解析 + 地址重定位 + 合并段 |

链接器的两个核心工作

1. 符号解析（找地址）

  • main.obj 说："我需要 _add"（对应 C 的 extern）
  • add.obj 说："我提供 _add"（对应汇编的 public）
  • 链接器匹配两边，把地址填进 call 指令

2. 地址重定位（改地址）

每个 obj 内部地址都从 0 开始，直接拼接会冲突。链接器把所有代码重新排列，跳转地址全部改成新的。

C 调用汇编函数

汇编侧（add.asm）：


.386
.model flat, c              ; 用 C 调用约定，MASM 自动处理下划线
public add                  ; 导出 add

.code
add proc c a:DWORD, b:DWORD ; c 约定，参数自动压栈
    mov eax, a
    add eax, b
    ret
add endp
end

C 侧（main.c）：


extern int add(int a, int b);   // 声明：这个函数在别的文件里

int main() {
    int result = add(3, 5);
    return 0;
}

汇编调用 C 函数

C 侧（utils.c）：


int add(int a, int b) {
    return a + b;
}

汇编侧（main.asm）：


.386
.model flat, c
option casemap:none

add proto c a:DWORD, b:DWORD   ; 声明 C 函数

.code
start:
    invoke add, 3, 5           ; 调用 C 函数
    ; eax = 8
    ret
end start

符号对应关系

| 操作 | 汇编 | C | |------|------|---| | 定义函数 | add proc ... add endp | int add(int a, int b) { ... } | | 导出（声明公开） | public add | 不用写，默认公开（非 static） | | 导入（声明外部） | extrn add | extern int add(int, int); |

extern "C" 的作用

C++ 会给函数名加修饰（name mangling），C 不会。

| 编译器 | int add(int, int) 编译后的符号名 | |--------|----------------------------------| | C | _add | | C++ | ?add@@YAHHH@Z |

C++ 调用汇编时，如果不加 extern "C"，C++ 编译出 ?add@@YAHHH@Z，但汇编导出的是 _add，链接器对不上，链接失败。


// C++ 文件
extern "C" int add(int a, int b);   // 告诉 C++ 别改名，用 C 的命名规则

C 语言不需要 extern "C"，只有 C++ 才需要。

头文件兼容写法


#ifdef __cplusplus
extern "C" {
#endif

int add(int a, int b);

#ifdef __cplusplus
}
#endif

__cplusplus 是 C++ 编译器自动定义的宏，C 编译器不定义它。这样同一个头文件 C 和 C++ 都能用。

C 运行时库 (CRT) 的版本与初始化

汇编调用 C 函数时，如果调用的是 C 标准库函数（printf、malloc 等），会遇到 CRT 初始化问题。

新旧 CRT 的区别

| | 旧版 (VC6 时代) | 新版 (VS2015+) | |---|----------------|----------------| | 动态库 | msvcrt.dll | ucrtbase.dll (UCRT) | | 静态库 | libc.lib / libcmt.lib | libucrt.lib / ucrt.lib | | 配套工具 | MASM 6.14 | 新版 ml.exe (VS 自带) | | 初始化函数 | 导出，能手动调 | 不导出，调不了 |

为什么汇编调 CRT 会崩

C 程序的真正入口不是 main，是 mainCRTStartup：


程序启动
  → mainCRTStartup()     ← CRT 初始化在这里
      → _heap_init()      ← 初始化堆（malloc 依赖）
      → _ioinit()         ← 初始化 IO（printf/stdout 依赖）
      → _cinit()          ← 初始化全局变量、浮点状态
      → main()            ← 才调你的 main
      → exit()            ← 清理后退出

汇编程序的入口是 start:，直接跳过了 CRT 初始化。如果调 printf 这类 CRT 函数，它依赖的内部状态（stdout 句柄、缓冲区、locale）没初始化，轻则输出乱码，重则崩溃。

哪些 CRT 函数能直接用

| 函数 | 能不能用 | 原因 | |------|---------|------| | strcpy / strlen | ✓ | 纯内存操作，不依赖状态 | | printf | ✗ | 依赖 stdout 初始化 | | malloc | ✗ | 依赖堆初始化 | | exit | ✓ | 但要用它退出，不能用 ExitProcess |

手动初始化 CRT（仅旧版 msvcrt）

新版 UCRT 的初始化函数不导出，无法手动调。旧版 msvcrt 可以：


.386
.model flat, stdcall
option casemap:none

includelib msvcrt.lib

; 旧版 CRT 初始化函数
_heap_init proto c
_ioinit   proto c
_cinit    proto c

; CRT 函数
printf    proto c :ptr

.data
    fmt db "Hello from CRT, value=%d", 0Ah, 0
    val dd 42

.code
start:
    ; === 手动初始化 CRT ===
    call _heap_init      ; 1. 初始化堆
    call _ioinit         ; 2. 初始化 IO
    call _cinit          ; 3. 初始化全局变量/浮点

    ; === CRT 已就绪，可以用了 ===
    invoke printf, offset fmt, val

    ; === 必须用 exit 退出，不能用 ExitProcess ===
    push 0
    call exit            ; 让 CRT 清理（刷新缓冲区、关句柄）
end start

三个关键点：

1. 顺序不能乱：堆 → IO → 全局变量。_ioinit 可能用 malloc，堆没初始化就崩 2. 退出必须用 exit：ExitProcess 直接杀进程不清理 CRT，printf 输出可能丢失（缓冲区没刷新） 3. 只适用旧版：新版 UCRT 不导出这三个函数，无法手动初始化

实际建议：两种稳妥方案

方案A：让 C 当入口（最稳）

让 C 文件提供 main 函数，C 编译器自动插入 CRT 初始化代码，汇编只是被调用的函数：


// main.c - CRT 自动初始化
extern int asm_main();
int main() {
    return asm_main();   // 调汇编写的函数
}


; asm_main.asm - CRT 已初始化，随便用
asm_main proc c
    invoke printf, offset fmt    ; 能用，不会崩
    ret
asm_main endp

方案B：不用 CRT，全用 Win32 API

| 想用的 CRT | 替代 API | |-----------|---------| | printf | wsprintfA + OutputDebugStringA | | malloc | HeapAlloc / VirtualAlloc | | strlen | 自己写几行汇编循环 | | strcpy | 自己写几行汇编循环 | | exit | ExitProcess |

Win32 API 不依赖 CRT 初始化，汇编里直接调就行。shellcode 全用 API 就是这个思路。

四种混编方式

C 与汇编混合编程有四种常见方式：联合编译、静态库、动态库、内联汇编。

四种方式总览

| | 联合编译 | 静态库 | 动态库 | 内联汇编 | |---|---------|--------|--------|---------| | 汇编在 | .asm 文件 | .lib 文件 | .dll 文件 | C 代码里 | | 编译时 | obj 拼接 | obj 塞进 exe | 运行时加载 | 编译器处理 | | 需要源码 | 是 | 否 | 否 | 是 | | exe 体积 | 小 | 大 | 小 | 小 | | 运行时依赖 | 无 | 无 | 需要 dll | 无 | | 更新方便 | 否 | 否 | 是 | 否 | | 64 位支持 | ✓ | ✓ | ✓ | ✗（MSVC） | | 适用场景 | 协作开发 | 给二进制 | 插件/热更新 | 小块关键代码 |

1. 联合编译

两个源文件分别编译，链接器拼一起。前面"C 调用汇编函数"和"汇编调用 C 函数"两节讲的就是这种。


main.c + add.asm → 各自编译成 obj → 链接成一个 exe

特点：给源码、需要编译器、最直接。

2. 静态库 (.lib)

把汇编编译成 obj，用 lib.exe 打包成 .lib。用的时候链接进来，代码在链接时塞进 exe。

制作静态库：


; add.asm - 编译成 add.obj
.386
.model flat, c
public add
.code
add proc c a:DWORD, b:DWORD
    mov eax, a
    add eax, b
    ret
add endp
end


ml /c /coff add.asm          ; 编译成 add.obj
lib /out:mylib.lib add.obj   ; 打包成 mylib.lib

使用静态库（C 侧）：


#pragma comment(lib, "mylib.lib")   // MSVC 专用，告诉链接器找这个 lib
extern int add(int a, int b);

int main() {
    return add(3, 5);   // 链接器从 mylib.lib 找到 add 的代码塞进 exe
}

使用静态库（汇编侧）：


includelib mylib.lib
add proto c a:DWORD, b:DWORD

特点：

| | 说明 | |---|------| | 代码在哪 | 链接时塞进 exe | | exe 体积 | 变大（包含库代码） | | 运行时依赖 | 无，单文件就能跑 | | 源码保护 | 不给源码，只给 lib | | 更新麻烦 | 库改了要重新链接整个程序 |

Windows SDK 的 kernel32.lib、user32.lib 都是静态库（导入库，但用法一样）。

3. 动态库 (DLL)

汇编编成 DLL，运行时加载。

制作 DLL：


; add.asm - 编译成 DLL
.386
.model flat, stdcall
option casemap:none

include windows.inc

public add

.code
add proc stdcall a:DWORD, b:DWORD
    mov eax, a
    add eax, b
    ret
add endp

; DLL 入口点（必须有）
LibMain proc hInstDLL:DWORD, reason:DWORD, reserved:DWORD
    mov eax, TRUE        ; 返回 TRUE 表示加载成功
    ret
LibMain endp

end LibMain


ml /c /coff /Cp add.asm
link /DLL /out:add.dll add.obj   ; 生成 add.dll + add.lib（导入库）

使用 DLL - 隐式调用（最常用）：

链接时用 DLL 生成的导入库 add.lib，程序启动时自动加载 DLL：


#pragma comment(lib, "add.lib")
__declspec(dllimport) int __stdcall add(int a, int b);

int main() {
    return add(3, 5);   // 像普通函数一样调
}

找不到 DLL 启动就报错。

使用 DLL - 显式调用（LoadLibrary + GetProcAddress）：

运行时决定加载哪个 DLL、什么时候加载：


#include <windows.h>

typedef int (__stdcall *ADD_FUNC)(int, int);

int main() {
    HMODULE h = LoadLibraryA("add.dll");
    ADD_FUNC my_add = (ADD_FUNC)GetProcAddress(h, "add");
    int result = my_add(3, 5);
    FreeLibrary(h);
    return result;
}

插件机制、热更新都用这个。shellcode 注入本质上就是手动版的显式调用——LoadLibrary 加载 DLL 到目标进程。

特点：

| | 说明 | |---|------| | 代码在哪 | 运行时从 DLL 加载 | | exe 体积 | 小 | | 运行时依赖 | 必须有 DLL 文件 | | 更新方便 | 换 DLL 不用重新编译 exe | | 源码保护 | 只给 DLL，不给源码 |

4. 内联汇编

C 代码里直接写汇编，不单独建文件。

MSVC 语法（VS 里用，仅 32 位）：


int add(int a, int b) {
    __asm {
        mov eax, a       ; 直接用 C 变量名
        add eax, b
        // 不用写 return，eax 就是返回值
    }
}

常见用途：


// 读取控制寄存器（C 不能直接读）
unsigned int get_cr0() {
    __asm { mov eax, cr0 }
}

// CPUID
void get_cpuid() {
    __asm {
        mov eax, 1
        cpuid
    }
}

// 原子操作
int atomic_add(int* p, int v) {
    __asm {
        mov ecx, p
        mov eax, v
        lock xadd [ecx], eax
    }
}

特点：

| 优点 | 缺点 | |------|------| | 不用单独建 .asm 文件 | MSVC 64 位不支持，只能 32 位 | | 能直接访问 C 变量 | GCC/Clang 语法不同 | | 适合写几行关键代码 | 大段汇编不如单独文件清晰 | | 编译器自动处理栈帧 | 不能用宏、条件汇编等 MASM 特性 |

MSVC 64 位的替代方案——用内建函数：


#include <intrin.h>

unsigned __int64 get_cr0() {
    return __readcr0();        // 相当于 mov eax, cr0
}

int atomic_add(int* p, int v) {
    return _InterlockedExchangeAdd((long*)p, v);  // 原子加法
}

选择建议

| 场景 | 选哪个 | |------|--------| | 和别人协作，给源码 | 联合编译 | | 只给二进制，不给源码 | 静态库 | | 运行时动态加载、插件机制 | 动态库 | | C 代码里夹几行汇编 | 内联汇编 | | shellcode 注入 | 都不是，直接写机器码字节 |

内联汇编伪指令详解

MSVC 内联汇编的内置汇编器不是完整的 MASM，只支持一小部分伪指令。

能用的伪指令

| 伪指令 | 作用 | 示例 | |--------|------|------| | _emit | 定义一个字节（替代 db） | _emit 0x90 | | ptr | 指定访问宽度 | dword ptr [esp+4] | | 标签 : | 跳转标记 | label1: jmp label1 | | offset | 取地址（仅 C 变量） | mov eax, offset val | | align | 地址对齐 | align 4 | | even | 对齐到偶数 | even | | LENGTH | 取数组元素个数 | mov eax, LENGTH arr | | TYPE | 取变量大小 | mov eax, TYPE val | | SIZE | 取总字节数 | mov eax, SIZE arr |

不能用的伪指令

| 伪指令 | 为什么不能用 | 怎么替代 | |--------|------------|---------| | db / dw / dd | 内置汇编器不认 | 用 _emit | | invoke | 没有这个机制 | 手动 push + call | | proto | 没有函数声明 | 直接用 C 函数名 | | public / extrn | 不需要 | 直接用 C 变量/函数 | | local | 不能声明局部变量 | 用 C 变量代替 | | MACRO / ENDM | 不支持宏 | 用 C 的宏或函数 | | IF / ELSE / ENDIF | 不支持条件汇编 | 用 C 的 if/else | | .data / .code | 不支持段定义 | 数据放 C 变量里 | | STRUCT / UNION | 不支持 | 用 C 的 struct | | option | 不支持 | 无 | | assume | 不支持 | fs/gs 直接用 | | includelib | 不支持 | 在项目设置里配 | | include | 不支持 | 用 C 的 #include |

核心区别

一句话区分：能直接操作指令和字节的伪指令基本能用，涉及"声明、定义、组织代码结构"的伪指令全不能用——这些交给 C 去做。

最常用的就三个：_emit（写机器码字节）、ptr（指定内存访问宽度）、标签（跳转）。

_emit 伪指令

MSVC 内联汇编里专用的数据定义伪指令，作用等同于 MASM 的 db。


__asm {
    _emit 0xE9        // 等同于 db 0E9h，定义一个字节
}

为什么需要 _emit：MSVC 内联汇编不支持 db，会直接编译报错。db 是 MASM 的伪指令，只有 .asm 文件里才能用。MSVC 内联汇编的编译器不是 MASM，是 MSVC 自己的内置汇编器，不认 db。

_emit 和 db 的区别：

| | _emit | db | |---|---------|------| | 属于 | MSVC 内联汇编专用 | MASM 通用 | | 语法 | _emit 0x90 | db 90h | | 支持情况 | MSVC 全版本稳定 | 内联汇编里不能用 | | 一次定义量 | 只能一个字节 | 可多个：db 1, 2, 3 | | 十六进制写法 | 0x90（C 风格） | 90h（汇编风格） |

多字节数据要手动拆成小端序：

| MASM | MSVC 内联汇编 | |------|--------------| | db 1, 2, 3 | _emit 1 _emit 2 _emit 3 | | dw 0x1234 | _emit 0x34 _emit 0x12 | | dd 0xDEADBEEF | _emit 0xEF _emit 0xBE _emit 0xAD _emit 0xDE |

最常见用途——写 shellcode 和 hook 跳转：


// 构造 jmp 跳转（hook 时常用）
__asm {
    _emit 0xE9               // jmp 的 opcode
    _emit 0x00               // 偏移字节1
    _emit 0x00               // 偏移字节2
    _emit 0x00               // 偏移字节3
    _emit 0x00               // 偏移字节4
}

调函数的固定写法（因为没有 invoke）


__asm {
    push 0              // 参数从右往左压
    push 0
    call dword ptr [func]   // 手动 call
    add esp, 8          // cdecl 要自己清栈
}

裸函数 (__declspec(naked))

裸函数是 MSVC 的特性，用 __declspec(naked) 声明，编译器不生成函数序言和结语——栈帧全由自己管。

普通函数 vs 裸函数

普通函数编译后，编译器自动加序言/结语：


; 编译器实际生成的普通函数
push ebp              ; ← 序言（自动加的）
mov ebp, esp
sub esp, ...          ; ← 分配局部变量空间
; ...你的代码...
mov esp, ebp          ; ← 结语（自动加的）
pop ebp
ret

裸函数什么都不加：


__declspec(naked) int add(int a, int b) {
    __asm {
        mov eax, [esp+4]    // 参数 a（没有 ebp 栈帧，直接从栈上读）
        add eax, [esp+8]    // 参数 b
        ret                  // 必须自己写 ret
    }
}

对比

| | 普通函数 | 裸函数 | |---|---------|--------| | 序言 | 自动生成 push ebp / mov ebp,esp | 没有 | | 结语 | 自动生成 pop ebp / ret | 没有 | | 参数访问 | [ebp+8] | [esp+4] | | 局部变量 | [ebp-4] 等 | 要自己 sub esp 分配 | | ret | 自动 | 必须自己写 | | 适合场景 | 正常编程 | shellcode / hook / 特殊栈操作 |

裸函数的适用场景

1. 写 shellcode——没有栈帧开销，代码干净，可直接提取机器码：


__declspec(naked) void shellcode() {
    __asm {
        push 0
        push 0
        push 0
        push 0
        mov eax, 0x77D507EA    ; MessageBoxA 地址
        call eax
        ret
    }
}

2. Hook（钩子）——栈布局精确控制，不插额外指令：


__declspec(naked) void hook_func() {
    __asm {
        pushad              ; 保存寄存器
        ; ...处理逻辑...
        popad               ; 恢复寄存器
        jmp original_func   ; 跳回原函数
    }
}

3. 自定义调用约定：


__declspec(naked) int fastcall_custom() {
    __asm {
        mov eax, ecx        ; ecx = 参数1, edx = 参数2
        add eax, edx
        ret
    }
}

裸函数的坑

1. 不能用局部变量——要自己 sub esp 分配：


__declspec(naked) void good() {
    __asm {
        sub esp, 4        // 手动分配 4 字节
        mov [esp], 5      // 当局部变量用
        add esp, 4        // 手动释放
        ret
    }
}

2. 忘了写 ret 会崩——执行完继续往下跑。

3. 参数偏移会变——push 后偏移要跟着调：


__declspec(naked) int test(int a, int b) {
    __asm {
        // [esp+0] = 返回地址, [esp+4] = a, [esp+8] = b
        push ebx           // push 后偏移 +4
        // [esp+8] = a, [esp+12] = b（偏移变了）
        mov eax, [esp+8]
        add eax, [esp+12]
        pop ebx
        ret
    }
}

裸函数和 shellcode 的关系

| | 裸函数 | shellcode | |---|--------|-----------| | 谁写 | C 编译器 + 内联汇编 | 纯汇编 | | 运行在哪 | 本进程 | 目标进程 | | 地址 | 编译时确定 | 运行时确定（要 PIC） | | 调 API | 可以用 C 函数 | 必须手动 push + call |

用裸函数写 shellcode 的好处是可以在 VS 里调试——先写成裸函数跑通，再提取机器码注入，比直接在 RadASM 里写纯汇编好调试得多。

内联汇编 vs 内联 Hook

这两个概念容易混淆，但完全不同。

| | 内联汇编 (Inline Assembly) | 内联 Hook (Inline Hook) | |---|---------------------------|------------------------| | 是什么 | 一种写代码的方式 | 一种 Hook 技术 | | 干什么 | 在 C 代码里嵌汇编 | 修改函数入口拦截调用 | | "内联"的含义 | 嵌在 C 代码里 | 改的代码是原地替换（inline patch） |

内联 Hook 的原理

把目标函数入口处的指令改成跳转到你的函数：


目标函数原样：
  0x401000: push ebp           ← 原始指令
  0x401001: mov ebp, esp

内联 Hook 后：
  0x401000: jmp my_hook         ← 被 5 字节 jmp 覆盖了
  0x401005: ...                 ← 后面原始指令被破坏

内联 Hook 三步

1. 保存原始字节——目标函数入口前 5 字节会被覆盖，先存起来 2. 写入跳转——用 jmp my_hook（5 字节 E9 xx xx xx xx）覆盖入口 3. 调原函数——恢复那 5 字节，调完再重新 hook；或用蹦床（trampoline）

为什么容易和内联汇编混

内联 Hook 的实现经常用内联汇编来写——因为要操作栈、寄存器、跳转，C 代码写不了：


__declspec(naked) void my_hook() {
    __asm {
        pushad              // 保存现场
        // ...处理逻辑...
        popad               // 恢复现场
        jmp back_to_origin  // 跳回原函数
    }
}

各种 Hook 方式对比

| Hook 类型 | 原理 | 优点 | 缺点 | |-----------|------|------|------| | 内联 Hook | 改函数入口字节 | 能拦截任何函数 | 线程安全难处理 | | IAT Hook | 改导入表里的函数指针 | 简单稳定 | 只能 hook API 调用 | | 消息 Hook | SetWindowsHookEx | 系统支持，合法 | 只能 hook 窗口消息 | | VEH Hook | 向量异常处理 | 不改代码 | 性能差（靠异常触发） |

一句话：内联汇编是工具（C 里写汇编），内联 Hook 是技术（改函数入口拦截）。内联 Hook 经常用内联汇编来实现。

内联汇编的实际价值

日常开发几乎用不到

  • 编译器优化比人写汇编强（多数场景）
  • C/C++ 本身能搞定绝大多数事
  • 64 位 MSVC 直接不支持，限制了使用范围

对学逆向的人有特定价值

| 场景 | 有没有用 | |------|---------| | 写 shellcode | 很有用——裸函数 + _emit 写机器码，能在 VS 里直接调试 | | 逆向分析 | 有用——理解编译器怎么把 C 翻译成汇编 | | Hook 开发 | 有用——裸函数控制栈帧 | | 性能优化 | 没用——编译器比你写得好 | | 正常业务开发 | 没用——完全用不到 |

最大优势：调试方便

用 VS 裸函数写 shellcode，能设断点、看寄存器、单步走——调试效率比 RadASM 纯汇编高一个量级。跑通后提取机器码注入目标进程。

最大硬伤：64 位不支持

MSVC 64 位不支持内联汇编。64 位要用内建函数或单独写 .asm 文件。

选择建议

| 需求 | 建议用什么 | |------|-----------| | 学汇编、理解指令 | VS 内联汇编，方便调试 | | 写 32 位 shellcode | VS 裸函数 + _emit | | 写 64 位程序 | 单独 .asm 文件 + 联合编译 | | 正常开发 | 纯 C/C++，别碰汇编 |
