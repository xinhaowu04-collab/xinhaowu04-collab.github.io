Frida 动态插装

Frida 是动态插装工具：把 Agent 注入目标进程，在进程内部执行 JavaScript Hook 逻辑，再通过客户端与 Agent 通讯。价值在于不必先完全读懂几千万行代码，而是围绕感兴趣的功能，动态观察函数调用、参数、返回值和调用关系。

注意：Frida 实验只用于自己编写的测试程序、课堂样本及其他明确授权的实验目标。

| 组件 | 作用 | |---|---| | frida | 交互式 REPL，可按名称或 PID 附加，也可通过 -l 加载独立 JS | | frida-ps | 枚举进程，得到进程名和 PID；也可配合 USB 设备选项 | | frida-trace | 按函数名、模块名或模块偏移批量建立跟踪，并生成可编辑的 handler | | frida Python 包 | Python 绑定，提供设备枚举、附加、脚本创建和消息收发能力 | | frida-tools | frida、frida-ps、frida-trace 等命令行工具，版本号与核心 Frida 独立 | | JavaScript Agent | 真正运行在目标进程中的 Hook 逻辑 |

传统逆向定位思路：

  • 对写文件等关键 API 下断点
  • 搜索内存中的关键数据，再对相关内存下访问断点
  • 根据功能触发时的调用栈或异常逐层定位
  • 先处理反调试，再继续单步或跟踪

传统逆向的困难在于程序规模大、目标功能分散、数据可能加密、真实 API 未知，调试器还可能触发反调试。动态插装把问题收缩为：


我关心哪个行为？
    ↓
哪些函数在行为发生时被调用？
    ↓
它们接收了什么参数、返回了什么？
    ↓
哪个调用与目标功能最相关？

"给所有函数添加日志"只是分析方向，不是默认操作。frida-trace 会根据 -i、-I、-a 等条件建立 working set，只跟踪匹配到的函数；无差别跟踪会带来巨大日志量和运行开销。

动态插装的基本关系：


Frida 客户端 ──附加/派生──> 目标进程
Frida 客户端 ──加载脚本──> Frida Agent（注入目标进程）
Agent ──onEnter──> 读取/修改参数 ──> 原函数或替代函数 ──onLeave──> 读取/修改返回值
Agent ──日志/消息──> 客户端

学习顺序：


环境安装与版本排错
    ↓
frida-ps 枚举进程 → 按 PID 附加
    ↓
frida-trace 自动 Hook 导出 API → 修改自动生成的 handler
    ↓
打印并修改参数、返回值
    ↓
独立 hook.js 手动查地址并 Interceptor.attach
    ↓
模块基址 + RVA Hook 自己的内部函数
    ↓
NativeFunction 主动调用 → Interceptor.replace 替换实现
    ↓
内存补丁、反调试观察、调用栈与 Stalker（后续课程）

"两种 Hook 方式"要按上下文区分：

| 表述层级 | 两种方式 | 说明 | |---|---|---| | 工具工作流 | frida-trace 自动 handler vs 独立 hook.js | 课堂顺序主要指这一组 | | Interceptor 机制 | Interceptor.attach vs Interceptor.replace | 观察/替换机制的区别 | | 进程时机 | 附加已运行进程 vs Frida 派生新进程 | 决定能否捕获启动初期调用，不是另一套 Interceptor |

常见误解：

| 说法 | 正解 | |---|---| | Frida 会自动为所有函数加日志 | 只有选入跟踪集合或手动安装 Hook 的函数才会被跟踪 | | Frida 支持"全平台、全指令集" | 概括性表达；以当前版本官方支持矩阵、目标系统和架构为准 | | 动态插装能代替所有静态分析 | 适合快速定位运行时行为，但函数原型、RVA、调用约定和数据结构仍常需静态分析确认 | | Hook 一个反调试 API 就能解决全部反调试 | API 型检查只是一类；直接系统调用、PEB 读取、时间差、异常和多线程检查不会自动消失 | | Hook 越多越好 | Hook 越多日志噪声和性能影响越明显；从明确行为和小范围函数集合开始 |

安装排错：Python 与 Frida 17.17.0

Frida 在 Windows 上包含两个包，版本号各自独立：


frida         → Python 绑定和本地 Frida 核心（本次 17.17.0）
frida-tools   → frida、frida-ps、frida-trace 等命令（原环境 12.4.4）

pip 允许单独升级一个包。只执行 py -m pip install frida==17.17.0 时，pip 会满足这条请求，但旧 frida-tools 12.4.4 声明 frida<17.0.0,>=16.2.2，因此可以同时出现 Successfully installed frida-17.17.0 和依赖冲突警告——核心包装上了，只是环境依赖不一致，并非安装完全失败。

第二个问题来自 Python 版本：Frida 17.17.0 的源码执行 from typing import NotRequired，而 typing.NotRequired 是 Python 3.11 才加入标准库的，Python 3.10 导入即失败。

轮子文件名 frida-17.17.0-cp37-abi3-win_amd64.whl 中，cp37-abi3 表示本地二进制扩展采用稳定 ABI、兼容多个 CPython 版本；它不能保证包内 Python 源码只用了 3.7 的标准库成员，"轮子能安装"与"源码一定能导入"是两回事。

安装与修复


py -m pip install --upgrade pip
py -m pip install frida==17.17.0
py -m pip install --upgrade frida-tools
py -m pip check

只下载不安装：py -m pip download frida==17.17.0 -d .\frida_packages。

注意：对话最初提到的 17.17.1 在 PyPI 上没有可用安装包证据，标为待确认；17.17.0 是实际安装并验证的版本。只执行 py -m pip install frida-tools 会让 pip 自选依赖组合，要固定核心版本必须显式写 frida==17.17.0。

Windows 上 Python 3.10 不必删除，与 3.12 并存，用 py 启动器选版本：


winget install -e --id Python.Python.3.12
py -0p
py -3.12 --version
py -3.12 -m pip install --upgrade pip
py -3.12 -m pip install --upgrade frida==17.17.0 frida-tools
py -3.12 -c "import frida; print(frida.__version__)"

命令路径仍指向 Python 3.10

用 where frida 查看实际执行文件。若仍指向 Python310\Scripts\frida.exe，说明裸命令 frida 由旧 Scripts 目录提供。先直接测试新环境：


"%LocalAppData%\Programs\Python\Python312\Scripts\frida.exe" --version

确认不再需要旧环境中的 Frida 后，只卸载包、不卸载 Python 3.10：


py -3.10 -m pip uninstall frida frida-tools

重新打开 CMD 再验证 where frida 和 frida --version。

Python 3.10 临时源码修补（未采用）

必须保留 Python 3.10 时，可从 Frida 的 typing 导入列表移除 NotRequired，改为 from typing_extensions import NotRequired。但修改位于 site-packages，升级或重装会覆盖，不如直接用 Python 3.11+。本次未采用。

常见误解：

| 现象 | 误解 | 正解 | |---|---|---| | Successfully installed 前有 dependency conflicts | Frida 没装上 | 核心已装上，旧 frida-tools 依赖声明不兼容 | | 已装 typing_extensions 仍报错 | 扩展包没装好 | Frida 17.17.0 直接从标准库 typing 导入，扩展包不会把成员注入 typing | | py -3.12 import frida 成功但 frida --version 报 Python310 错误 | Python 3.12 的 Frida 坏了 | Python 模块正常；PATH 仍选择旧 Python310\Scripts\frida.exe | | frida-tools 不是 17.17.0 | 版本不匹配 | frida-tools 独立版本号，只需依赖范围兼容 | | cp37-abi3 | 所有代码只要求 Python 3.7 | 只描述二进制扩展 ABI，不保证源码未用新标准库功能 |

进程枚举与附加

Frida 可按进程名或 PID 附加已运行的程序，也可由 Frida 创建新进程。基本流程：frida-ps 列出全部进程 → 找到目标 → 记录 PID → 按 PID 附加。

进程名可能重复，PID 能准确指向某一次运行实例，适合实验复现；但 PID 只在进程生命周期内有效，程序重启后要重新枚举。

| 方式 | 示例 | 特点 | |---|---|---| | 按 PID 附加 | frida -p 4196 | 精确定位当前实例 | | 按名称附加 | frida -n Notepad.exe | 简便，同名进程可能有歧义 | | 由 Frida 启动 | frida -f "HookDemo.exe" -l hook.js | 在业务逻辑执行前安装脚本，适合捕获早期调用 |

实际操作：


frida-ps
frida-ps | findstr /i notepad
frida -p 4196

findstr 只是列表过长时的可选过滤，不是 Frida 必需步骤。连接 USB 设备上的 Frida 服务用 frida-ps -U（本次只连接了 Local System）。

附加成功后在 REPL 中验证：


Process.id
Process.arch
Process.pointerSize
Process.enumerateModules()[0]

也可拆开查看主模块：


const mainModule = Process.enumerateModules()[0];
mainModule.name
mainModule.base
mainModule.size

常见误解：

| 误解 | 正解 | |---|---| | 记住一次 PID 就能永久使用 | 进程重启后要重新枚举 | | Python 是 64 位就不能附加 32 位目标 | 主机 Python 位数与目标附加能力不能简单画等号，以实际附加结果和目标架构为准 | | Process.pointerSize 是文件位数 | 反映目标进程指针宽度：32 位通常为 4，64 位通常为 8 | | 启动模式意味着程序永远挂起 | Frida 早期注入后，现代 CLI 默认在脚本加载后恢复，只有显式暂停选项才保持暂停 |

实验记录：

[Local::PID::4196 ]->

PID 4196 附加成功；目标进程名称和架构未在对话中贴出，标记待确认。

frida-trace 自动生成 handler

第一种 Hook 方式：用 frida-trace 按通配符查找函数，工具自动生成 handler 文件，然后直接编辑 handler。


frida-trace -p 4196 -i "MessageBox*"
frida-trace -p 4196 -i "user32.dll!MessageBox*"

-i 的基本格式是 [MODULE!]FUNCTION，模块名和函数名都可用通配符。

用户最初执行 frida -p 4196 -i "MessageBox*" 报 unrecognized arguments: -i——-i 属于 frida-trace，不属于 frida REPL：

| 命令 | 主要用途 | 支持 -i | |---|---|---| | frida | REPL、执行表达式、加载独立脚本 | 否 | | frida-trace | 匹配函数、批量跟踪、生成 handler | 是 |

frida-trace 的自动化工作：


解析 -i 规则 → 枚举已加载模块和导出函数 → 建立 working set
→ 为匹配函数安装跟踪 → 生成 __handlers__ 下的 JS 文件 → 监视文件变化并自动重载

为避免 handler 生成在用户目录根部，先进入实验目录：


mkdir C:\Users\Lenovo\Documents\FridaLab
cd /d C:\Users\Lenovo\Documents\FridaLab
frida-trace -p 4196 -i "user32.dll!MessageBox*"

本次实际从 C:\Users\Lenovo 启动，handler 生成在 C:\Users\Lenovo\__handlers__\user32.dll\，共 8 个：


MessageBoxA.js          MessageBoxW.js
MessageBoxExA.js        MessageBoxExW.js
MessageBoxTimeoutA.js   MessageBoxTimeoutW.js
MessageBoxIndirectA.js  MessageBoxIndirectW.js

保存 handler 只触发重载，不会主动调用目标 API；只有目标程序下一次调用对应函数时 onEnter/onLeave 才执行。目标持续弹窗时，看起来像"保存后马上打印"。

常见误解：

  • 老师说的"直接改默认生成的文件"指 __handlers__\user32.dll\MessageBoxA.js。排查过程中曾猜测是 REPL 内部 Agent Python312\Lib\site-packages\frida_tools\repl_agent.js（可用 py -3.12 -c "import frida_tools, pathlib; print(pathlib.Path(frida_tools.__file__).parent / 'repl_agent.js')" 定位），最终结论以 __handlers__ 为准，不要改 site-packages 内部文件。
  • 自动生成 8 个 handler 不代表目标调用了 8 个函数——"生成"只说明通配符匹配到 8 个导出。

实验记录：


MessageBoxExA: Auto-generated handler at "C:\Users\Lenovo\__handlers__\user32.dll\MessageBoxExA.js"
...（共 8 个）
Started tracing 8 functions.
Web UI available at http://localhost:63835/

端口 63835 是当次运行的随机端口，不是固定值。控制台还推荐了官方 GUI Luma，本次未使用。

实际调用日志：

MessageBoxA handler：参数与返回值打印

自动生成的原始 handler：


defineHandler({
  onEnter(log, args, state) {
    log('MessageBoxA()');
  },

  onLeave(log, retval, state) {
  }
});

回调签名与参数含义：

| 名称 | 含义 | |---|---| | log | frida-trace 提供的格式化日志函数，显示线程和调用层级 | | args | 目标函数参数数组，元素以 NativePointer 形式暴露 | | state | handler 状态对象，可保存需要持续引用的数据 | | retval | 原始返回值对象，可读取或调用 replace() 修改 |

MessageBoxA 函数原型：


int MessageBoxA(
    HWND   hWnd,
    LPCSTR lpText,
    LPCSTR lpCaption,
    UINT   uType
);

参数映射：

| Frida 参数 | Win32 参数 | 解释方式 | |---|---|---| | args[0] | hWnd | 窗口句柄，保留为指针值显示 | | args[1] | lpText | ANSI 字符串指针，readAnsiString() | | args[2] | lpCaption | ANSI 字符串指针，readAnsiString() | | args[3] | uType | UINT 标志，toUInt32() | | retval | int | 按钮编号，toInt32() |

args[1] 不是 JS 字符串，而是目标进程中的地址，指向以 0 结尾的 ANSI 字节串，要通过指针读取内容：args[1].readAnsiString()。

A/W 版区别：

| API | 参数类型 | Frida 读取方式 | |---|---|---| | MessageBoxA | LPCSTR，Windows ANSI | readAnsiString() | | MessageBoxW | LPCWSTR，UTF-16 | readUtf16String() |

注意：老师截图对 MessageBoxA 用了 readUtf8String()。英文 ASCII 在 UTF-8 和常见 ANSI 编码中字节相同，所以英文演示能成功；但遇到中文 ANSI/GBK 字节可能乱码或失败。按 API 语义应使用 readAnsiString()。

模板字符串必须用反引号，${表达式} 先计算再插入：


log([MessageBoxA] 返回值 = ${result});   // 正确
log('[MessageBoxA] 返回值 = ${result}');   // 错误：原样输出 ${result}

三个典型问题代码

模板字符串用了单引号：


log('hWnd = ${hWnd}');              // 错误
log(hWnd = ${hWnd});              // 修正

变量名叫 textPtr 但存的已是字符串：


const textPtr = args[1].readAnsiString();   // 能工作，命名误导
const textAddress = args[1];                // 更清楚的写法
const text = textAddress.readAnsiString();

不检查空指针：


const text = args[1].isNull()
  ? '<NULL>'
  : args[1].readAnsiString();

const caption = args[2].isNull()
  ? '<NULL>'
  : args[2].readAnsiString();

修正后的打印版本


defineHandler({
  onEnter(log, args, state) {
    log(MessageBoxA());

    const hWnd = args[0];

    const text = args[1].isNull()
      ? '<NULL>'
      : args[1].readAnsiString();

    const caption = args[2].isNull()
      ? '<NULL>'
      : args[2].readAnsiString();

    const type = args[3].toUInt32();

    log(hWnd = ${hWnd});
    log(text = ${text});
    log(caption = ${caption});
    log(type = ${type}，十六进制 = 0x${type.toString(16)});
  },

  onLeave(log, retval, state) {
    const result = retval.toInt32();
    log(返回值 = ${result});
  }
});

onEnter 在弹窗显示前执行；onLeave 必须等用户点击按钮、MessageBoxA 准备返回时才执行，没立即输出不是 Hook 失败。

常见返回值：

| 数值 | 常量 | 含义 | |---:|---|---| | 1 | IDOK | 确定 | | 2 | IDCANCEL | 取消 | | 3 | IDABORT | 中止 | | 4 | IDRETRY | 重试 | | 5 | IDIGNORE | 忽略 | | 6 | IDYES | 是 | | 7 | IDNO | 否 |

常见误解：

| 误解 | 正解 | |---|---| | textPtr 这个名字证明它还是指针 | 名字不决定类型；readAnsiString() 后得到的是 JS 字符串 | | args[3] 直接打印就是普通整数 | 以 NativePointer 形式提供，按 UINT 解释应用 toUInt32() | | retval 直接打印就是 C 的 int | 应按返回类型调用 toInt32() 等转换方法 | | readUtf8String() 可用于所有 A 版 API | A 表示 Windows ANSI，不等于 UTF-8；ASCII 只是碰巧兼容 | | handler 可以混用其他 API 的读取方式 | handler 必须按自己对应 API 的函数原型解释参数 |

实验记录：用户最终版本用 const textPtr = args[1].readAnsiString() 和 type.toInt32()，对小值 uType 通常能显示，但更严谨是 toUInt32()；textPtr 命名不准确但不导致运行错误。该版参数打印的完整控制台输出未贴出，具体标题、正文、uType 和按钮返回值均为待回验。

修改参数与返回值

参数修改在 onEnter，返回值修改在 onLeave：


进入 MessageBoxA → onEnter：查看/替换 args[] → MessageBoxA 用修改后的参数执行
→ 用户点击按钮 → onLeave：查看/替换 retval → 调用者收到最终返回值

字符串参数的本质是地址，JS 普通字符串不能直接作为 LPCSTR 传入，要先在目标进程申请内存并编码：Memory.allocAnsiString('hello Frida') 返回 NativePointer，再把参数改成新地址。返回值读取用 retval.toInt32()，修改用 retval.replace(100)。

申请新字符串并替换参数指针


state.newtext = Memory.allocAnsiString(hello Frida);
state.newcaption = Memory.allocAnsiString(Frida Hook);

args[1] = state.newtext;
args[2] = state.newcaption;

log(newtext = ${state.newtext.readAnsiString()});
log(newcaption = ${state.newcaption.readAnsiString()});

指针保存在 state 中，让 handler 持续持有这些对象。

问题代码：对象属性与局部变量混淆。


state.newtext = Memory.allocAnsiString(hello Frida);
args[1] = newtext;        // ReferenceError: 'newtext' is not defined
args[1] = state.newtext;  // 修正

state.newtext 是 state 的属性，不会自动声明局部变量 newtext。

注意地址与内容的区别：${state.newtext} 打印地址（如 0x1f53a990250），${state.newtext.readAnsiString()} 才打印内容。

修改 uType

参数数组元素以指针大小的值暴露，写整数标志：


args[3] = ptr(0x04);

| 数值 | 含义 | |---:|---| | 0x00 | MB_OK | | 0x01 | MB_OKCANCEL | | 0x04 | MB_YESNO | | 0x40 | MB_ICONINFORMATION |

修改返回值

问题代码：retval.add(100) 只是指针运算，算出"原地址加 100"的新 NativePointer 且结果被丢弃，不会修改真实返回值。


retval.replace(100);                              // 强制返回 100

const oldResult = retval.toInt32();               // 在原结果上加 100
retval.replace(oldResult + 100);

retval.replace(1);   // IDOK，更符合 MessageBoxA 语义
retval.replace(6);   // IDYES
retval.replace(7);   // IDNO

验证前后变化要各打印一次：


const oldResult = retval.toInt32();
log(修改前返回值 = ${oldResult});

retval.replace(100);

log(修改后返回值 = ${retval.toInt32()});

综合版本


defineHandler({
  onEnter(log, args, state) {
    log(MessageBoxA());
    const hWnd = args[0];
    const textPtr = args[1].readAnsiString();
    const captionPtr = args[2].readAnsiString();
    const type = args[3];

    log(hWnd = ${hWnd});
    log(text = ${textPtr});
    log(caption = ${captionPtr});
    log(type = ${type.toInt32()});

    state.newtext = Memory.allocAnsiString(hello Frida);
    state.newcaption = Memory.allocAnsiString(Frida Hook);
    args[1] = state.newtext;
    args[2] = state.newcaption;

    log(newtext = ${state.newtext.readAnsiString()});
    log(newcaption = ${state.newcaption.readAnsiString()});
  },

  onLeave(log, retval, state) {
    log(返回值 = ${retval.toInt32()});
    retval.replace(100);
    log(修改后返回值 = ${retval.toInt32()});
  }
});

建议的稳健性改进：


const text = args[1].isNull() ? '<NULL>' : args[1].readAnsiString();
const caption = args[2].isNull() ? '<NULL>' : args[2].readAnsiString();
const type = args[3].toUInt32();

常见误解：

  • 老师截图中的 args[1].writeUtf8String("Hooked by Frida!") 直接覆盖原缓冲区，必须同时满足：原内存可写、缓冲区足够大、编码兼容。新字符串更长或原内存只读时可能越界或异常；申请新内存替换指针更稳妥。
  • retval.replace(100) 不会让弹窗重新显示：onLeave 发生在弹窗关闭后，替换只影响调用者收到的值。
  • 目标程序可能完全忽略返回值：即使替换成功，调用者不读结果，程序外观就不变。验证 Frida 层是否修改应在 replace() 前后打印；验证业务效果要求目标程序根据返回值分支。
  • 100 不是标准按钮返回值，调用者用 switch 可能落入默认分支；功能实验更适合用 1、2、6、7。

独立 JS 与 Interceptor.attach

第二种 Hook 方式：脚本自己查找模块、查找导出地址、调用 Interceptor.attach。与 frida-trace 底层目标相同，外层职责不同：

| frida-trace handler | 独立 hook.js | |---|---| | 工具已找到函数地址 | 脚本自己找模块和函数地址 | | 工具已安装跟踪 | 脚本自己调用 Interceptor.attach | | onEnter(log,args,state) | onEnter(args) | | onLeave(log,retval,state) | onLeave(retval) | | 使用 log() | 常用 console.log() 或 send() |

自动 handler 适合快速批量观察；独立脚本适合精确控制：自己决定地址解析方式、同时 Hook 多个不相关函数、维护共享数据、Hook 未导出函数、用 NativeFunction 主动调用、用 Interceptor.replace 替换实现。

老师截图的核心代码：


function HookMessageBoxA() {
  console.log("Frida HookMessageBoxA");

  const mou = Process.getModuleByName("user32.dll");
  const msgBoxAddr = mou.getExportByName("MessageBoxA");

  if (msgBoxAddr) {
    console.log("[+] 找到 MessageBoxA: " + msgBoxAddr);

    Interceptor.attach(msgBoxAddr, {
      onEnter: function (args) {
        console.log("==== 拦截到弹窗 ====");
        console.log("标题: " + args[2].readUtf8String());
        console.log("内容: " + args[1].readUtf8String());

        // 修改弹窗内容
        // args[1].writeUtf8String("Hooked by Frida!");
      }
    });
  }
}

函数声明本身不会自动执行，完整脚本还需显式调用 HookMessageBoxA(); 或 setImmediate(HookMessageBoxA);。

独立脚本基本结构：


function hookApi() {
  const module = Process.getModuleByName('user32.dll');
  const address = module.getExportByName('MessageBoxA');

  console.log(user32.dll基址 = ${module.base});
  console.log(MessageBoxA地址 = ${address});

  Interceptor.attach(address, {
    onEnter(args) {
      const text = args[1].isNull()
        ? '<NULL>'
        : args[1].readAnsiString();

      console.log(正文 = ${text});
    },

    onLeave(retval) {
      console.log(返回值 = ${retval.toInt32()});
    }
  });
}

setImmediate(hookApi);

Interceptor.attach() 返回 listener，可单独撤销：


const listener = Interceptor.attach(address, {
  onEnter(args) {
  }
});

listener.detach();

| 误解 | 正解 | |---|---| | 这是完全不同的底层 Hook 技术 | 两者最终都用 Frida Interceptor，区别是自动化层级 | | 可把 Interceptor.attach 代码直接粘进生成的 handler | handler 已由 frida-trace 安装 Hook，重复手动 attach 会混淆职责 | | onEnter: function(args) 与 onEnter(args) 功能不同 | 前者是传统属性函数写法，后者是对象方法简写 | | 独立脚本只需声明函数 | 还必须调用函数或安排它执行 | | 老师对 MessageBoxA 用 readUtf8String() 可推广到所有中文场景 | ASCII 演示可行；按 Win32 语义应优先 ANSI |

Hook 未导出函数：模块基址、VA 与 RVA

系统 API 可通过导出名找到；自己程序的内部函数往往没有导出名，要从静态分析工具得到 RVA（函数相对模块基址的偏移）：


RVA       = 静态VA - 默认ImageBase
运行时VA  = 当前模块基址 + RVA

注意：不能把磁盘文件偏移 FOA 直接加到模块内存基址。

查找模块的两种接口：

| 接口 | 模块不存在时 | |---|---| | findModuleByName() | 返回 null，适合自己写条件分支 | | getModuleByName() | 抛出异常，适合"模块必须存在"的场景 |


const module = Process.findModuleByName('HookDemo.exe');

if (module === null) {
  throw new Error('HookDemo.exe 尚未加载');
}

ASLR 使程序每次运行的模块基址可能变化，直接把 IDA 里的静态地址当运行时绝对地址会 Hook 到错误位置；RVA 相对模块内部布局稳定，因此用 module.base.add(rva)。

建议自己准备 32 位 Debug 测试程序：

    return a + b;

  • 使用 x86 Debug，关闭优化

NativeFunction 主动调用与 Interceptor.replace

NativeFunction 把本地函数地址包装成 JS 可调用对象；Interceptor.replace 把目标函数后续调用重定向到新的 NativeCallback 实现。


attach：  调用者 → onEnter → 原函数 → onLeave → 调用者
replace： 调用者 → replacement →（可选：主动调用原函数）→ 调用者

attach 适合旁路观察和局部修改，原函数自动执行；replace 适合完全或部分接管实现，原函数不会自动执行。

replace 与程序是否已运行没有必然关系：

  • 附加已运行进程后安装：只影响安装后的后续调用
  • 由 Frida 创建进程并尽早加载脚本：可捕获启动初期调用
  • 安装前已发生的调用无法倒退捕获
  • 已进入执行中的一次调用通常不会被中途改写

NativeFunction 主动调用内部函数时，地址正确只是第一步，还要准确声明：返回值类型、参数数量和类型、x86 调用约定、是否有隐藏 this、是否依赖特定对象/线程/TLS/初始化状态、是否会造成重入。

replace 比 attach 多一项硬要求：替代实现必须通过 NativeCallback 准确声明返回类型、参数类型和 ABI。attach 构造时不要求完整原型，但解释 args[] 时仍必须知道真实原型。

基本用法

包装原函数：


const original = new NativeFunction(
  functionAddress,
  'int',
  ['int', 'int'],
  Process.arch === 'ia32' ? 'stdcall' : 'default'
);

替代函数骨架：


const replacement = new NativeCallback(
  function (a, b) {
    console.log(a = ${a}, b = ${b});

    // 完全替换：直接返回自己的结果
    return 1234;

    // 部分替换时可主动调用 original(a, b)
  },
  'int',
  ['int', 'int'],
  Process.arch === 'ia32' ? 'stdcall' : 'default'
);

Interceptor.replace(functionAddress, replacement);

恢复原函数：Interceptor.revert(functionAddress);

MessageBoxW 完整替换模板

原型：


int MessageBoxW(
    HWND    hWnd,
    LPCWSTR lpText,
    LPCWSTR lpCaption,
    UINT    uType
);


const user32 = Process.getModuleByName('user32.dll');
const messageBoxW = user32.getExportByName('MessageBoxW');

const argTypes = [
  'pointer',
  'pointer',
  'pointer',
  'uint'
];

const abi = Process.arch === 'ia32'
  ? 'stdcall'
  : 'default';

const originalMessageBoxW = new NativeFunction(
  messageBoxW,
  'int',
  argTypes,
  abi
);

const newText = Memory.allocUtf16String('Hooked by Frida');
const newCaption = Memory.allocUtf16String('Interceptor.replace');

const replacement = new NativeCallback(
  function (hWnd, text, caption, type) {
    // 部分替换：手动调用原函数
    return originalMessageBoxW(
      hWnd,
      newText,
      newCaption,
      type
    );
  },
  'int',
  argTypes,
  abi
);

Interceptor.replace(messageBoxW, replacement);

若 replacement 不调用 originalMessageBoxW() 而直接 return 1，就是完全接管，原弹窗逻辑不会执行。调用原地址的 NativeFunction 用于在 replacement 内显式进入原实现——"替换"不等于"原函数永远不能再调用"。

加载方式：


frida -p PID -l replace.js
frida -f "HookDemo.exe" -l replace.js

常见误解：

| 误解 | 正解 | |---|---| | replace 必须在程序没运行时使用 | 目标函数已加载、地址可得即可安装；越晚越会漏掉早期调用 | | replace 后原函数仍自动执行 | 不会，除非 replacement 显式通过 NativeFunction 调用原实现 | | replace 会修改磁盘 EXE | 只改当前进程的执行路径，不改磁盘文件 | | 替换脚本退出后永久有效 | 可用 Interceptor.revert() 恢复；脚本卸载或进程结束也不等于磁盘被永久修改 | | NativeFunction 只要地址对就安全 | 原型、ABI、对象状态和线程环境任何一项错误都可能崩溃 | | 主动调用内部算法就能直接"穷举" | 只适用于明确授权的受控实验，且函数必须能在当前状态下独立、重复、安全调用 |
