资源与 TLS

PE 结构

资源与 TLS

资源表（索引 2）的树形结构与解析，以及线程局部存储体系：TLS 目录（索引 9）、动态 TLS、静态 TLS 与 thread_local、TLS 回调。

资源表

资源表位于 DataDirectory[IMAGE_DIRECTORY_ENTRY_RESOURCE]（DataDirectory[2]），保存图标、光标、位图、菜单、对话框、字符串、版本信息、Manifest 和自定义二进制数据等。它不是简单数组，而是一棵树：


Type（类型）
  ↓
Name / ID（名称或编号）
  ↓
Language（语言）
  ↓
IMAGE_RESOURCE_DATA_ENTRY
  ↓
实际资源数据

每一级目录头，16 字节：


typedef struct _IMAGE_RESOURCE_DIRECTORY
{
    DWORD Characteristics;
    DWORD TimeDateStamp;
    WORD  MajorVersion;
    WORD  MinorVersion;
    WORD  NumberOfNamedEntries;
    WORD  NumberOfIdEntries;
} IMAGE_RESOURCE_DIRECTORY;

紧随其后的表项数为 NumberOfNamedEntries + NumberOfIdEntries。每个目录项 8 字节：


typedef struct _IMAGE_RESOURCE_DIRECTORY_ENTRY
{
    union
    {
        DWORD Name;
        WORD  Id;
    };
    union
    {
        DWORD OffsetToData;
        struct
        {
            DWORD OffsetToDirectory : 31;
            DWORD DataIsDirectory   : 1;
        };
    };
} IMAGE_RESOURCE_DIRECTORY_ENTRY;

名称字符串：


typedef struct _IMAGE_RESOURCE_DIR_STRING_U
{
    WORD  Length;
    WCHAR NameString[1];
} IMAGE_RESOURCE_DIR_STRING_U;

叶子数据描述符，也是 16 字节：


typedef struct _IMAGE_RESOURCE_DATA_ENTRY
{
    DWORD OffsetToData;  // 实际资源数据 RVA
    DWORD Size;
    DWORD CodePage;
    DWORD Reserved;
} IMAGE_RESOURCE_DATA_ENTRY;

目录项的两个 DWORD 都复用最高位作标志：


第一个 DWORD：
最高位 0 → 低位是整数 ID
最高位 1 → 低 31 位是相对资源根的名称字符串偏移

第二个 DWORD：
最高位 1 → 低 31 位指向下一层目录
最高位 0 → 低 31 位指向 IMAGE_RESOURCE_DATA_ENTRY

最关键的两种地址语义：

| 位置 | 地址含义 | |---|---| | 目录项中的名称、子目录、数据描述符偏移 | 相对整棵资源树根的偏移 | | IMAGE_RESOURCE_DATA_ENTRY.OffsetToData | 实际资源数据的 RVA |

字符串名称使用 UTF-16，长度由前置 WORD Length 指定，不应依赖 \0 终止。

常见资源类型：

| ID | 类型 | |---:|---| | 1 | RT_CURSOR | | 2 | RT_BITMAP | | 3 | RT_ICON | | 4 | RT_MENU | | 5 | RT_DIALOG | | 6 | RT_STRING | | 9 | RT_ACCELERATOR | | 10 | RT_RCDATA | | 11 | RT_MESSAGETABLE | | 12 | RT_GROUP_CURSOR | | 14 | RT_GROUP_ICON | | 16 | RT_VERSION | | 24 | RT_MANIFEST |

RT_GROUP_ICON 描述一组图标并引用多个 RT_ICON；提取程序图标时不能只随便取一个 RT_ICON。

解析步骤：


1. 检查 NumberOfRvaAndSizes > 2。
2. 记录资源根 RVA = DataDirectory[2].VirtualAddress。
3. 资源根 RVA → FOA，读取 16 字节目录头。
4. 遍历 NamedEntries + IdEntries 个 8 字节表项。
5. 第一个 DWORD 最高位决定名称还是整数 ID。
6. 第二个 DWORD 最高位决定递归到子目录还是读取数据描述符。
7. 目录内部目标 RVA = 资源根 RVA + (值 & 7FFFFFFFh)。
8. 叶子 IMAGE_RESOURCE_DATA_ENTRY.OffsetToData 直接按 RVA 转 FOA。
9. 按 Size 读取实际资源数据。
10. 对目录深度、重复偏移、条目数量和所有范围进行限制。

软件运行时可按类型、名称和语言查找：


FindResource / FindResourceEx
  ↓
LoadResource
  ↓
LockResource
  ↓
得到资源数据指针

SizeofResource → 取得资源大小

注意：

  • 资源表是树，不是线性数组；只读一层会丢失名称、语言或数据叶子
  • 所有目录内部偏移都相对于资源根，不是相对当前目录
  • 名称偏移不是普通 RVA，先加资源根 RVA
  • 叶子 IMAGE_RESOURCE_DATA_ENTRY.OffsetToData 已经是 RVA，不能再加资源根
  • 名称字符串是长度前缀 UTF-16，不应盲找 \0
  • .rsrc 只是常见节名，应以数据目录为准
  • CodePage 要结合资源类型解释；图标、位图等二进制资源不一定按文本代码页处理
  • Reserved 应为 0；非零要提示而不能随意解释
  • 递归解析必须限制深度并检测循环偏移，避免异常文件导致死循环

计算示例：


资源根 RVA = 00005000
资源目录 Size = 00001000
资源根 FOA = 00002600

类型项：


Name         = 00000018
OffsetToData = 80000040

Name 最高位为 0：ID = 18h = 24 = RT_MANIFEST
OffsetToData 最高位为 1：指向子目录

子目录 RVA = 00005000 + 00000040 = 00005040

最终语言层表项 OffsetToData = 000000A0，最高位为 0，目标是数据描述符：


数据描述符 RVA = 00005000 + 000000A0 = 000050A0

描述符内容：


OffsetToData = 00005200  // 直接是实际资源 RVA
Size         = 00000180
CodePage     = 000004B0
Reserved     = 00000000

00005200 RVA 转为 FOA 00002800，实际资源位于文件 FOA 00002800，长度 180h 字节。示例路径：


Type=24 (Manifest) → Name=1 → Language=0409h → 数据描述符 → 实际资源

TLS 表

TLS 表位于 DataDirectory[IMAGE_DIRECTORY_ENTRY_TLS]（DataDirectory[9]），描述静态线程局部存储：同一个声明在每个线程中都有独立的数据副本。它还可提供进程/线程生命周期中自动调用的 TLS 回调数组。

目录入口 VirtualAddress 是 TLS 目录结构的 RVA。PE32 结构：


typedef struct _IMAGE_TLS_DIRECTORY32
{
    DWORD StartAddressOfRawData;
    DWORD EndAddressOfRawData;
    DWORD AddressOfIndex;
    DWORD AddressOfCallBacks;
    DWORD SizeOfZeroFill;
    DWORD Characteristics;
} IMAGE_TLS_DIRECTORY32;

PE32 大小 24 字节（18h）；PE32+ 的前四个地址字段为 8 字节，结构大小 40 字节（28h）。

| 偏移 | 大小 | 字段 | |---:|---:|---| | +00 | 4 | StartAddressOfRawData | | +04 | 4 | EndAddressOfRawData | | +08 | 4 | AddressOfIndex | | +0C | 4 | AddressOfCallBacks | | +10 | 4 | SizeOfZeroFill | | +14 | 4 | Characteristics |

TLS 目录主要描述四件事：TLS 初始化模板在哪里、还要追加多少零、加载器把模块 TLS 索引写到哪里、进程/线程生命周期要调用哪些 TLS 回调。

地址语义是本节最关键的规则：目录入口 DataDirectory[9].VirtualAddress 是 RVA，但结构内前四个字段 StartAddressOfRawData、EndAddressOfRawData、AddressOfIndex、AddressOfCallBacks 都是 VA。磁盘解析时先做 字段 VA - ImageBase = RVA，再 RVA→FOA。这些 VA 通常还需要相应重定位，因为 ASLR 或手工加载可能改变模块实际基址。

初始化模板与零填充


已初始化模板大小 = EndAddressOfRawData - StartAddressOfRawData
每线程 TLS 块大小 = 模板大小 + SizeOfZeroFill

每个线程创建时，加载器为该模块分配线程私有 TLS 块，复制模板，再补 SizeOfZeroFill 个零。

AddressOfIndex

它不是 TLS 索引值，而是保存索引的变量地址。加载器给模块分配索引后执行概念操作 [AddressOfIndex] = TLS Index。编译器生成的访问逻辑大致是：


找到当前线程 TLS 数组
  ↓
读取当前模块 TLS 索引
  ↓
索引到当前线程中的模块 TLS 块
  ↓
加变量在块内的偏移
  ↓
访问本线程自己的变量

x86 上可通过 FS 相关的线程环境机制找到线程数据；这是编译器和加载器协同完成的底层过程。

解析步骤：


1. 检查 NumberOfRvaAndSizes > 9。
2. DataDirectory[9].VirtualAddress：按 RVA 转 FOA。
3. 根据 PE32/PE32+ 选择结构。
4. TLS 结构前四字段按 VA 处理：减 ImageBase 后再 RVA→FOA。
5. 验证 Start <= End，模板范围位于有效映像/文件范围。
6. 计算模板大小和总 TLS 大小，检查加法溢出。
7. AddressOfIndex 应指向合适的可写映像区域。
8. AddressOfCallBacks 指向的数组应有边界并以 0 结束。
9. 回调地址应位于有效映像范围，运行时还要考虑重定位后的实际 VA。

手工加载带静态 TLS 的 PE，不能只完成头/节复制、重定位、导入和跳 OEP；还要初始化 TLS 索引、为当前线程分配并复制模板、补零、写入索引、最后按顺序调用 TLS 回调。

注意：

  • TLS 目录入口是 RVA，但结构中的前四个字段是 VA
  • EndAddressOfRawData - StartAddressOfRawData 是模板范围长度；不要额外加 1
  • AddressOfIndex 是索引变量的地址，不是索引本身
  • AddressOfCallBacks 是回调数组的 VA；数组元素也保存回调 VA
  • TLS 数据常在 .tls，回调数组可能在 .rdata，回调代码可能在 .text；都不能依赖节名
  • 静态 TLS 解决每线程数据，动态 TlsAlloc API 不依赖 PE TLS 目录
  • 只调用 TLS 回调而没有先建立正确的 TLS 数据，回调访问静态 TLS 变量时仍可能崩溃

计算示例：


ImageBase = 00400000
DataDirectory[9].VirtualAddress = 00005000  // TLS 目录 RVA

StartAddressOfRawData = 00406000  // VA
EndAddressOfRawData   = 00406008  // VA
AddressOfIndex        = 00406100  // VA
AddressOfCallBacks    = 00406200  // VA
SizeOfZeroFill        = 00000004
Characteristics       = 00000000

换算：


TLS 模板 RVA   = 00406000 - 00400000 = 00006000
Index 变量 RVA = 00406100 - 00400000 = 00006100
回调数组 RVA   = 00406200 - 00400000 = 00006200

模板大小 = 00406008 - 00406000 = 8 字节
总 TLS 块 = 8 + 4 = 12 字节

模板字节 0A 00 00 00 14 00 00 00 按小端可表示两个初值 10 和 20；每线程再追加 4 字节零。加载器分配 TLS Index = 3 时，[00406100] = 00000003。

动态 TLS（TlsAlloc）

动态 TLS 是在程序运行时申请一个进程内 TLS 索引，并让每个线程在同一索引下保存自己的值。它不依赖 IMAGE_TLS_DIRECTORY。

四个主要 API：


DWORD  TlsAlloc();
BOOL   TlsSetValue(DWORD index, LPVOID value);
LPVOID TlsGetValue(DWORD index);
BOOL   TlsFree(DWORD index);

| API | 责任 | |---|---| | TlsAlloc | 申请进程内索引；失败返回 TLS_OUT_OF_INDEXES | | TlsSetValue | 给调用它的当前线程写入一个槽位值 | | TlsGetValue | 从调用它的当前线程读取槽位值 | | TlsFree | 释放索引，不释放槽位值指向的堆内存 |

索引由进程共享，但槽位属于每个线程：


g_tlsIndex = 5

线程 A 的槽位 5 → A 的数据
线程 B 的槽位 5 → B 的数据
线程 C 的槽位 5 → C 的数据

核心是：索引相同，槽位值可以不同。槽位类型是 LPVOID，通常保存每线程上下文指针，例如错误状态、日志缓冲区、缓存或解析上下文。API 只负责保存/取出值，不负责对象分配、析构或释放。

完整示例——每个线程保存自己的计数器：


#include <windows.h>
#include <stdio.h>

struct ThreadData
{
    int counter;
};

DWORD g_tlsIndex = TLS_OUT_OF_INDEXES;

DWORD WINAPI WorkerThread(LPVOID)
{
    ThreadData* data =
        static_cast<ThreadData*>(
            HeapAlloc(GetProcessHeap(),
                      HEAP_ZERO_MEMORY,
                      sizeof(ThreadData)));

    if (data == nullptr)
    {
        return 1;
    }

    data->counter = 0;

    if (!TlsSetValue(g_tlsIndex, data))
    {
        HeapFree(GetProcessHeap(), 0, data);
        return 1;
    }

    for (int i = 0; i < 3; ++i)
    {
        ThreadData* current =
            static_cast<ThreadData*>(
                TlsGetValue(g_tlsIndex));

        ++current->counter;

        printf("线程 %lu 的计数器 = %d\n",
               GetCurrentThreadId(),
               current->counter);

        Sleep(10);
    }

    ThreadData* current =
        static_cast<ThreadData*>(
            TlsGetValue(g_tlsIndex));

    HeapFree(GetProcessHeap(), 0, current);
    TlsSetValue(g_tlsIndex, nullptr);
    return 0;
}

int main()
{
    g_tlsIndex = TlsAlloc();

    if (g_tlsIndex == TLS_OUT_OF_INDEXES)
    {
        return 1;
    }

    HANDLE threads[2];

    threads[0] = CreateThread(
        nullptr, 0, WorkerThread, nullptr, 0, nullptr);

    threads[1] = CreateThread(
        nullptr, 0, WorkerThread, nullptr, 0, nullptr);

    WaitForMultipleObjects(2, threads, TRUE, INFINITE);

    CloseHandle(threads[0]);
    CloseHandle(threads[1]);

    TlsFree(g_tlsIndex);
    return 0;
}

生命周期顺序：


进程：TlsAlloc
  ↓
每线程：分配 ThreadData → TlsSetValue
  ↓
每线程：TlsGetValue → 使用自己的数据
  ↓
每线程退出前：释放自己的 ThreadData → 槽位置空
  ↓
所有线程结束：TlsFree 释放进程索引

动态 TLS 也可使用第一次访问时发现槽位为空、再为当前线程分配的惰性初始化方式；若在 DLL 中用 DllMain 管理线程创建/退出，还要遵守加载器上下文的限制，不能把 TLS API 当成自动析构机制。

注意：

  • TlsAlloc 返回的是索引，不是线程编号，也不是数据地址
  • TlsSetValue 只修改当前线程的槽位
  • TlsFree 不会释放 HeapAlloc/new 得到的每线程对象
  • 动态 TLS 不会自动调用 DLL_THREAD_ATTACH/DETACH，也不会自动为每线程分配数据
  • 把同一个全局对象地址放进每个线程的槽位，数据仍然共享，仍可能需要同步
  • TLS 让槽位线程独立，不等于它指向的一切都自动线程安全
  • 多线程输出顺序受调度影响，交错顺序不是固定结论

地址模型示例：


g_tlsIndex = 5

线程 A：TlsSetValue(5, 0012A000)
线程 B：TlsSetValue(5, 0034B000)

线程 A：TlsGetValue(5) → 0012A000
线程 B：TlsGetValue(5) → 0034B000

可能输出：


线程1000 的计数器 = 1
线程1001 的计数器 = 1
线程1000 的计数器 = 2
线程1001 的计数器 = 2
线程1000 的计数器 = 3
线程1001 的计数器 = 3

静态 TLS 与 thread_local

静态 TLS 是编译、链接阶段已经声明好的线程局部数据：工具链把初始化模板和 TLS 目录写入 PE，Windows 加载器为每个线程复制一份。两种写法：


__declspec(thread) int g_counter = 10; // MSVC 扩展
thread_local int g_counter = 10;       // C++11 标准写法

thread_local 描述变量具有线程存储期：每个线程独立一份、分别初始化、分别修改，并在线程结束时销毁。它不是线程对象，也不会创建或启动线程。

源代码与 PE 的关系：


thread_local / __declspec(thread)
  ↓ 编译、链接
.tls 相关模板 + IMAGE_TLS_DIRECTORY
  ↓ Windows 加载器
每个线程得到独立 TLS 块

编译器把对静态 TLS 变量的普通访问转换为“当前线程 TLS 数组 + 模块 TLS 索引 + 变量块内偏移”的访问逻辑，程序员通常不需要显式调用 TlsAlloc/TlsGetValue/TlsSetValue。

普通局部变量、静态变量、线程局部变量：


int Test()
{
    int a = 0;
    static int b = 0;
    thread_local int c = 0;
}

| 变量 | 有多少份 | 生命周期 | |---|---|---| | a | 每次函数调用一份 | 函数返回后结束 | | b | 整个进程一份 | 程序结束时结束 | | c | 每个线程一份 | 对应线程结束时结束 |

函数内示例：


int NextNumber()
{
    thread_local int number = 0;
    return ++number;
}

线程 A 连续调用可得到 1、2、3；线程 B 第一次调用仍从 1 开始。函数作用域 thread_local 通常在该线程第一次执行到声明处时初始化一次；若初始化抛出异常，后续进入可再次尝试。

类对象也可使用线程存储期，每个线程有独立对象，并分别执行构造和析构：


class ThreadContext
{
public:
    ThreadContext()
    {
        // 当前线程的对象初始化
    }

    ~ThreadContext()
    {
        // 当前线程结束时清理
    }
};

thread_local ThreadContext context;

完整示例：


#include <windows.h>
#include <stdio.h>

__declspec(thread) int g_counter = 10;

DWORD WINAPI Worker(LPVOID)
{
    ++g_counter;

    printf("线程 %lu: g_counter = %d\n",
           GetCurrentThreadId(),
           g_counter);

    ++g_counter;

    printf("线程 %lu: g_counter = %d\n",
           GetCurrentThreadId(),
           g_counter);

    return 0;
}

int main()
{
    HANDLE threads[2];

    threads[0] = CreateThread(
        nullptr, 0, Worker, nullptr, 0, nullptr);

    threads[1] = CreateThread(
        nullptr, 0, Worker, nullptr, 0, nullptr);

    WaitForMultipleObjects(2, threads, TRUE, INFINITE);

    CloseHandle(threads[0]);
    CloseHandle(threads[1]);
    return 0;
}

可能输出：


线程1000: g_counter = 11
线程1000: g_counter = 12
线程1001: g_counter = 11
线程1001: g_counter = 12

thread_local 可用于全局、命名空间、函数内部和类静态成员：


thread_local int g_counter = 0;

namespace App
{
    thread_local int errorCode = 0;
}

void Work()
{
    thread_local int callCount = 0;
    ++callCount;
}

class Worker
{
public:
    static thread_local int taskCount;
};

thread_local int Worker::taskCount = 0;

常见用途包括每线程错误状态、日志缓冲区、随机数生成器、缓存、解析上下文和递归深度：


void Parse()
{
    thread_local int depth = 0;
    ++depth;
    // 当前线程的解析工作
    --depth;
}

注意：

  • thread_local 是一个完整关键字，中间不能有空格（thread _local 是错误写法）
  • __declspec(thread) 不能当成普通自动局部变量的临时属性，MSVC 要求静态存储期语境；函数内部优先使用标准写法 thread_local int x = 0;
  • thread_local 不会创建、启动或切换线程；创建线程仍要使用 CreateThread、std::thread 等
  • thread_local int* pointer = &sharedValue; 只保证指针变量每线程一份；若都指向同一个 sharedValue，目标数据仍共享
  • 线程池中任务结束不等于线程结束；上一任务的 thread_local 状态可能留给下一任务，应显式重置敏感上下文
  • 不同线程取得 &g_counter 通常是不同地址；线程结束后不能继续使用其 TLS 实例地址
  • 线程 B 的初值来自模板或自己的初始化，不会复制线程 A 修改后的值
  • C++ 类对象的构造/析构可能借助运行库和 TLS 回调等机制，不能简单理解为只有一块 .tls 原始字节
  • 早期 Windows 对运行后通过 LoadLibrary 加载、且含静态 TLS 的 DLL 支持曾有限；现代系统已改善。插件需要运行时灵活性时仍常选择动态 TLS

模板字节示例：thread_local int g_counter = 10; 在 PE 模板中可出现小端字节 0A 00 00 00。概念状态：


线程 A：10 → 11 → 12
线程 B：10 → 11 → 12

线程 A：NextNumber() → 1 → 2 → 3
线程 B：NextNumber() → 1
线程 C：尚未调用，尚未产生该调用序列

TLS 回调

TLS 回调是由 Windows 加载器按进程/线程生命周期自动调用的一组函数。它和静态 TLS 数据同属 TLS 体系，但职责不同：静态 TLS / thread_local 解决每线程数据放在哪里，TLS 回调解决什么时候执行初始化或清理代码。

回调数组由 IMAGE_TLS_DIRECTORY32.AddressOfCallBacks 指向：AddressOfCallBacks 是 VA，数组每个元素也是回调函数 VA，数组以空指针 0 结束，多个回调按数组顺序调用。PE32 每个回调表项 4 字节，PE32+ 每项 8 字节。

函数原型：


typedef VOID (NTAPI *PIMAGE_TLS_CALLBACK)(
    PVOID DllHandle,
    DWORD Reason,
    PVOID Reserved
);

| 参数 | 含义 | |---|---| | DllHandle | 当前模块实际加载基址/句柄 | | Reason | 本次回调原因 | | Reserved | 保留参数，通常不用 |

Reason：

| 值 | 宏 | 时机 | |---:|---|---| | 0 | DLL_PROCESS_DETACH | 进程正常退出或模块卸载 | | 1 | DLL_PROCESS_ATTACH | 模块随进程加载 | | 2 | DLL_THREAD_ATTACH | 后续新线程创建 | | 3 | DLL_THREAD_DETACH | 线程正常退出 |

示例函数形式：


void NTAPI TlsCallback(
    PVOID moduleBase,
    DWORD reason,
    PVOID reserved)
{
    switch (reason)
    {
    case DLL_PROCESS_ATTACH:
        // 进程初始化
        break;
    case DLL_THREAD_ATTACH:
        // 新线程初始化
        break;
    case DLL_THREAD_DETACH:
        // 线程清理
        break;
    case DLL_PROCESS_DETACH:
        // 进程清理
        break;
    }
}

模块启动流程可概念化为：


映射 PE 头和节
  ↓
处理重定位
  ↓
修复导入
  ↓
初始化静态 TLS
  ├─ 分配模块 TLS 索引
  ├─ 为初始线程创建 TLS 块
  ├─ 复制模板并补零
  └─ 写入 AddressOfIndex
  ↓
按顺序调用 TLS 回调：PROCESS_ATTACH
  ↓
进入模块正常入口（EXE OEP / DLL 入口流程）

在 OEP 下断点并不能证明此前没有执行模块自己的代码。TLS 回调可在 OEP 之前进行全局初始化、对象构造、代码解密、调试环境检测、异常机制设置或其他准备工作。壳、保护程序和恶意软件有时利用该时机，但正常编译器和运行库也会使用 TLS 回调；存在回调不等于恶意。

后续线程创建：


创建线程
  ↓
为新线程分配 TLS 数组和模块 TLS 块
  ↓
复制模板并补零
  ↓
TLS 回调：THREAD_ATTACH
  ↓
进入线程入口函数

初始线程随进程加载时对应 PROCESS_ATTACH，不是再额外把同一过程简单算作 THREAD_ATTACH。正常线程结束时调用 THREAD_DETACH，再释放线程 TLS 数据；强制 TerminateThread 时不能依赖正常清理路径。TLS 回调返回 VOID，不能像 DllMain 那样通过返回 FALSE 表示拒绝加载。

磁盘解析回调数组：


DataDirectory[9].VirtualAddress
  ↓ RVA→FOA
读取 IMAGE_TLS_DIRECTORY32/64
  ↓
AddressOfCallBacks（VA）- ImageBase
  ↓
得到回调数组 RVA
  ↓ RVA→FOA
按 4/8 字节读取回调 VA
  ↓
遇到 0 停止，同时受目录/映像边界和最大数量限制

定位某回调函数在磁盘中的代码：


回调 RVA = 回调 VA - ImageBase
回调 FOA = RvaToFoa(回调 RVA)

手工加载时，回调必须使用重定位后的实际地址；导入和静态 TLS 基础设施应先准备好，再传入正确 Reason 调用回调，最后进入 OEP。

注意：

  • TLS 回调不是 OEP，也不是普通程序主动注册后随意调用的回调
  • AddressOfCallBacks 与数组元素都是 VA，不是 RVA
  • 数组由 0 终止，但解析器仍需最大边界，不能在损坏文件上无限扫描
  • 初始线程收到模块的 PROCESS_ATTACH 初始化；后续线程才对应 THREAD_ATTACH
  • 回调无返回值，不能返回 FALSE 取消加载
  • TLS 回调可能早于 OEP，但有 TLS 回调不能作为恶意判据
  • 强制终止线程/进程时，不能保证正常的 detach 清理语义
  • 静态 TLS 对象的构造析构可由编译器/运行库机制配合完成，不应假设一个用户回调直接对应一个 thread_local 对象

计算示例：


ImageBase          = 00400000
AddressOfCallBacks = 00406200  // VA

回调数组 RVA = 00406200 - 00400000 = 00006200

[00406200] = 00401230
[00406204] = 00401300
[00406208] = 00000000

调用顺序：00401230 → 00401300 → 遇到 0 结束 → OEP

附录：各数据目录横向对照

| 索引 | 目录 | 入口 VirtualAddress 的特殊含义 | 主要结构/形态 | |---:|---|---|---| | 2 | 资源 | RVA | 目录树 + 数据叶子 | | 3 | 异常 | RVA | 依赖 CPU 架构 | | 4 | 安全/证书 | FOA | WIN_CERTIFICATE 变长记录 | | 6 | 调试 | RVA | 28 字节目录项数组 | | 7 | 架构 | 保留，应为 0 | 无当前通用结构 | | 8 | 全局指针 | GP 的 RVA；Size=0 | 不是数组 | | 9 | TLS | TLS 目录 RVA | PE32 24 字节 / PE32+ 40 字节 | | 10 | 加载配置 | RVA | Size 控制的可变结构 | | 11 | 绑定导入 | RVA | 8 字节主描述符 + 转发引用 | | 13 | 延迟导入 | RVA | 32 字节描述符数组 |

同样都装在 IMAGE_DATA_DIRECTORY 中，不代表 VirtualAddress 与 Size 永远具有完全相同的解释。目录项只是入口，真正的结构、地址基准、结束条件和运行时用途由具体目录规范决定。

统一解析策略：


先检查 NumberOfRvaAndSizes 是否覆盖目标索引
  ↓
根据目录类型选择地址语义（RVA / FOA / 特殊 RVA 值）
  ↓
根据 Machine、PE32/PE32+、结构 Size 或目录 Size 选择布局
  ↓
对所有偏移、计数、步进、加法和乘法做边界检查
  ↓
区分“目录入口”“子表指针”“表中元素”各自的地址语义

三种地址概念：

| 概念 | 公式/含义 | |---|---| | FOA | 字节在磁盘文件中的偏移 | | RVA | 相对模块加载基址的偏移 | | VA | 运行时虚拟地址，通常为 实际加载基址 + RVA |

  • 对磁盘映像，普通 RVA 要先转 FOA；已有 FOA 不再转换；结构内部 VA 通常先减基址得到 RVA
  • 证书表是最明显的例外：数据目录地址字段直接是 FOA
  • 资源目录内部偏移、绑定表名称偏移不是普通 RVA，而是相对各自根的偏移
  • 全局指针项的 RVA 本身就是要形成 GP 的值，不一定是要去文件中解引用的位置
