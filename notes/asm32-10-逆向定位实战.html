Cheat Engine 实战：扫雷破解

数值扫描定位内存

  • 精确数值扫描：已知"剩余雷数"当前显示值，先扫描；改变游戏状态（插一次旗，雷数 -1）后再做"数值已改变"过滤，反复收敛锁定地址。
  • 数值增加扫描："用时"字段持续自增，用"数值增加"类型多次扫描收敛。

结合 OllyDbg 定位修改代码

  • CE 锁定地址后，用"找出是谁在写入这个地址"功能（本质硬件写入断点），或手动切到 OD 对该地址下硬件写入断点。
  • 断下后 OD 停在正在修改该数值的汇编指令上，直接看到运算方式（dec/sub/inc/add）。

补丁思路

| 目标 | 修改 | |------|------| | 雷数"加血" | sub → add，或 NOP 掉递减逻辑 | | 时间静止 | NOP 掉自增指令（inc/add） |

修改完成后：OD "复制到可执行文件（Copy to executable）→ 保存文件"生成持久化补丁 exe，而非仅内存临时生效。

逆向思维：API 断点与栈回溯

API 断点

原理：在系统 DLL 导出函数入口下断点，程序调用 API 时断下。

三种下断方式

| 方式 | 命令/操作 | 特点 | |------|----------|------| | 符号断点 | bp MessageBoxA / bp user32.MessageBoxA | 调试器解析导出表找地址，最常用，所有调用都断 | | IAT 调用处断点 | Find Intermodular Calls → 选中 → F2 | 断在程序自己的 CALL 指令处，只断指定调用点 | | 地址断点 | 直接对 API 实现地址 F2 | 受 ASLR 影响，地址每次可能变 |

符号断点断在 API 实现入口（DLL 里），IAT 断点断在用户调用指令处。需要看参数时，IAT 断点停在调用现场，参数刚压完栈，更直观。

断下后如何读参数（关键）

x86 stdcall（Win32 API 统一约定）：断在 API 入口第一行（尚未 push ebp），用 ESP：


[ESP]     = 返回地址（调用者 CALL 的下一条）
[ESP+4]   = 参数 1
[ESP+8]   = 参数 2
[ESP+12]  = 参数 3
...

注意：是 ESP 不是 EBP！API 入口还没建栈帧，EBP 还是调用者的值。新手常犯的错：在 API 入口用 [EBP+8] 取参数，取到的是调用者数据。

x64 Microsoft 约定：

| 参数 | 位置 | |------|------| | 第 1 参 | RCX | | 第 2 参 | RDX | | 第 3 参 | R8 | | 第 4 参 | R9 | | 第 5 参起 | [RSP+0x28]（返回地址 8 + 影子空间 32） |

常用 API 断点切入点

| 逆向目的 | 关键 API | |---------|---------| | 弹窗/提示 | MessageBoxA/W、MessageBoxExA | | 文件读写 | CreateFileA/W、ReadFile、WriteFile | | 注册表 | RegOpenKeyExA/W、RegQueryValueA/W | | 网络 | WSAStartup、connect、send、recv、InternetOpenA | | 进程/注入 | CreateProcessA/W、OpenProcess、CreateRemoteThread、WriteProcessMemory | | 内存分配 | VirtualAlloc、VirtualAllocEx（壳常用） | | 窗口查找 | FindWindowA/W（反调试常用） | | 绘图 | BitBlt、TextOutA/W、DrawTextA/W | | 字符串比较 | lstrcmpA/W、strcmp（注册码校验常用） |

A/W 后缀：A = ANSI 多字节，W = Wide Unicode。不确定时两个都下。

条件 API 断点（减少噪音）

API 调用频繁，每次都断太吵。结合条件断点，只在特定参数时断：


bp CreateFileW
条件: [ESP+4] 指向的字符串包含 "flag"

只有当程序打开文件名含 "flag" 时才断下。

反 API 断点对抗

| 对抗手段 | 原理 | 应对 | |---------|------|------| | 动态解析 API | LoadLibrary+GetProcAddress 自取地址，不走 IAT | IAT 断点失效，改用符号断点 bp | | 调用 ntdll 内部函数 | 绕过 kernel32/user32 包装层 | 在 ntdll 更底层函数下断 | | 检测 0xCC | 扫描 API 入口字节是否被改 | 改用硬件断点下 API | | API Hook 检测 | 校验 API 前 N 字节完整性 | 硬件断点 + ScyllaHide |

栈回溯（Call Stack）

原理：基于 x86 函数调用机制和 EBP 链。CALL 指令等价于 push 返回地址; jmp target。标准函数序言：


push ebp          ; 保存调用者栈帧基址
mov  ebp, esp     ; 建立当前栈帧
sub  esp, N       ; 局部变量空间

每个函数栈帧里 [EBP] 存的是调用者的 EBP，串成一条链，[EBP+4] 存的是返回地址。

栈帧结构（必须记牢）


高地址
┌─────────────────┐
│ 参数 N          │  [EBP + 4 + 4*N]
├─────────────────┤
│ 参数 1          │  [EBP + 8]      ← stdcall/cdecl 参数起始
├─────────────────┤
│ 返回地址        │  [EBP + 4]      ← CALL 压入，调用者代码位置
├─────────────────┤
│ 保存的 EBP      │  [EBP]          ← 指向上一层栈帧
├─────────────────┤  ← 当前 EBP 锚定此处
│ 局部变量 1      │  [EBP - 4]
├─────────────────┤
│ ...             │
├─────────────────┤  ← ESP 指向栈顶
低地址

栈回溯算法


void* ebp = 当前EBP;
while (ebp != 0 && 合法地址) {
    void* ret_addr = *(void**)(ebp + 4);   // 返回地址 = 调用者代码位置
    ebp = *(void)ebp;                     // 爬到上一层 EBP
}

调试器 Call Stack 窗口就是这么算的。

栈回溯失效场景

| 场景 | 原因 | 后果 | |------|------|------| | FPO 优化 | 编译器省掉 push ebp/mov ebp,esp，直接用 ESP 寻址 | EBP 链断裂，回溯只到当前层 | | 叶子函数 | 不调用其他函数的简单函数，可能无标准栈帧 | 同上 | | 手写汇编 | 非标准序言 | 链路不规则 | | 栈被破坏 | 缓冲区溢出覆盖返回地址/EBP | 回溯出乱码或崩溃 | | Release 优化 | VS /O2 默认开 FPO | 经常回溯不全 |

FPO 是栈回溯最大敌人。x64 有 PE 的 .pdata 段 unwind 信息，即使没 EBP 链也能精确回溯——这是 x64 架构优势。

两种断点参数读取对比

| 时机 | 用什么取参 | 原因 | |------|----------|------| | API 入口（断在函数第一行） | ESP | 还没建栈帧，EBP 是调用者的 | | API 内部（已 push ebp/mov ebp,esp） | EBP | 栈帧已建，参数在 [EBP+8] | | IAT 调用处（断在 CALL 指令） | ESP | 参数刚压完栈，[ESP]=参数1（还没 CALL） |

注意：断在 CALL 之前（还没执行 CALL），[ESP]=参数1，没有返回地址；断在 CALL 之后（进入 API），[ESP]=返回地址，[ESP+4]=参数1。差一层，别搞混。

API 断点 + 栈回溯协同流程

这是逆向最通用的切入套路：


① 下 API 断点（切入）—— 程序行为暴露关键逻辑
② 断下后读参数（确认行为）—— ESP 取参
③ 栈回溯（定位调用者）—— Call Stack 找用户代码
④ 跳到调用者代码（分析关键逻辑）
⑤ 条件断点/内存断点（深入追踪）

示例（想知道程序在哪读琴谱文件）：

1. bp CreateFileA 2. F9 运行，触发读文件操作 3. 断在 CreateFileA，看 [ESP+4] 指向的字符串 = 文件路径 4. 打开 Call Stack，双击上一层（调用者） 5. 跳到程序自己的代码——就是处理读文件的逻辑位置

推导扫雷内部数据结构

切入思路：游戏最终必须调用 Windows 图形 API 把格子画到屏幕，从"结果"（绘图 API）反推"数据源"。典型切入点：BitBlt / StretchBlt。

经典扫雷位标志编码体系（以 XP winmine.exe 为例，不同版本有差异，以动态调试观察为准）：

| 位 | 含义 | |----|------| | bit7 (0x80) | 是否为雷 | | bit6 (0x40) | 是否已翻开 | | 低 3 位 (0x07) | 周围雷数 |

| 字节值 | 含义 | 二进制 | |--------|------|--------| | 0x0F | 未翻开（非雷） | 0000 1111 | | 0x8F | 未翻开（雷） | 1000 1111 | | 0x40 | 已翻开（0 雷/空） | 0100 0000 | | 0x41~0x48 | 已翻开（1~8 雷） | 0100 0001 ~ 0100 1000 | | 0x4E / 0xCC | 踩雷/边界（版本差异） | — |

数组按行×列线性存放在连续内存中，格子间偏移固定。找到数组基址与每格字节大小后，遍历即可还原整张图。

作弊程序设计思路

| 思路 | 实现 | 隐蔽性 | |------|------|--------| | 透视（只读） | ReadProcessMemory 读取数组、解析每字节含义，悬浮窗口标雷 | 高，不修改游戏数据 | | 自动标记/提示 | 读取数据后外部计算屏幕坐标，模拟鼠标辅助玩家 | 较高，接近"辅助" | | 内存篡改 | 直接修改内存让雷显示 | 低，检测风险高 |

其他定位技巧与 x64dbg

字符串参考定位法

程序关键逻辑分支旁常有提示文本（"注册成功""序列号错误"）。OD "查找所有字符串参考"列出模块中被引用的所有 ASCII/Unicode 字符串，搜索关键词双击跳转到引用处。对未做字符串加密的程序，效率远高于盲目扫描代码段。

查找模块间调用（Find Intermodular Calls）

Ctrl+N 打开名称窗口，或右键 "Search for → Intermodular calls"，列出当前模块所有跨模块 CALL（调用 API 的地方）。想找程序在哪调用 CreateFile，这比全代码段搜索快得多。

跟踪功能（Trace）

Trace 自动逐条执行并记录经过的每条指令与寄存器状态，无需人工 F7/F8。

  • 用途：应对花指令/垃圾指令混淆，用动态执行结果代替静态反汇编，绕开混淆陷阱。
  • 条件 Trace**：设"当 EIP 落在某地址范围才记录"或"寄存器满足条件才记录"，过滤系统 DLL 和无关代码。对付 VMP/Themida 重混淆，条件 Trace 是还原执行路径的主力。

执行控制补充

| 操作 | 快捷键 | 作用 | |------|--------|------| | 运行到选中行 | F4 | 临时跑到此处，实战高频 | | 设置新 EIP | Ctrl+\* | 跳过/重放代码 | | 执行到返回 | Ctrl+F9 | 在栈帧返回地址下临时断点 | | 自动步入/步过 | Animate | 自动连续单步，可视化执行流 |

调用约定识别（看懂函数参数的基础）

逆向看一段汇编，第一件事是判断"参数怎么传、谁清栈"：

| 调用约定 | 参数传递 | 清栈方 | 汇编特征（x86） | |---------|---------|--------|----------------| | cdecl | 从右到左压栈 | 调用者 | call 后紧跟 add esp, N | | stdcall | 从右到左压栈 | 被调者 | 函数内 ret N，调用后无 add esp | | fastcall | 前两参走 ECX/EDX，其余压栈 | 被调者 | 直接用 ECX/EDX，不 mov 取栈参数 | | thiscall | this 走 ECX，其余压栈 | 被调者 | 成员函数常见 |

Win32 API 统一是 stdcall（WINAPI 宏），API 调用后不会有 add esp。C 运行时函数多为 cdecl，调用后有 add esp, N。看这一条就能区分调用的是 API 还是 CRT 函数。

结构体解析

在 Dump 窗口应用结构体定义（如 WNDCLASSEX、_TEB），按字段名查看而非裸字节。x64dbg 内置结构体查看器，OD 依赖插件。

x64dbg 与 OllyDbg 对比

| 维度 | OllyDbg | x64dbg | |------|---------|--------| | 位数支持 | 仅 32 位 | 32/64 位（x32dbg/x64dbg） | | 界面 | 较老旧，插件生态老化 | 现代化，布局灵活 | | 流程图 | 无原生支持（需插件） | 原生 Graph 视图 | | 结构体解析 | 弱，依赖插件 | 内置结构体查看器 | | 异常处理配置 | 选项简单 | 可按异常码分别配置策略 | | FPO 回溯 | 弱 | 强（利用 .pdata unwind 信息） | | 维护状态 | 已停止更新多年 | 开源、社区活跃、持续更新 |

x64 调用约定差异（迁移 x64dbg 必懂）

| 维度 | x86（stdcall） | x64（Microsoft） | |------|---------------|----------------| | 前 4 个参数 | 全压栈 | RCX/RDX/R8/R9 寄存器传 | | 其余参数 | 压栈 | 压栈 | | 栈空间 | 实参大小 | 预留 32 字节影子空间 | | 清栈方 | 被调者 | 调用者 | | 寻址方式 | 任意 | RIP 相对寻址（影响地址计算） |

不懂这个，到 x64dbg 里看 API 调用会找不到参数——它们不在栈上，在 RCX/RDX/R8/R9 里。

调试器底层：Debug Loop

理解调试器本质要懂调试循环：


DebugActiveProcess / CreateProcess(DEBUG_ONLY_THIS_PROCESS)
    ↓ 循环
WaitForDebugEvent(&de, INFINITE)   ; 等调试事件
    处理异常/断点
ContinueDebugEvent(...)             ; 继续被调试进程

所有断点、单步、异常，本质都是这个循环里收到 EXCEPTION_DEBUG_EVENT。理解这个，才明白"附加"和"直接启动"行为不同（创建标志不同），以及 ThreadHideFromDebugger 怎么让调试器收不到事件。

Cheat Engine 高级技巧：基址查找

动态地址与基址问题

| 内存类型 | 地址稳定性 | 原因 | |---------|-----------|------| | 全局/静态变量（.data/.bss） | 固定（相对模块基址） | 编译期确定，即使 ASLR，"模块基址+固定偏移"关系不变 | | 堆（heap） | 每次变化 | 取决于分配器当时状态 | | 栈（stack） | 每次变化 | 取决于函数调用深度 |

直接记录"这次运行"的绝对地址，重启后大概率失效。需要一条"从固定基址出发，经若干级解引用/偏移，始终能算出正确地址"的路径，即基址 + 多级偏移。

指针链的静态起点必须在模块的 .data/.bss 段，不能在堆栈上。指针扫描的本质就是反向搜索一条从静态地址通向动态地址的解引用链。

CE 指针扫描（Pointer Scan）

1. 用常规数值扫描定位到"这次运行"中数据的动态地址 2. 对该地址执行 Pointer Scan，CE 在整个进程内存空间反向搜索：哪些位于固定段的静态地址，其存放的值经 0~N 级偏移解引用后，恰好能算出目标地址 3. 得到若干候选指针链（基址 + 偏移1 + 偏移2 + …）

验证

重启目标程序，用同一条指针链重新计算地址，与重新扫描得到的实际地址核对是否一致；吻合则该指针链稳定有效，之后直接用"基址+偏移"公式定位，无需每次重新扫描。

PE 基础与脱壳

PE 结构基础

| 结构 | 作用 | |------|------| | DOS 头 | MZ 标志，指向 PE 头 | | PE 头 | 包含 EP（入口点）、节表、可选头 | | 节表 | 描述各节（.text/.data/.rdata/.rsrc 等）属性 | | 导入表（IAT） | 程序调用的外部 API 地址表 | | 导出表 | DLL 对外暴露的函数 | | 重定位表 | ASLR 下修正绝对地址 | | TLS 目录 | TLS 回调函数表（见下） |

EP 与 OEP

| 概念 | 含义 | |------|------| | EP（Entry Point） | PE 头记录的入口点，调试器直接打开断在这里 | | OEP（Original EP） | 加壳程序的真实入口点，脱壳就是找它 |

TLS 回调（重要反调试点）

TLS 回调是在 EP 之前执行的代码段。调试器默认断在 EP，但 TLS 回调已经跑完了——这是经典反调试藏匿点。

注意：很多壳/保护把反调试放在 TLS 回调里，你断在 EP 时它早就检测完了。新手调试加壳程序"一附加就被发现"，十有八九是 TLS 回调作祟。调试时必须勾选"在 TLS 回调处断下"。

脱壳基本流程


① 找 OEP（运行到真实入口，常用内存断点/硬件断点定位）
② Dump（把内存中解密后的代码转存成新 PE）
③ 修复 IAT（壳运行时才重建导入表，dump 出来的 IAT 是乱的，用 Scylla 修复）
④ 修复重定位（如有需要）

工具生态

| 工具 | 用途 | |------|------| | ScyllaHide | 反反调试，hook 各类检测点 | | Scylla | IAT 修复 + Dump | | IDA Pro | 静态反汇编/反编译，配合动态调试 | | CFF Explorer | PE 查看/编辑/修复 | | LordPE | PE 编辑、Dump | | Detect It Easy (DIE) | 查壳/查编译器 |

动态（OD/x64dbg）+ 静态（IDA）+ PE 工具（CFF Explorer）是逆向三板斧。
