Shellcode：PEB 链与导出表解析

32 位汇编

Shellcode：PEB 链与导出表解析

shellcode 没有 IAT、没有 .data 段，要在任意内存地址运行，靠一条完整链路定位 API 地址：PEB → Ldr → 模块链表 → 导出表。

TEB 与 PEB 结构

TEB（Thread Environment Block，线程环境块） 是每个线程独有的结构体，记录线程的运行时状态信息，好比每个线程的"个人信息本"。PEB（Process Environment Block，进程环境块） 是每个进程独有的结构体，记录进程全局信息，好比进程的"户口本"。

二者是 Windows 在用户态暴露给进程/线程的核心管理结构，shellcode 通过遍历 PEB 内部的模块链表实现动态定位 API 地址。关系链：TEB → PEB → Ldr → 模块链表。

TEB 内存布局

x86 下 TEB 的 +0x30 偏移处存放着指向 PEB 的指针，这是从线程环境块进入进程环境块的关键桥梁：


TEB 内存布局（x86）：
+0x00: 异常处理链（SEH 链表头）
+0x04: 栈顶
+0x08: 栈底
...
+0x18: TEB 自身地址
...
+0x30: PEB 指针    ← 关键：通过它跳转到 PEB
  • 每个线程有自己独立的 TEB
  • x86 下通过 FS 段寄存器访问：FS:[偏移]
  • x64 下改用 GS 段寄存器（PEB 偏移变为 +0x60）

PEB 内存布局

PEB 的 +0x0C 偏移处存放着 PEB_LDR_DATA* 指针，它指向模块链表，是后续遍历所有已加载 DLL 的入口：


typedef struct _PEB {
    BYTE  InheritedAddressSpace;    // +0x00
    BYTE  ReadImageFileExecOptions; // +0x01
    BYTE  BeingDebugged;            // +0x02  ← 反调试常用
    BYTE  Spare;                    // +0x03
    VOID* Mutant;                   // +0x04
    VOID* ImageBaseAddress;         // +0x08  ← exe 基地址
    PEB_LDR_DATA* Ldr;              // +0x0C  ← 模块链表入口
    // ...
} PEB;

完整访问链路


FS 段寄存器（指向当前线程 TEB）
  → TEB +0x30 → PEB 地址
    → PEB +0x0C → Ldr（PEB_LDR_DATA）
      → 模块链表 → kernel32 基地址

关键要点：

  • fs:[30h] 取出的是 PEB 的地址，不是 PEB 结构体本身
  • 内核在创建线程时把 TEB 地址加载到 FS，线程切换时 FS 自动切换，所以 fs:[30h] 永远是当前线程的 PEB
  • 一个进程只有一个 PEB，但可以有多个 TEB（多线程）
  • PEB 地址每次进程启动都不同（ASLR），必须通过 fs:[30h] 动态获取，无法硬编码

获取 PEB 地址


mov eax, fs:[30h]   ; x86：eax = PEB 地址
mov rax, gs:[60h]   ; x64：rax = PEB 地址（偏移不同）

对应的 C 内联函数分别是 __readfsdword(0x30) 和 __readgsqword(0x60)。

assume fs:nothing（MASM 专用）：


assume fs:nothing

这是给 MASM 编译器看的声明，不生成任何机器码。作用：告诉汇编器"FS 没有关联我程序里定义的任何段，别报警告，直接生成指令"。不写的话，MASM 看到 mov eax, fs:[30h] 会警告 fs 没有关联任何段。

PEB_LDR_DATA 与模块链表

PEB_LDR_DATA 是 PEB 中用来管理已加载模块（EXE 和 DLL）的核心数据结构，PEB 偏移 +0x0C 处的 Ldr 指针指向该结构体：


typedef struct _PEB_LDR_DATA {
    ULONG     Length;                              // +0x00
    BOOLEAN   Initialized;                         // +0x04
    PVOID     SsHandle;                            // +0x08
    LIST_ENTRY InLoadOrderModuleList;              // +0x0C
    LIST_ENTRY InMemoryOrderModuleList;            // +0x14
    LIST_ENTRY InInitializationOrderModuleList;    // +0x1C  ← shellcode 常用
} PEB_LDR_DATA;

结构中包含三条双向链表，每条链表串联所有已加载模块的 LDR_DATA_TABLE_ENTRY，区别在于排序依据不同：

|链表|偏移|排列依据|特点| |---|---|---|---| |InLoadOrderModuleList|+0x0C|加载顺序|谁先加载谁在前| |InMemoryOrderModuleList|+0x14|内存地址顺序|按基址从小到大| |InInitializationOrderModuleList|+0x1C|初始化顺序|DllMain 调用顺序|

为什么用 InInitializationOrderModuleList

Windows 内核加载 DLL 时会依次调用每个 DLL 的入口点（DllMain），InInitializationOrderModuleList 严格按照这个初始化顺序排列，顺序在所有 Windows 版本中稳定，因此第一条有效的用户态 DLL 通常是 kernel32.dll（紧随 ntdll.dll 之后）。shellcode 利用这个稳定性来定位 kernel32 基址。

注意：该链表不含 exe 自身节点，ntdll.dll 是第 1 个节点、kernel32.dll 通常是第 2 个节点，位于链表头部附近，遍历次数少。

嵌入式链表

链表由 LIST_ENTRY 双向循环链表节点构成：


typedef struct _LIST_ENTRY {
    LIST_ENTRY* Flink;   // 指向下一个节点
    LIST_ENTRY* Blink;   // 指向上一个节点
} LIST_ENTRY;            // 共 8 字节（32位）

关键设计是嵌入式链表：LIST_ENTRY 不独立存在，而是嵌入到 LDR_DATA_TABLE_ENTRY 结构体的某个字段中。链表头的 Flink 指向第一个模块节点的 InInitializationOrderLinks，而不是指向结构体开头。

遍历顺序：链表头 → ntdll → kernel32 → … → 回到链表头（循环）。当遍历到的节点地址等于链表头地址（即 PEB_LDR_DATA.InInitializationOrderModuleList 的地址）时，说明已经遍历完一圈。

取链表头地址


mov eax, fs:[30h]       ; eax = PEB 地址
mov eax, [eax + 0Ch]    ; eax = PEB.Ldr → PEB_LDR_DATA 地址
mov eax, [eax + 1Ch]    ; eax = InInitializationOrderModuleList.Flink
                        ;     = 第一个模块的 InInitializationOrderLinks 地址

[eax + 1Ch] 读取的是 InInitializationOrderModuleList 的第一个字段（Flink），即链表第一个节点的地址。

LDR_DATA_TABLE_ENTRY 详解

LDR_DATA_TABLE_ENTRY 是 Windows 内核为进程内每个已加载 DLL 分配的数据结构，可以视为 DLL 的户口本。它完整记录了一个模块的全部元信息，包括基地址（DllBase）、入口点、镜像大小、完整路径和文件名，并通过三个 LIST_ENTRY 链节挂入 PEB_LDR_DATA 中的不同链表。


typedef struct _LDR_DATA_TABLE_ENTRY {
    LIST_ENTRY InLoadOrderLinks;              // +0x00  加载顺序链表挂钩
    LIST_ENTRY InMemoryOrderLinks;            // +0x08  内存顺序链表挂钩
    LIST_ENTRY InInitializationOrderLinks;    // +0x10  初始化顺序链表挂钩
    VOID*      DllBase;                       // +0x18  DLL 基地址
    VOID*      EntryPoint;                    // +0x1C  DllMain 地址
    ULONG      SizeOfImage;                   // +0x20  内存中的大小
    UNICODE_STRING FullDllName;               // +0x24  完整路径
    UNICODE_STRING BaseDllName;               // +0x2C  文件名（如 KERNEL32.DLL）
} LDR_DATA_TABLE_ENTRY;

偏移计算（以 InInitializationOrderLinks 为基准）

遍历时寄存器指向 InInitializationOrderLinks（结构体偏移 +0x10），所有字段需要以该字段的地址为基准计算偏移：

|字段|结构体绝对偏移|相对 eax（InInitializationOrderLinks）偏移| |---|---|---| |InInitializationOrderLinks|+0x10|+0x00（eax 指向此处）| |DllBase|+0x18|+0x08| |EntryPoint|+0x1C|+0x0C| |SizeOfImage|+0x20|+0x10| |FullDllName.Length|+0x24|+0x14| |FullDllName.Buffer|+0x28|+0x18| |BaseDllName.Length|+0x2C|+0x1C| |BaseDllName.Buffer|+0x30|+0x20|

内存直观布局：


LDR_DATA_TABLE_ENTRY 内存布局（32位）：
地址        内容
0x????00   [InLoadOrderLinks.Flink]        +0x00
0x????04   [InLoadOrderLinks.Blink]        +0x04
0x????08   [InMemoryOrderLinks.Flink]      +0x08
0x????0C   [InMemoryOrderLinks.Blink]      +0x0C
0x????10   [InInitializationOrderLinks.Flink]  ← eax 指向这里
0x????14   [InInitializationOrderLinks.Blink]
0x????18   [DllBase]                       ← eax + 0x08
0x????1C   [EntryPoint]
0x????20   [SizeOfImage]
0x????24   [FullDllName.Length / MaximumLength]
0x????28   [FullDllName.Buffer]
0x????2C   [BaseDllName.Length / MaximumLength]
0x????30   [BaseDllName.Buffer]

DllBase 与 UNICODE_STRING

DllBase 是 DLL 被加载到进程地址空间后的起始虚拟地址，相当于该模块在内存中的"门牌号"。有了 DllBase，才能进一步按照 PE 格式解析导出表，定位目标函数地址。


typedef struct _UNICODE_STRING {
    USHORT Length;        // 字符串的字节长度（不含结尾空字符）
    USHORT MaximumLength; // 缓冲区最大字节长度
    PWSTR  Buffer;        // 指向实际宽字符的指针
} UNICODE_STRING;
  • BaseDllName 为此类型，存储 Unicode 宽字符串（每个字符 2 字节）
  • 示例：KERNEL32.DLL 的 Length = 12 字符 × 2 字节 = 24 = 0x18

汇编访问示例


; eax = InInitializationOrderLinks 地址
mov esi, [eax + 08h]              ; esi = DllBase
mov ebx, [eax + 20h]              ; ebx = BaseDllName.Buffer 指针
movzx ecx, word ptr [eax + 1Ch]   ; ecx = BaseDllName.Length（字节数）

遍历链表找 kernel32 基地址

kernel32.dll 的加载地址随系统版本甚至每次启动而变化（ASLR）。通过遍历 PEB 中的模块链表动态定位 kernel32 基地址，是 shellcode 实现跨 Windows 版本兼容的核心技术。

|系统|kernel32 基地址| |---|---| |Windows XP SP3|0x7C800000| |Windows 7|0x75630000| |Windows 10|0x74B70000|

不能依赖硬编码地址的原因：ASLR 使每次加载基址不同；不同 Windows 版本内核布局差异巨大；安全更新和补丁也会改变加载地址。

查找链路：通过 PEB → Ldr → InInitializationOrderModuleList 链表，从 ntdll.dll 开始遍历，找到 kernel32.dll 后取出其 DllBase 字段即为基地址。


fs:[30h] → PEB → +0x0C → PEB_LDR_DATA → +0x1C → InInitializationOrderModuleList.Flink
  → ntdll → Flink → kernel32 → +0x08 → DllBase

完整汇编代码


assume fs:nothing

; ===== 第一步：取 PEB 地址 =====
mov eax, fs:[30h]       ; eax = PEB 地址（从 TEB+0x30 取）

; ===== 第二步：取 Ldr 指针 =====
mov eax, [eax + 0Ch]    ; eax = PEB.Ldr → PEB_LDR_DATA 地址

; ===== 第三步：取链表头 =====
mov eax, [eax + 1Ch]    ; eax = InInitializationOrderModuleList.Flink
                        ;     = 第一个模块(ntdll)的 InInitializationOrderLinks 地址

; ===== 第四步：遍历找 kernel32 =====
find_k32:
    mov esi, [eax + 08h]              ; esi = 当前模块 DllBase
    mov ebx, [eax + 20h]              ; ebx = BaseDllName.Buffer（名字指针）
    movzx ecx, word ptr [eax + 1Ch]   ; ecx = BaseDllName.Length（字节长度）
    cmp ecx, 18h                      ; "KERNEL32.DLL" = 12字符×2 = 0x18
    jne next_mod
    cmp word ptr [ebx], 004Bh         ; 首字符是 'K'？（Unicode，004B = 'K'）
    je found_k32
next_mod:
    mov eax, [eax]      ; eax = Flink → 下一个模块的 InInitializationOrderLinks
    jmp find_k32

found_k32:
    ; esi = kernel32.dll 基地址

比对技巧

eax 指向 InInitializationOrderLinks（结构体偏移 +0x10），字段访问偏移 = 结构体绝对偏移 − 0x10，例如 DllBase：0x18 − 0x10 = 0x08，即 [eax + 08h]。

KERNEL32.DLL 长度为何是 0x18： Windows 内核用 Unicode（UTF-16 LE）存储字符串，每个字符占 2 字节，"KERNEL32.DLL" = 12 个字符 × 2 字节 = 24 字节 = 0x18。先比较长度，长度不对直接跳过，避免不必要的字符串比较，提高遍历效率。

mov eax, [eax] 的含义： LIST_ENTRY 结构的第一个字段就是 Flink，所以 [eax] 读出来的就是链表中下一个模块的 InInitializationOrderLinks 地址，等价于 C 的 eax = eax->Flink。

PE 导出表与按名字查找

找到 kernel32 基地址后，下一步在它的导出表里按名字查找 GetProcAddress。PE 导出表是 PE 文件数据目录的第一项（DataDirectory[0]），记录 DLL 向外暴露的导出函数信息——GetProcAddress 和链接器隐式导入，实际就是在查找导出表。

导出表的核心由三个并行数组组成：

  • AddressOfFunctions（导出地址表 EAT）：函数入口 RVA 数组
  • AddressOfNames：函数名字符串指针（RVA）数组
  • AddressOfNameOrdinals：名字到地址表的序号映射数组

其中 AddressOfNames[i] 和 AddressOfNameOrdinals[i] 使用相同的下标 i，描述同一个函数；AddressOfFunctions[ordinal] 才是该函数的入口 RVA。

三数组协作关系


AddressOfNames          AddressOfNameOrdinals      AddressOfFunctions
  Name[0] (GetProcAddress)  Ordinal[0] = 2           Func[0] (LoadLibraryA)
  Name[1] (LoadLibraryA)    Ordinal[1] = 0           Func[1] (VirtualAlloc)
  Name[2] (VirtualAlloc)    Ordinal[2] = 1           Func[2] (GetProcAddress)
       ↓ i=0                     ↓ ordinal=2              ↓
  匹配到下标 0  →  Ordinal[0]=2  →  Func[2] = GetProcAddress 地址

按名字查找的流程


1. 遍历 AddressOfNames，逐个比较函数名字符串
2. 匹配成功后记下下标 i
3. ordinal = AddressOfNameOrdinals[i]
4. funcRVA = AddressOfFunctions[ordinal]
5. funcVA = funcRVA + ImageBase

shellcode 场景中操作的是已加载到内存的 DLL，不是磁盘文件。Windows 加载器已完成文件偏移到虚拟地址的映射，因此内存中直接 RVA + ImageBase = VA，无需转文件偏移（磁盘文件才需要根据节表做 RVA-to-Offset 转换）。

0x78 偏移的由来

从 PE 签名（e_lfanew 指向的位置）开始计算到 DataDirectory[0]：


PE 签名        4 字节
File Header   20 字节
Optional Header 前 0x60 字节
─────────────────────────
总计：4 + 20 + 96 = 120 = 0x78

若从可选头起始算则是 0x60，两者指向同一个位置，不要混淆。

小端序字符串比对

内存中 "GetProcAddress" 的字节序列：


47 65 74 50 72 6F 63 41 ...
G  e  t  P  r  o  c  A ...

按 DWORD（4 字节）读取时，小端序（低字节在低地址）决定了比较常数的写法：

|偏移|内存字节|DWORD 值|汇编中写法| |---|---|---|---| |[0]|47 65 74 50|0x50746547|"GetP" → 50746547h| |[4]|72 6F 63 41|0x41636F72|"rocA" → 41636f72h|

定位导出表


; esi = kernel32 基地址
mov eax, [esi + 3Ch]    ; e_lfanew（PE头偏移，从 DOS Header 读）
add eax, esi            ; PE头实际地址（VA）
mov eax, [eax + 78h]    ; 导出表 RVA（DataDirectory[0]，从PE签名算偏移0x78）
add eax, esi            ; 导出表实际地址（VA）

获取三个关键数组


mov ebx, [eax + 1Ch]
add ebx, esi            ; AddressOfFunctions（EAT）：函数地址数组
mov ecx, [eax + 20h]
add ecx, esi            ; AddressOfNames：函数名字符串指针数组
mov edx, [eax + 24h]
add edx, esi            ; AddressOfNameOrdinals：名字对应序号数组

完整实现：查找 GetProcAddress


xor edi, edi                        ; 计数器 = 0
find_gp:
    mov eax, [ecx + edi*4]          ; 第 edi 个名字的 RVA（DWORD，x4）
    add eax, esi                    ; 名字字符串实际地址
    cmp dword ptr [eax], 50746547h  ; 比对 "GetP"（小端序）
    jne nxt
    cmp dword ptr [eax + 4], 41636f72h ; 比对 "rocA"
    jne nxt
    ; 找到了
    movzx eax, word ptr [edx + edi*2]  ; 取序号（WORD，x2）
    mov eax, [ebx + eax*4]             ; 用序号找函数地址 RVA
    add eax, esi                        ; GetProcAddress 实际地址
    jmp got_gp
nxt:
    inc edi
    jmp find_gp
