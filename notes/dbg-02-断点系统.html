断点系统

断点方式对比

| 方式 | 原理 | 优点 | 缺点 | |------|------|------|------| | 0xCC (INT3) | 替换指令首字节为 CC，触发 EXCEPTION_BREAKPOINT | 简单、精确到字节 | 遍历 CC 可被检测 | | 其他异常指令 | CLI/INT3/INTO 等能产生异常的指令 | 绕过 CC 遍历检测 | 需要特权指令知识 | | 内存断点 | VirtualProtectEx 改页属性，触发 EXCEPTION_ACCESS_VIOLATION | 不改代码、防 CC 遍历 | 按页生效、性能开销 | | 硬件断点 | DR0-DR3 寄存器 + DR7 控制 | 精确、不影响性能 | 最多 4 个 | | 校验和检测 | 定期校验代码完整性 | 能检测所有代码修改 | 不能定位断点位置 |

反断点检测升级路线：遍历 0xCC → 校验和检测 → 内存断点 → 硬件断点 → 时间检测

软件断点 BP

基本原理

软件断点把目标地址的第一个字节改成 int 3（机器码 CCh）。命中后必须完成：


恢复原来的1字节
EIP 回退1字节
执行原指令
永久断点重新写回 CCh

恢复长度必须是 1 字节

bOriginal 可以使用 DWORD 保存，结构体对齐不受影响；但实际恢复机器码时必须只写 1 字节：


invoke DbgWriteProcessMemory, [esi].dwAddress, eax, 1

如果恢复 4 字节，会覆盖断点地址后面的三字节，破坏原指令流。

永久断点的重新插入

命中永久断点时不能立刻重新写 CCh，否则 EIP 回退后会再次执行 int3，形成无限断点循环。正确流程：


命中 BP
→ 恢复原字节
→ EIP--
→ 记录待恢复断点 g_stepBreakPoint
→ 设置 TF
→ 执行一条原指令
→ EXCEPTION_SINGLE_STEP
→ 重新写入 CCh

一次性断点不需要重新写入。这也是 P 在 call 下一条指令处使用临时断点的基础。

已验证结果

在 00401000、0040100E 同时设置 BP 后，两处均能命中；永久断点执行原指令后能够重新插入。

内存断点原理

核心流程


下断点: VirtualProtectEx 改页属性为 PAGE_NOACCESS
    ↓
程序访问该页 → 触发 EXCEPTION_ACCESS_VIOLATION (0xC0000005)
    ↓
调试器收到异常 → 恢复原页属性 → 设单步(Trap Flag)
    ↓
程序执行触发异常的那条指令 → 单步异常
    ↓
调试器收到单步 → 重新设回 PAGE_NOACCESS → 程序继续

注意：不先恢复内存属性就继续执行，会在同一条访问指令上递归产生访问异常。

EXCEPTION_RECORD 关键字段

| 字段 | 含义 | |------|------| | ExceptionInformation[0] | 操作类型：0=读，1=写，8=执行（DEP） | | ExceptionInformation[1] | 被访问的内存地址（不是指令地址） | | ExceptionAddress | 触发异常的指令地址（EIP） |

注意：ExceptionAddress 是指令地址，ExceptionInformation[1] 是指令想访问的内存地址，两者不同。

页对齐

VirtualProtectEx 按 4KB（1000h）页生效，断点地址 & 0xFFFFF000 取页起始地址（如 00402008 → 页首 00402000）。判断命中时先比较访问地址与断点地址是否属于同一页，再判断访问地址是否落在实际监控范围内。

BREAKPOINT 结构体设计


BREAKPOINT STRUCT
    dwNum      DWORD ?   ; 序号
    dwAddress  DWORD ?   ; 地址
    dwState    DWORD ?   ; 0=删除 1=禁用 2=启用
    dwKind     DWORD ?   ; 0=int3断点 1=内存断点 2=硬件断点
    bOriginal  DWORD ?   ; int3用：原数据
    dwType     DWORD ?   ; 0=一次性 1=永久
    dwBytes    DWORD ?   ; 内存断点用：监控大小
    dwOldProto DWORD ?   ; 内存断点用：原页属性
    dwMemType  DWORD ?   ; 内存断点用：1读/2写/3执行/4访问
BREAKPOINT ENDS

用 dwKind 字段区分断点种类，共用一个结构体数组 g_bps[256]。

内存断点实现

下断点 DbgMemBreakPoint


DbgMemBreakPoint(addr, bytes, type, memType)
    OpenProcess → hProcess
    VirtualProtectEx(hProcess, addr, bytes, PAGE_NOACCESS, &dwOldProto)
    遍历 g_bps 找空槽(dwState==0)：
        存 dwAddress, dwBytes, dwOldProto, dwType, dwMemType, dwState=2, dwKind=1

命令解析 CmdMemBreakPoint


bm 地址 字节数 类型 内存类型
例: bm 401000 4 1 2  → 在401000下4字节永久写断点

参数解析：第一个 token 在字符串开头，循环前先存 lpAddress，遇到空格后存后续参数。

访问违例处理 ExecAccess


ExecAccess:
    dwAccessAddr = ExceptionInformation[4]   ; 被访问地址（MASM中[4]是第二个DWORD）
    dwAccessType = ExceptionInformation[0]   ; 操作类型

    遍历 g_bps:
        if dwKind==1 && dwState==2:          ; 内存断点且启用
            页范围 = dwAddress & 0xFFFFF000
            if 触发地址在同页:
                OpenProcess
                VirtualProtectEx 恢复原属性(dwOldProto)
                存 g_MemBpAddr = dwAddress

                if 触发地址在断点范围内:
                    等命令循环

                CloseHandle
                g_IsMemStep = 1
                DbgSetStep(设Trap Flag)
                return DBG_CONTINUE

    return DBG_EXCEPTION_NOT_HANDLED          ; 没找到匹配断点

单步处理 ExecStep


ExecStep:
    if g_IsMemStep == 1:                      ; 内存断点的单步
        g_IsMemStep = 0
        DbgFindBreakPoint(g_MemBpAddr) → esi
        if 找到:
            VirtualProtectEx 重设 PAGE_NOACCESS
            CloseHandle
        return DBG_CONTINUE                   ; 不等命令，直接放行

    ; 正常单步（用户按t）
    显示寄存器
    等命令循环
    return DBG_CONTINUE

多断点与同页冲突

老师贴出的 C++ 代码只使用一组全局变量（g_BmAddress / g_BmOldProto / g_BmType / g_BmBytes），实际只支持一个 BM 重复命中，不支持多个 BM。当前汇编版使用断点数组，已经能扩展为不同页面的多个 BM。

同一页面上的多个逻辑断点更复杂，因为页面保护以页为单位。完整支持需要：每个页面只保存一次原始属性；一个页面记录多个监控范围；异常时遍历该页的所有范围；页面内仍有有效断点时继续保持保护。

关键问题记录

DbgMemBreakPoint 漏存 dwBytes

下断点时忘了把 nBytes 存到结构体的 dwBytes 字段。恢复保护时 VirtualProtectEx 大小为 0 失败，页一直 NOACCESS，指令执行不了，死循环崩溃。

MASM 数组索引是字节偏移


ExceptionInformation[1]   ; 这是地址+1字节，不是第二个元素！
ExceptionInformation[4]   ; 这才是第二个DWORD元素

MASM 的 [n] 是字节偏移，不是元素索引。DWORD 数组第二个元素要 [4]。

MASM .if 表达式折叠陷阱


; 错误写法 —— MASM 会折叠成错误的寻址
.if eax < [esi].dwAddress + [esi].dwBytes
; 编译成: cmp eax, [esi + esi*1 + 0x1C]  ← 完全错误的地址

; 正确写法 —— 先算出来
mov edx, [esi].dwAddress
add edx, [esi].dwBytes
.if eax >= [esi].dwAddress && eax < edx

MASM 把同一个基址寄存器的两个结构体字段相加，当成了一个寻址表达式折叠，而不是两次内存读取再相加。两个结构体字段相加必须手动用寄存器算。

invoke 覆盖 caller-saved 寄存器


mov eax, ExceptionInformation[1]    ; eax = 被访问地址
invoke OpenProcess, ...             ; eax = 进程句柄（覆盖了！）
invoke VirtualProtectEx, ...        ; eax = 返回值（又覆盖了）
.if eax >= [esi].dwAddress          ; eax 已经不是地址了

stdcall 下 eax/ecx/edx 是 caller-saved，invoke 会覆盖。需要保存到 LOCAL 变量。

dwMemType 编码不一致

自定义编码 1=读/2=写/3=执行/4=访问，Windows 编码 0=读/1=写/8=执行。两套编码对不上，.if eax == [esi].dwMemType 永远不匹配，暂时去掉了类型判断。

g_MemBpAddr 要存断点地址

存触发地址（ExceptionInformation[1]）会导致 DbgFindBreakPoint 找不到断点（同页不同偏移）。要存断点的 dwAddress。

硬件断点 BA

调试寄存器

| 寄存器 | 作用 | |--------|------| | DR0～DR3 | 最多保存 4 个硬件断点地址 | | DR6 | 命中状态：B0=1 表示 DR0 命中，B1/B2/B3 同理 | | DR7 | 启用、访问类型、长度配置 |

DR7 每个槽位包含：Lx 局部启用位、Gx 全局启用位、RWx 访问类型、LENx 长度。

常用编码：

| 字段 | 值 | 含义 | |------|-----|------| | RW | 0 | 执行 | | RW | 1 | 写入 | | RW | 3 | 读写访问 | | LEN | 0 | 1 字节 | | LEN | 1 | 2 字节 | | LEN | 3 | 4 字节 |

执行型硬件断点长度固定按 1 字节处理。数据断点地址应满足长度对齐要求。

线程属性

DR0～DR7 属于线程上下文，给线程 A 设置 DR0 不会自动影响线程 B。完整实现有两种语义：

  • 线程级 BA：只修改当前线程
  • 进程级 BA：给现有所有线程设置，并在创建新线程时继续应用

与现有断点结构结合

可继续使用现有 BREAKPOINT 数组（dwKind=2 表示硬件断点），复用地址、状态、长度、访问类型字段，另需记录硬件槽位 0～3 和所属线程 ID（若实现线程级管理）。

一次性与重复断点

  • 一次性硬件断点：命中后清除对应 DR7.Lx
  • 重复执行型硬件断点：命中 → 暂时关闭对应槽位 → 设置 TF 执行当前指令 → 单步异常 → 重新开启该槽位

老师示例只使用 DR0，并在命中后关闭 L0；如果后续没有重新启用，就只能算一次性硬件断点。

特权指令断点

原理

用特权指令（如 CLI/STI）代替 0xCC 作为断点指令。特权指令在 Ring3 执行会触发 STATUS_PRIVILEGED_INSTRUCTION (0xC0000096)，而不是 EXCEPTION_BREAKPOINT。

与 INT3 断点的区别：

| | INT3 断点 | 特权指令断点 | |---|-----------|-------------| | 触发异常 | EXCEPTION_BREAKPOINT | STATUS_PRIVILEGED_INSTRUCTION | | 恢复后 EIP | 需要 -1（INT3 执行后 EIP 已越过 CC） | 不需要回退（特权指令没有执行，EIP 还指着它） |

处理流程 ExecPrivilegedIns


ExecPrivilegedIns:
    if ExceptionAddress == g_BpAddress:
        恢复原指令
        DbgGetRegs → DbgSetRegs（不需要 EIP-1）
        if 永久断点:
            g_IsBreakStep = TRUE
            DbgSetStep
        等命令循环

cd 03 绕过 0xCC 扫描

int3 有两种编码：0xCC（单字节，通常的 INT3 断点）和 0xCD 0x03（两字节 cd 03）。功能相同，但 0xCC 扫描检测通常只扫 0xCC，用 cd 03 做断点可以绕过这种检测。老师的代码注释里也有 //WORD g_BpCode = 0x03CD; 作为备选断点指令。

各种断点指令对比

| 指令 | 编码 | 触发异常码 | EIP回退 | 绕过0xCC扫描 | |------|------|-----------|---------|-------------| | int3 | CC | EXCEPTION_BREAKPOINT (0x80000003) | 需要-1 | 不能 | | cd 03 | CD 03 | EXCEPTION_BREAKPOINT (0x80000003) | 需要-2 | 能 | | cli | FA | STATUS_PRIVILEGED_INSTRUCTION (0xC0000096) | 不需要 | 能 | | sti | FB | STATUS_PRIVILEGED_INSTRUCTION (0xC0000096) | 不需要 | 能 |

反调试检测方式

| 检测方式 | 原理 | 能防住的断点 | |----------|------|-------------| | 0xCC 扫描 | 遍历代码段找 0xCC 字节 | int3 (0xCC) | | 校验和检测 | 计算代码段 CRC/累加和，与原始值比对 | 所有改代码的断点（0xCC、cd 03、cli） | | 内存断点检测 | 检查页属性是否被改为 NOACCESS | 内存断点 | | 时间检测 | RDTSC 测量指令执行时间，单步会变慢 | 所有断点 |

结论：0xCC 扫描只能防最基础的 int3 断点；校验和能防所有改代码的断点；只有内存断点和硬件断点不改代码，但内存断点改页属性可被检测，硬件断点最难被检测。

DbgReadProcessMemory 加 VirtualProtectEx

内存断点把页设为 PAGE_NOACCESS 后，调试器自己读内存（如 u 命令反汇编）也会触发访问违例。做法：


DbgReadProcessMemory:
    OpenProcess → hProcess
    VirtualProtectEx(hProcess, addr, size, PAGE_READWRITE, &dwOld)  ; 临时改为可读
    ReadProcessMemory(hProcess, addr, buf, size)
    VirtualProtectEx(hProcess, addr, size, dwOld, &dwOld)            ; 恢复原属性
    CloseHandle

读之前临时改成 PAGE_READWRITE，读完后恢复。这样 u 命令读内存断点页就不会失败。
