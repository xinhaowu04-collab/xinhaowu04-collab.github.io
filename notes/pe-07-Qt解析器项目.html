PE 结构

Qt PE32 解析器项目

Qt/C++ 编写的 PE32 解析器：PEParser 负责读取磁盘文件和解析，MainWindow 负责树和表格展示。本节整理导出功能设计、典型代码错误修正、前端拉伸、作业顺序与攻防讨论。

解析器结构与职责分离


MainWindow（QTreeWidget + QTableWidget）
└── PEParser m_parse（对象成员，用点号调用）
     ├── QByteArray m_fileData              磁盘文件原始字节
     ├── IMAGE_DOS_HEADER m_dosHander
     ├── IMAGE_NT_HEADERS32 m_ntHander
     └── QVector<IMAGE_SECTION_HEADER> m_sections

m_parse 是 MainWindow 的 PEParser 对象成员，不是指针，调用写 m_parse.ReadFile(...) 而不是 m_parse->ReadFile(...)。

已有流程：QFileDialog → ReadFile → ParserHeader → parserSections → GetPE → 树和详情表显示，已能显示 DOS 头、NT 头、File Header、Optional Header 和节表的主要字段。

PEParser 拥有 m_fileData，解析逻辑必须放在解析器里；UI 层直接模拟课堂的 hModule + RVA，就是把磁盘文件误当内存映像。

导出功能的 UI 设计

最终目标：点击 Export Table 节点时，不显示一整页元数据，而是每个有效导出项目一行：


EAT下标 | 导出序号 | 函数名称 | 函数RVA / 转发目标

| 阶段 | 内容 | 状态 | |---|---|---| | 第一版最小验证 | 只显示 DataDirectory[0].VirtualAddress/Size | 仅内部定位验证 | | 第二版 | 显示 IMAGE_EXPORT_DIRECTORY 11 个字段 | 信息完整但不够简洁 | | 第三版 | 只显示 Base、数量和三张表地址 6 个核心字段 | 仍偏结构体查看 | | 最终选择 | 每个导出项目一行：EAT下标、序号、名称、RVA/转发 | 当前设计 |

树节点层级：


NT Headers
└── Optional Header
    └── Export Table

不要把导出表挂在 .edata 节下：.edata 只是常见存放位置，实际位置由 DataDirectory[0] 指定，目录 RVA 也不要求等于同名节的起始 RVA。

问题代码（创建了子节点却修改父节点，真正子节点为空；类型又存进点击处理器不读的 UserRole + 2）：


QTreeWidgetItem *ExportTable = new QTreeWidgetItem(OptionalHeader);
OptionalHeader->setText(0, "ExportTable");
OptionalHeader->setData(0, Qt::UserRole + 2, NodeType_ExportTable);

修正：


QTreeWidgetItem *exportTableItem = new QTreeWidgetItem(OptionalHeader);
exportTableItem->setText(0, "Export Table");
exportTableItem->setData(0, Qt::UserRole, NodeType_Export_Table);

枚举中增加 NodeType_Export_Table，点击分支加 case NodeType_Export_Table: { ExportTable(); break; }。

Qt::UserRole 是"自定义数据槽位"，不是节点类别。当前约定：UserRole 统一保存 NodeType，UserRole + 1 给 Section 节点额外保存节索引。区分节点靠枚举值，不是为每类节点换一个 Role。

读取导出表头：典型错误与修正

错误一：UI 层直接算地址


DWORD EptAddressRVA = m_ntHander.OptionalHeader.DataDirectory[0].VirtualAddress;
PDWORD EptAddress = (PDWORD)EptAddressRVA + m_ntHander.OptionalHeader.ImageBase;
PIMAGE_EXPORT_DIRECTORY ExportTables = (PIMAGE_EXPORT_DIRECTORY)*EptAddress;
for (int i = 0; i > EptSize; i++) { }

| 问题 | 原因 | |---|---| | 用 ImageBase + RVA 访问 | 当前是磁盘文件，不是已加载模块 | | 整数强转 PDWORD 后相加 | 指针运算按 sizeof(DWORD) 缩放，且地址不可解引用 | | *EptAddress 再强转结构指针 | 把目标处 4 字节内容误当成新指针 | | EptSize 用作循环数量 | Size 是字节范围，不是导出数量 | | i > EptSize | i=0 时为假，循环一次也不执行 | | UI 直接读私有文件数据 | 破坏 PEParser/MainWindow 职责分离 |

错误二：memcpy 方向与 sizeof


memcpy(
    m_fileData.constData() + exprotFov,
    exportDirectory,
    sizeof(PIMAGE_EXPORT_DIRECTORY)
);

问题：memcpy 目标和来源写反；constData() 是只读来源不能当写入目标；引用作目标要写 &exportDirectory；sizeof(PIMAGE_EXPORT_DIRECTORY) 是指针大小不是结构体大小；局部 exprotFov 没赋给输出参数；返回 void 让调用者无法区分"无导出表/转换失败/成功"；RvaToFov 失败时 exprotFov 可能未初始化。

修正后：


bool PEParser::GetExportDirectory(
    IMAGE_EXPORT_DIRECTORY &exportDirectory,
    DWORD &exportFoa)
{
    exportDirectory = {};
    exportFoa = 0;

    const IMAGE_DATA_DIRECTORY &directory =
        m_ntHander.OptionalHeader.DataDirectory[IMAGE_DIRECTORY_ENTRY_EXPORT];
    if (directory.VirtualAddress == 0 || directory.Size == 0) {
        return false;
    }
    if (!RvaToFov(directory.VirtualAddress, exportFoa)) {
        return false;
    }
    memcpy(
        &exportDirectory,
        m_fileData.constData() + exportFoa,
        sizeof(IMAGE_EXPORT_DIRECTORY)
    );
    return true;
}

正确复制方向：m_fileData + exportFoa →（memcpy）→ exportDirectory。

RvaToFov 也应改为 bool RvaToFov(DWORD rva, DWORD &foa)：成功写入并返回 true，无匹配时清零返回 false；调用者不能把失败后的 0 当成有效 FOA。

构造导出函数列表

ExportFunctionInfo 不用 union：名称和序号并不互斥（命名导出同样有序号），转发状态也不是名称/序号的替代项。


struct ExportFunctionInfo
{
    DWORD eatIndex {};
    DWORD ordinal {};
    DWORD functionRva {};
    QString name;       // 空 = 没有名称
    QString forwarder;  // 空 = 普通导出
};

两遍构造，避免"每个 EAT 项都重新扫描整个名称序号表"：


第一遍：遍历 EAT
  for i in [0, NumberOfFunctions):
      functionRva == 0 → 空洞，跳过或标 Empty
      eatIndex = i，ordinal = Base + i，name = 空

第二遍：遍历名称表补名字
  for j in [0, NumberOfNames):
      nameRva = Names[j]，eatIndex = NameOrdinals[j]
      functions[eatIndex].name = 文件中的零结尾字符串

第三步：识别转发
  ExportRVA <= functionRva < ExportRVA + ExportSize → 读转发字符串
  否则 → 普通 EAT RVA（仍需区分函数/数据导出）

UI 最终四列：


EAT下标 | 导出序号 | 函数名称 | 函数RVA / 转发目标

普通导出示意 0 | 1000 | MyAdd | 0x00001000；转发导出示意 3 | 1003 | MsgBox | 0x0000581F -> user32.MessageBoxA。函数 RVA 应显示；默认不显示 VA（首选 VA 受 ASLR 影响，不一定是运行时地址）；FOA 可由地址转换器按需查看。

易错点

1. exportFoa 不是多余数据，它是导出表头在磁盘文件内的位置，用于从 m_fileData 读取并计算各字段 FOA。 2. 显示每个导出项目不等于不解析表头：UI 可隐藏 Base/NumberOfFunctions，但解析器内部必须使用这些字段。 3. 结构体字段视图适合 字段名|FOA|大小|值 四列；函数列表视图列语义不同，可另写 addExportRow 或切换表头。 4. 只得到表头不代表功能完成，还需 EAT、名称、序号、转发解析和实际 DLL 验证。

验证状态

导出解析已完成结构设计和代码纠错，最小验证步骤：


1. 选择一个确定有导出的 32 位 DLL
2. GetExportDirectory 返回 true
3. 记录 exportFoa
4. 记录 NumberOfFunctions 与 NumberOfNames
5. 用另一 PE 工具交叉核对
6. 再进入 EAT 遍历

Qt 前端与自动拉伸

界面为 QTreeWidget 加两个 QTableWidget：导出模式上表显示 IMAGE_EXPORT_DIRECTORY、下表显示导出函数；重定位模式上表显示块、下表显示选中块的条目。PEParser 管理原始数据和解析结果，MainWindow 负责显示；嵌套 QVector 正好对应"点击块显示块内条目"。

ResizeToContents 只按内容算列宽，可能留白；Stretch 让列共同填满表格宽度。改变列数后要重新设置 Stretch。


void MainWindow::stretchTables()
{
    ui->tableDetail->horizontalHeader()
        ->setSectionResizeMode(QHeaderView::Stretch);
    ui->tableExportFunctions->horizontalHeader()
        ->setSectionResizeMode(QHeaderView::Stretch);
}

在构造函数、resetTableHeaders、RelocationTable、ExportTable、showRelocationEntries 和节点点击结束处调用；删除会覆盖 Stretch 效果的 resizeColumnsToContents。默认最大化可在 main 中 w.showMaximized();。

当前表头：


导出：  EAT下标 | EAT项FOA | 导出序号 | 函数RVA | 名称RVA | 名称 | 转发器
重定位：块FOA | Page RVA | Block Size | 项目数
       项目FOA | 值 | 类型 | 页内偏移 | Reloc RVA

注意：

  • Qt Creator 报"读取 1 行、1 列 UI 文件时需要开始标记"，通常是 XML 前有多余文本或误复制了 Markdown 代码围栏，文件第一行应从 XML 声明开始。
  • 列自动拉伸和上下表格高度不是一回事：列用 QHeaderView::Stretch，上下高度由 QSplitter 控制。
  • 节点切换要清空旧内容、恢复表头、设置新列数，最后再次调用 stretchTables。

作业顺序与学习路线

老师布置两项作业：32 位汇编模拟实现 MyGetProcAddress；PE 工具增加导出表解析。

没有硬性提交顺序时，先做可视化 PE 工具更适合：三张表、RVA→FOA、名称→EAT下标→序号→函数RVA 都能直接看见，之后写 MASM 只是把同一流程换成寄存器、指针和调用约定表达。若老师下一节优先检查汇编作业，则先完成汇编的最小普通查询，再回头补 UI。

推荐顺序：


阶段1：Qt 工具取得导出表头并验证
阶段2：遍历 EAT，显示 EAT下标/序号/RVA
阶段3：名称表 + 名称序号表补名称
阶段4：识别转发字符串
阶段5：MASM 实现按名称/序号查询普通导出
阶段6：MASM 增加函数转发

PE 工具可作为汇编作业的"结果观察器"：汇编算出 EAT 下标、序号或 RVA 后用工具对照。不要一开始同时写转发、EAT Hook、IAT 反查和 UI 全功能，每层先有可核对输出。作业是否要求转发、空洞、仅序号导出，应向老师确认验收范围。

导入/导出逆向攻防思路

当前只学过导入表、IAT、导出表、EAT、函数转发和 API 解析，攻防讨论以此为限（授权实验环境）：

| 攻击/对抗思路 | 防御/逆向关注点 | |---|---| | 擦除或伪造导入描述符 | 从现存 IAT 地址、模块和导出表尝试恢复名称 | | 手工遍历导出表 | 不只监控系统 GetProcAddress，还关注最终调用目标 | | API Hash | 恢复哈希算法与候选导出名称，结合动态行为确认 | | IAT Hook | 检查 IAT 目标是否指向预期模块/导出 | | EAT Hook | 比较内存 EAT 与可信文件/干净映像的 EAT RVA | | 仅序号导入/导出 | 结合具体 DLL 版本导出表还原名称，注意版本兼容性 | | 代理 DLL/导出转发 | 检查模块加载路径、来源、转发链与最终实现 | | 伪造大量假导入 | 区分"文件声明"与"运行时实际调用" |

静态导入表只是"文件声明的依赖"，不必然等于运行时所有实际 API：可能存在未使用的导入、故意添加的假导入、运行时动态解析的额外 API、被擦除描述符但保留的 IAT，甚至不保留 IAT 而手工解析导出表。防御分析必须把静态声明、运行时地址、转发链和实际控制流结合起来。

可向老师追问的问题：

1. EAT Hook 不影响已填好的 IAT，攻击者何时选 EAT Hook、何时选 IAT Hook 或 Inline Hook？ 2. 攻击者短暂修改 EAT、调用后立即恢复，快照式扫描如何发现？是否应监控 .edata 页保护变化与写入？ 3. EAT 指向模块内部代码洞/跳板时返回地址仍在 SizeOfImage 内，范围检查为何失效？ 4. 无导入表、手工遍历导出表并用 API Hash 时，静态和动态分析如何恢复真实 API？ 5. 恶意 PE 能否利用无序名称表、异常数量、越界 RVA 或循环转发造成加载器与安全工具解析差异？ 6. IAT 地址最终落在 KernelBase/ntdll 时，如何同时保留原始 kernel32 导入名与最终实现？ 7. 磁盘文件也不可信时，内存 EAT 比较应从哪里取得可信基线？ 8. 安全产品只 Hook GetProcAddress/LdrGetProcedureAddress 时，手工导出解析能否绕过？防守应观察解析过程还是最终调用？ 9. IAT 与 EAT 同时被修改时，怎样避免用两张都被污染的表互相验证？ 10. 序号导入可隐藏名称，但不同 DLL 版本的序号稳定性如何？ 11. 代理 DLL 大量转发真实 DLL 导出时，怎样区分正常转发和恶意代理？ 12. 伪造敏感假导入是否会误导静态分析，怎样与运行时实际调用区分？

注意：

  • "地址在模块外"只是异常线索（合法转发本来落到其他模块）；"地址在模块内"也不是强证明（可能是内部跳板或代码洞）。
  • EAT 原始项是 RVA，ASLR 通常不改变它，可信同版本映像的 EAT RVA 可比较，但来源和版本必须可信。
  • 热补丁、安全产品 Hook、版本更新都可能造成差异，发现差异后需结合上下文判断。
  • 导出反查可能有多个候选名称：转发、别名、导出变量、Hook 都会造成歧义。
  • "导出表由系统维护、更稳定"是相对说法，EAT Hook 本身证明它也能被修改。
