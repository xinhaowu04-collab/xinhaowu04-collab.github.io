Shellcode：内存与位置无关代码

写 shellcode loader 之前必须掌握的前置知识：用什么类型存 shellcode 字节、怎么申请能执行代码的内存、代码如何在任意地址运行。

unsigned char 与 C 数据类型

unsigned char 是 C 语言中占用 1 字节、无符号的整数类型，取值范围 0 ~ 255。它本质上是"1 字节的无符号整数"，而非通常意义上的"字符"。shellcode 的每一个字节范围是 0x00 ~ 0xFF，unsigned char 是存储 shellcode 最自然、最安全的类型。

C 整数类型全家：

|类型|大小|范围| |---|---|---| |unsigned char|1 字节|0 ~ 255| |char|1 字节|-128 ~ 127| |unsigned short|2 字节|0 ~ 65535| |short|2 字节|-32768 ~ 32767| |unsigned int|4 字节|0 ~ 4294967295| |int|4 字节|-2147483648 ~ 2147483647|

与汇编对应关系：

|C|汇编伪指令|大小| |---|---|---| |unsigned char|db / BYTE|1 字节| |unsigned short|dw / WORD|2 字节| |unsigned int|dd / DWORD|4 字节|

因此 unsigned char shellcode[] 等价于汇编中的 shellcode db 90h, 0C3h。

为什么必须用无符号类型

普通 char 的最高位是符号位（补码表示），取值范围 -128 ~ 127。当存放的值超过 127 时会被解释为负数，例如 0x90 = 144 在 signed char 中实际存储为 -112。虽然内存中的比特位完全相同，但在打印、比较、数学运算时会产生意外结果。

shellcode 字节中的每一位都是指令或数据的一部分，没有任何"符号"语义，必须使用无符号类型避免符号扩展问题。


0x90 (144)
  ├─ unsigned char → 值为 144，打印正确，比较正确
  └─ signed char   → 值为 -112（补码），打印出错，比较出错

用法


unsigned char shellcode[] = {
    0x90,   // NOP
    0xC3,   // RET
    0x48, 0x31, 0xC0,  // xor rax, rax (64-bit)
    0xC3                // RET
};

// 传递给 Win32 API 时，通常需要强制转型
void *addr = VirtualAlloc(NULL, sizeof(shellcode), MEM_COMMIT, PAGE_EXECUTE_READWRITE);
memcpy(addr, shellcode, sizeof(shellcode));

若 API 需要 BYTE* 或 LPVOID 参数，unsigned char* 可以安全转换（BYTE 即是 unsigned char 的 typedef）。

注意：shellcode 中可能包含 0x00 空字节，不能用 strlen 获取长度，它会在第一个空字节处停止。

VirtualAlloc 与 VirtualFree

VirtualAlloc 和 VirtualFree 是 Windows 提供的虚拟内存分配与释放 API，允许调用者精确控制内存的分配方式（提交/保留）和保护属性（读/写/执行），是 shellcode loader 中申请可执行内存的核心手段。


// VirtualAlloc — 申请虚拟内存
LPVOID VirtualAlloc(
    LPVOID lpAddress,        // 想要的地址，传 NULL 让系统自动选择
    SIZE_T dwSize,           // 申请大小（字节）
    DWORD  flAllocationType, // 分配方式：MEM_COMMIT / MEM_RESERVE
    DWORD  flProtect         // 保护属性：PAGE_EXECUTE_READWRITE 等
);

// VirtualFree — 释放虚拟内存
BOOL VirtualFree(
    LPVOID lpAddress, // VirtualAlloc 返回的地址
    SIZE_T dwSize,    // 大小，MEM_RELEASE 时必须为 0
    DWORD  dwFreeType // MEM_RELEASE / MEM_DECOMMIT
);

参数速查

|参数|典型值|含义| |---|---|---| |lpAddress|NULL|让系统自动选地址，避免指定地址被占用导致失败| |dwSize|shellcode 长度|申请多少字节| |flAllocationType|MEM_COMMIT|提交物理内存| |flProtect|PAGE_EXECUTE_READWRITE|可读可写可执行|

flAllocationType 取值：

|值|含义| |---|---| |MEM_COMMIT (0x1000)|提交物理内存，分配后可直接读写| |MEM_RESERVE (0x2000)|只保留地址空间，不占物理内存| |MEM_COMMIT \| MEM_RESERVE|保留 + 提交，一步到位|

flProtect 取值：

|值|含义|读|写|执行| |---|---|:-:|:-:|:-:| |PAGE_READONLY (0x02)|只读|是|否|否| |PAGE_READWRITE (0x04)|可读写|是|是|否| |PAGE_EXECUTE (0x10)|只执行|否|否|是| |PAGE_EXECUTE_READ (0x20)|可读可执行|是|否|是| |PAGE_EXECUTE_READWRITE (0x40)|可读写可执行|是|是|是|

flFreeType 取值：

|值|含义| |---|---| |MEM_RELEASE (0x8000)|彻底释放，归还给系统，dwSize 必须为 0| |MEM_DECOMMIT (0x4000)|只回收物理内存，地址空间还保留着|

为什么 malloc 不够用


void* mem = malloc(1024);
memcpy(mem, shellcode, 1024);
((void(*)())mem)();   // 崩溃！malloc 分配的内存不可执行


malloc        → PAGE_READWRITE         能读 能写 不能执行
VirtualAlloc  → PAGE_EXECUTE_READWRITE  能读 能写 能执行

malloc 分配的内存保护属性为 PAGE_READWRITE，只允许读写，不允许执行。这是 Windows DEP（Data Execution Prevention，数据执行保护） 机制的体现——数据段不能当作代码执行，防止缓冲区溢出攻击。

Shellcode loader 的本质就是：主动申请一块可执行内存（PAGE_EXECUTE_READWRITE），从而在 DEP 保护下合法地执行注入的代码。

内存生命周期：


VirtualAlloc（申请 RWX 内存）
    → memcpy（写入 shellcode）
    → 函数指针调用（执行 shellcode）
    → VirtualFree（释放内存）

注意：RWX 内存页是 EDR/杀软的经典检测特征。实战中通常分两步：先以 PAGE_READWRITE 申请并写入 shellcode，再用 VirtualProtect 改为 PAGE_EXECUTE_READ。

标准 loader 分配模式


#include <windows.h>

int main() {
    // shellcode 数据
    unsigned char shellcode[] = { /* ... */ };
    SIZE_T size = sizeof(shellcode);

    // 1. 申请可执行内存
    LPVOID mem = VirtualAlloc(
        NULL,                    // 系统选地址
        size,                    // shellcode 大小
        MEM_COMMIT,              // 提交物理内存
        PAGE_EXECUTE_READWRITE   // RWX 权限
    );
    if (mem == NULL) return -1;

    // 2. 写入 shellcode
    memcpy(mem, shellcode, size);

    // 3. 执行 shellcode
    ((void(*)())mem)();

    // 4. 释放内存
    VirtualFree(mem, 0, MEM_RELEASE);

    return 0;
}

参数选择要点：

  • lpAddress = NULL：让系统自动选择地址，避免因指定地址已被占用而失败
  • flAllocationType = MEM_COMMIT：直接提交物理内存，一步到位
  • flProtect = PAGE_EXECUTE_READWRITE：同时满足写入（memcpy）和执行（跳转调用）的需求
  • VirtualFree 的 dwSize = 0：MEM_RELEASE 时要求 dwSize 必须为 0，否则调用失败

位置无关代码（PIC）与 call/pop 技术

位置无关代码（Position-Independent Code, PIC） 是指代码中不出现任何绝对地址，所有内存引用都是相对地址。无论将代码加载到哪个内存基址，它都能正确执行，无需重定位修正。

这是 shellcode 编写的核心基础——shellcode 被注入到目标进程后，由 VirtualAlloc 分配的内存地址不可预知，必须保证代码在任何地址都能正常运行。

普通 exe 代码不能直接当 shellcode 的三个原因

问题 1：offset 是绝对地址


push offset szLoadLibraryA   ; 编译后变成 push 0x00402030（写死的地址）

shellcode 被放到其他地址时，0x00402030 指向垃圾内存，导致崩溃。

问题 2：extrn 依赖导入表


call ExitProcess@4   ; 跳到 IAT（导入地址表）

提取出来的裸机器码没有 IAT，没有加载器帮忙填充真实地址，调用失败。

问题 3：.data 变量地址写死


mov pGetProcAddress, eax   ; pGetProcAddress 在 .data 段，地址固定

shellcode 运行时 .data 段不存在于目标内存中。

PE 文件 vs shellcode

|特性|PE 文件|shellcode| |---|---|---| |绝对地址|有，靠重定位表修正|根本不出现| |字符串|.data 段 + offset|call/pop 内联| |API 地址|IAT，加载器填写|PEB 遍历 + 导出表动态查找| |任意地址运行|否（需重定位）|是|

call/pop 原理

call 指令在底层做两件事：将返回地址（call 下一条指令的地址）压栈，然后跳转到目标地址。call/pop 技巧利用这一机制，通过 call 跳过内联的字符串数据，然后用 pop 从栈上取出该字符串的运行时地址。


call lbl          ① 把下一条指令地址压栈（= 字符串起始地址）
db "hello", 0     ② 字符串紧跟在 call 后面（数据，不会被执行）
lbl:              ③ 跳到这里继续执行
pop eax           ④ eax = 字符串的地址！

无论 shellcode 被加载到哪个基址，call 指令和其后面的内联数据之间的相对距离永远不变，因此拿到的地址始终正确。

call 指令的机器码：


E8 0D 00 00 00    call lbl

E8 是 call rel32 的操作码，后面 4 字节是相对偏移（有符号整数），不是绝对地址。这就是 call/pop 能做到位置无关的根本原因——相对偏移在任意加载地址下语义不变。

基本模式与寄存器分工


; 错误：绝对地址（位置相关）
push 0x00402030          ; 写死的地址，换个内存就错

; 正确：call/pop（位置无关）
call s1
db "LoadLibraryA", 0
s1: pop eax              ; eax = "LoadLibraryA" 的当前地址
push eax

避免使用 .data 变量，改用寄存器持久保存函数指针：

|寄存器|用途| |---|---| |edi|保存 GetProcAddress 地址| |ebp|保存 LoadLibraryA 地址| |esi|保存 kernel32 基地址|
