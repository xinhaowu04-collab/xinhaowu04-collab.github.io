B - 页表属性（通过VirtualProtectEx修改页面保护） 9. C - EXCEPTION_ACCESS_VIOLATION（0xC0000005） 10. B - 访问类型（0=读，1=写，8=执行） 11. B - 命中后是否重新设置断点 12. B - 遇到call指令时，P会跳过call内部 13. C - 记录硬件断点的命中状态（B0~B3位） 14. C - 读写访问断点（RW=11b） 15. B - 0x80000003（系统初始断点）

二、填空题（每空1分，共20分）

1. 调试事件共有 9 种，分别通过DEBUG_EVENT结构体的 dwDebugEventCode 字段区分。

2. ContinueDebugEvent的返回值有两种：DBG_CONTINUE(0x00010002) 表示异常已处理，DBG_EXCEPTION_NOT_HANDLED(0x80010001) 表示异常未处理，交给SEH链。

3. 软件断点的完整流程是：写入 0xCC 机器码 → 命中后恢复 原 字节 → EIP回退 1 字节 → 执行 原 指令 → 永久断点重新写入。

4. TF标志位的位置是EFLAGS的第 8 位，可以通过OR运算 0x100 来设置。

5. 硬件断点的配置包括：DR0~DR3存放 断点地址，DR6记录 命中状态，DR7配置 断点启用 和 访问类型/长度。

6. 内存断点通过 VirtualProtectEx API修改页面属性为 PAGE_NOACCESS/PAGE_READONLY，触发 EXCEPTION_ACCESS_VIOLATION 异常。

7. 内存断点的恢复流程：命中后恢复为 原始 属性 → 设置 TF 标志 → 执行一条指令 → 单步异常中重新设置 内存保护。

8. EXCEPTION_RECORD结构中，ExceptionAddress 字段是触发异常的指令地址，ExceptionInformation[1] 字段是被访问的内存地址。

9. 单步步过的实现：判断当前指令是否为 call，如果是则在 下一条指令 处设置 临时 断点。

10. 调试寄存器是 线程 级属性，修改线程A的DR0不会影响线程B，需要通过 GetThreadContext 和 SetThreadContext API操作。

三、判断题（每题1分，共10分）

1. √ - 软件断点理论上可以设置无限个（仅受内存限制） 2. × - DR0~DR7是线程级的，每个线程独立 3. √ - 内存断点按页面（4KB）粒度生效 4. × - 特权指令断点命中后EIP不需要回退（异常发生在指令执行前） 5. √ - INT3的两字节形式"CD 03"功能相同但机器码不同 6. × - 单步异常可能来自TF标志、硬件断点、内存断点恢复等多种情况 7. × - 永久断点需要先恢复原字节并单步执行原指令后才能重新写入 8. × - 调试器和被调试进程是不同的进程，LastError独立 9. × - ExceptionInformation[1]是被访问的内存地址，ExceptionAddress是触发异常的指令地址 10. √ - WaitForDebugEvent会阻塞到调试事件发生（除非指定超时）

四、简答题（每题5分，共20分）

1. 软件断点恢复流程原理

为什么需要完整流程：

  • 如果命中后直接重新写入0xCC，会导致原指令无法执行
  • EIP已经指向断点指令的下一字节，如果不回退，原指令被跳过
  • 恢复原字节后必须单步执行原指令，否则断点失效

流程必要性： 1. 恢复原字节：让原指令可以正常执行 2. EIP回退1字节：回到原指令位置 3. 设置TF单步：确保执行一条原指令后重新获得控制权 4. 单步异常中重新写入0xCC：恢复断点功能

如果直接重新写入0xCC，会导致CPU反复执行INT3指令，进入死循环，原指令永远无法执行。

2. 硬件断点与软件断点对比

软件断点优缺点：

  • ✓ 数量无限制
  • ✓ 实现简单
  • ✗ 修改代码段，容易被检测（扫描0xCC）
  • ✗ 无法对只读页面设置
  • ✗ 需要恢复原字节流程

硬件断点优缺点：

  • ✓ 不修改代码，隐蔽性强
  • ✓ 支持读写访问断点
  • ✓ 可对只读内存设置
  • ✗ 数量限制（最多4个）
  • ✗ 实现较复杂（操作调试寄存器）

使用场景： 1. 需要隐蔽调试（反反调试） 2. 监控数据读写访问 3. 对只读代码段设置断点 4. 断点数量少于4个的情况

3. 内存断点工作原理

工作原理： 1. 通过VirtualProtectEx修改页面属性为PAGE_NOACCESS或PAGE_READONLY 2. 当程序访问该页面时，触发EXCEPTION_ACCESS_VIOLATION异常 3. 调试器在异常处理中判断是否为内存断点，并处理

恢复流程必要性： 1. 恢复页属性：必须让程序能够正常访问该内存 2. 设置TF单步：执行一条导致异常的指令后重新获得控制权 3. 单步异常中重新保护：恢复内存断点的监控功能

如果不恢复页属性，程序会反复触发访问违例异常；如果不重新保护，断点失效。这个流程确保：既能执行原指令，又能保持断点持续生效。

4. 单步步过（P命令）实现原理

实现步骤： 1. 反汇编当前指令：读取EIP指向的机器码并解析 2. 判断是否为call指令：

  • 可以判断首字节是否为0xE8（near call）或0xFF（间接call）
  • 也可以用反汇编引擎识别指令类型

3. 计算call的下一条指令地址：

  • 对于E8型：下一地址 = EIP + 5
  • 对于FF型：需根据ModR/M字节计算指令长度

4. 在下一条指令处设置临时软件断点 5. 继续执行，不设置TF标志 6. 断点命中后删除临时断点

关键点：

  • 临时断点是一次性的，命中后自动删除
  • 如果不是call指令，则退化为T命令（设置TF单步）
  • 需要准确计算指令长度，否则断点位置错误

五、代码分析题（每题5分，共10分）

1. 调试事件处理代码分析

问题（3分）：

  • 当异常代码不是EXCEPTION_BREAKPOINT或EXCEPTION_SINGLE_STEP时，函数返回DBG_CONTINUE
  • 这会导致未知异常被标记为"已处理"，阻止程序的正常异常处理机制（SEH链）
  • 正确的做法应该是返回DBG_EXCEPTION_NOT_HANDLED，让系统继续分发异常

修正（2分）：


EventException proc
    LOCAL ctx:CONTEXT

    mov eax, g_DbgEvent.u.Exception.pExceptionRecord
    mov eax, [eax].ExceptionCode

    .if eax == EXCEPTION_BREAKPOINT
        invoke ExecBreakPoint
        mov eax, DBG_CONTINUE
        ret
    .elseif eax == EXCEPTION_SINGLE_STEP
        invoke ExecStep
        mov eax, DBG_CONTINUE
        ret
    .endif

    mov eax, DBG_EXCEPTION_NOT_HANDLED  ; 改为未处理
    ret
EventException endp

2. 断点设置代码分析

问题1（2分）：

  • ReadProcessMemory读取4字节是为了保存原指令的足够上下文
  • WriteProcessMemory只写入1字节是因为INT3指令(0xCC)只占1字节
  • 保存4字节可以确保恢复时不会出现问题（虽然理论上只需保存1字节）

问题2（3分）： 如果WriteProcessMemory写入4字节会导致： 1. 破坏后续指令：后面3字节的指令被破坏，即使恢复原字节也无法正确执行 2. 指令边界错位：可能破坏多条指令，导致程序崩溃 3. 断点无法正确恢复：只有第1字节需要替换为0xCC，其余字节应保持不变

正确做法是：读取1~4字节保存原值，但只写入1字节的0xCC。

六、综合实现题（共10分）

硬件执行断点实现

1. DR7配置值计算（2分）：

硬件执行断点使用DR0，DR7配置如下：

  • L0位（bit 0）= 1：启用DR0局部断点
  • RW0字段（bit 16-17）= 00b：执行断点
  • LEN0字段（bit 18-19）= 00b：1字节长度

DR7 = 0x00000001（只设置L0位）

完整计算：


Bit 0 (L0) = 1
Bit 16-17 (RW0) = 00 (执行)
Bit 18-19 (LEN0) = 00 (1字节)
DR7 = 0x00000001

2. 判断断点触发源（2分）：

检查DR6寄存器的B0~B3位：


mov eax, ctx.iDr6
and eax, 0Fh        ; 取低4位
.if eax != 0
    ; 是硬件断点触发（检查哪一位为1）
.else
    ; 是TF单步触发
.endif

DR6的B0=1表示DR0命中，B1=1表示DR1命中，以此类推。

3. 永久硬件断点恢复流程（2分）：

需要"关闭 → 单步 → 重新启用"的原因：

  • 如果不关闭断点，单步执行后会立即再次触发硬件断点
  • 因为硬件断点在指令执行前就会触发，不像软件断点需要修改代码
  • 流程：DR7清除L0位 → 设置TF → 执行一条指令 → 单步异常中重新设置DR7

4. 多硬件断点数据结构（2分）：


HWBP_ITEM struct
    dwAddress   DWORD ?     ; 断点地址
    dwType      DWORD ?     ; RW类型(0=执行,1=写,3=读写)
    dwLen       DWORD ?     ; 长度(0=1字节,1=2字节,3=4字节)
    bEnabled    BYTE ?      ; 是否启用
    bPermanent  BYTE ?      ; 是否永久
HWBP_ITEM ends

g_HwBpList  HWBP_ITEM 4 dup(<>)  ; 4个硬件断点槽位

5. 进程级硬件断点实现（2分）：

需要为所有线程设置相同的DR0~DR7： 1. CREATE_THREAD事件中自动设置：新线程创建时同步断点配置 2. 维护全局配置表：记录当前生效的硬件断点 3. 遍历所有线程应用配置：


; 伪代码
for each thread in process:
    GetThreadContext(thread, &ctx)
    ctx.Dr0 = g_HwBpList[0].dwAddress
    ctx.Dr7 = CalculateDR7()
    SetThreadContext(thread, &ctx)

七、调试场景分析题（共10分）

多断点冲突处理

1. 触发顺序（2分）：

软件断点会先触发，因为：

  • 软件断点(0xCC)直接替换指令机器码，CPU取指时立即执行INT3
  • 硬件断点在指令执行阶段检测
  • 内存断点在内存访问时检测
  • 由于软件断点已将指令替换为INT3，CPU根本不会执行到原指令，所以硬件断点和内存断点不会触发

2. 单步执行时内存断点（2分）：

会触发内存断点，因为：

  • 软件断点恢复原字节后，原指令被恢复
  • 单步执行时，CPU执行原指令，会从0x00401000取指（读访问）
  • 内存断点监控读写访问，所以会触发EXCEPTION_ACCESS_VIOLATION
  • 这会与软件断点的恢复流程产生冲突

3. 断点优先级和恢复流程设计（2分）：

设计方案： 1. 优先级：软件断点 > 硬件断点 > 内存断点 2. 冲突处理：

  • 软件断点命中时，临时禁用同地址的内存断点和硬件断点
  • 恢复流程：恢复原字节 → 禁用其他断点 → 设置TF → 执行原指令
  • 单步异常中：判断是否有其他断点，依次触发 → 最后重新启用所有断点

3. 状态机：使用标志位记录当前处于哪个断点的恢复阶段

4. 多内存断点页面管理（2分）：

管理策略： 1. 引用计数：每个页面维护断点引用计数


   页面0x00401000: {保护状态: PAGE_NOACCESS, 引用计数: 2}

2. 删除断点时：引用计数-1，计数为0时才恢复原始页面属性 3. 添加断点时：引用计数+1，已保护则不重复设置 4. 恢复流程：临时恢复页面 → 单步 → 重新保护（只要引用计数>0）

5. 区分EXCEPTION_SINGLE_STEP来源（2分）：

判断方法： 1. 检查DR6寄存器：如果B0~B3任一位为1，来自硬件断点 2. 检查恢复状态标志：


   g_BreakpointRecovering  DWORD 0  ; 0=无,1=软件断点,2=内存断点

3. 判断逻辑：


   if (DR6 & 0x0F != 0):
       来自硬件断点
   else if (g_BreakpointRecovering == 1):
       来自软件断点恢复
   else if (g_BreakpointRecovering == 2):
       来自内存断点恢复
   else:
       来自用户T命令

4. 处理完成后清除标志
