导出表与函数转发

PE 结构

导出表与函数转发

导出表（Export Table）描述一个 PE 映像向外提供的符号，最常见于 DLL，但 EXE 同样可以拥有导出表。

| 对象 | 回答的问题 | |---|---| | 导入表 | 当前程序需要哪些外部 DLL 和函数 | | 导出表 | 当前模块向其他模块提供哪些函数或数据 |

导出表结构与三张核心表

PE 文件总体布局：


IMAGE_DOS_HEADER
MS-DOS Stub
IMAGE_NT_HEADERS（Signature + IMAGE_FILE_HEADER + IMAGE_OPTIONAL_HEADER32 + DataDirectory[]）
IMAGE_SECTION_HEADER[]
SectionData[]
Extra Data / Overlay（若存在）

导出表入口位于 OptionalHeader.DataDirectory[IMAGE_DIRECTORY_ENTRY_EXPORT]（索引 0），VirtualAddress 是导出目录 RVA，Size 是范围字节数。

注意：数据目录通常使用 RVA，但安全目录（证书目录）是特例，其"地址"具有文件偏移语义。

真正的导出表头：


typedef struct _IMAGE_EXPORT_DIRECTORY {
    DWORD Characteristics;
    DWORD TimeDateStamp;
    WORD  MajorVersion;
    WORD  MinorVersion;
    DWORD Name;                  // 模块名称字符串 RVA
    DWORD Base;                  // 导出序号基准
    DWORD NumberOfFunctions;     // EAT 项数
    DWORD NumberOfNames;         // 有名称的导出数量
    DWORD AddressOfFunctions;    // EAT RVA，DWORD 数组
    DWORD AddressOfNames;        // 名称 RVA 数组的 RVA，DWORD 数组
    DWORD AddressOfNameOrdinals; // 名称对应 EAT 下标数组的 RVA，WORD 数组
} IMAGE_EXPORT_DIRECTORY, *PIMAGE_EXPORT_DIRECTORY;

Base、NumberOfFunctions、NumberOfNames、AddressOfFunctions、AddressOfNames、AddressOfNameOrdinals 是核心字段；其余为版本/时间戳/名称等元数据，不参与名称/序号解析主链。这些字段在文件中都可被修改，但修改核心计数、RVA 或 Name 可能改变解析结果，甚至导致文件无法解析。

三张核心表：

| 表 | 元素大小 | 内容 | |---|---:|---| | 函数地址表 EAT（AddressOfFunctions） | DWORD | 函数 RVA、数据 RVA、空洞 0 或转发字符串 RVA | | 名称指针表（AddressOfNames） | DWORD | 导出名称字符串的 RVA | | 名称序号表（AddressOfNameOrdinals） | WORD | 对应名称的 EAT 下标 |

按序号查找


EAT 下标 = Ordinal - Base
函数 RVA = AddressOfFunctions[EAT 下标]

边界：EAT 下标必须 < NumberOfFunctions；EAT 项为 0 是序号空洞，不对应有效导出。人为指定的导出序号不连续时，Base 到最大序号之间仍要保留 EAT 下标位置，因此出现填 0 的空洞，造成空间浪费。

按名称查找

名称表顺序与 EAT 顺序不是同一套索引，不能直接用"名称表下标"访问 EAT。正确链路：


函数名 → 在 AddressOfNames 中找到下标 i
→ AddressOfNameOrdinals[i] 得 EAT 下标
→ AddressOfFunctions[EAT 下标] = 函数 RVA
→ 序号 = Base + EAT 下标

名称指针表通常按字典序组织，可以二分查找；课堂演示代码用遍历加 strcmp。

序号与名称的关系

  • 所有非空 EAT 项都有序号：Ordinal = Base + EATIndex；只有部分 EAT 项额外拥有名称。
  • "名称导出"和"序号导出"不是严格二选一：有名称的函数也可按序号获取；没有名称映射的非空 EAT 项才是"仅按序号导出"。
  • NumberOfFunctions 是 EAT 槽位数量（可能含 0 空洞），NumberOfNames 是名称表/名称序号表的有效项数量。建完整导出列表应以 NumberOfFunctions 遍历 EAT，再用名称表给相应行补名字；只遍历 NumberOfNames 会漏掉仅按序号导出的项。

课堂示意示例

以下三张表来自课堂代码注释，为示意数据（与后文实测数据数值不同，结构关系一致）：


EAT：        0:0x1000  1:0x100B  2:0x6030  3:0x581F→"user32.MessageBoxA"  4:0x580A→"kernel32.#388"
名称表：     0:ExitProcess  1:MsgBox  2:MyAdd  3:g_num
名称序号表： 0→4  1→3  2→0  3→2

| 名称 | EAT 下标 | EAT 内容 | 结论 | |---|---:|---|---| | ExitProcess | 4 | 0x580A | 转发到 kernel32.#388 | | MsgBox | 3 | 0x581F | 转发到 user32.MessageBoxA | | MyAdd | 0 | 0x1000 | 普通 RVA | | g_num | 2 | 0x6030 | 名字暗示为数据导出，需实际 DLL 确认 | | 无名称 | 1 | 0x100B | 仅按序号导出的候选项 |

小例子：Base = 1，AddressOfNames[0] → "Demo"，AddressOfNameOrdinals[0] = 1，AddressOfFunctions[1] = 0x5678，则 Demo 的 EAT 下标为 1、导出序号为 1 + 1 = 2、函数 RVA 为 0x5678。

易错点

| 误区 | 正解 | |---|---| | DataDirectory[0] 就是完整导出表 | 它只是含 RVA 和 Size 的入口，先定位再读 IMAGE_EXPORT_DIRECTORY | | AddressOfNameOrdinals[i] 是最终导出序号 | 它是 EAT 下标，最终序号是 Base + 下标 | | DataDirectory.Size 可作函数循环次数 | 它是字节范围，循环上限应为 NumberOfFunctions | | EAT 项一定是函数代码 RVA | 也可能是数据导出、0 空洞或转发字符串 RVA |

函数转发与手工 MyGetProcAddress

函数转发（Forwarded Export）指 EAT 项不直接指向本模块代码，而是指向导出目录中的字符串：


库名.函数名   例如 user32.MessageBoxA
库名.#序号    例如 kernel32.#388

判断条件（半开区间）：


ExportRVA <= FunctionRVA < ExportRVA + ExportSize

普通导出时 真实函数 VA = 模块基址 + 函数 RVA；转发导出时该位置是字符串，不能当函数调用，必须：读转发字符串 → 拆成目标 DLL + 目标名称/序号 → 加载目标 DLL → 在目标 DLL 中重复导出解析，直到得到普通函数 RVA。

return MyGetProcAddress(hDll, FuncName); 属于递归——函数尚未返回时又调用自身；运行效果就是换目标 DLL 和名称后重新执行一遍解析流程。终止条件是遇到普通函数 RVA：return (FARPROC)((char*)hModule + Rva);

调用栈示例：


第1层：MyGetProcAddress(MyDll, "MsgBox")  发现 "user32.MessageBoxA"
第2层：MyGetProcAddress(user32, "MessageBoxA")  找到普通代码 RVA，返回真实地址
第1层：直接把第2层结果返回给原调用者

解析步骤

验证 PE 头（'ZM' 是小端下 MZ 的整数写法，0x00004550 对应 PE\0\0）：


IMAGE_DOS_HEADER* DosHeader = (IMAGE_DOS_HEADER*)hModule;
if (DosHeader->e_magic != 'ZM') {
    return NULL;
}
IMAGE_NT_HEADERS* NtHeader =
    (IMAGE_NT_HEADERS*)((char*)hModule + DosHeader->e_lfanew);
if (NtHeader->Signature != 0x00004550) {
    return NULL;
}

定位导出表和三张表（前提是 hModule 指向已加载模块）：


IMAGE_DATA_DIRECTORY* Directory =
    &NtHeader->OptionalHeader.DataDirectory[IMAGE_DIRECTORY_ENTRY_EXPORT];
IMAGE_EXPORT_DIRECTORY* ExportTable =
    (IMAGE_EXPORT_DIRECTORY*)((char*)hModule + Directory->VirtualAddress);
DWORD* AddressOfFunctions = (DWORD*)((char*)hModule + ExportTable->AddressOfFunctions);
DWORD* AddressOfNames     = (DWORD*)((char*)hModule + ExportTable->AddressOfNames);
WORD*  AddressOfNameOrdinals = (WORD*)((char*)hModule + ExportTable->AddressOfNameOrdinals);

按序号查询（HIWORD(lpProcName) == 0 表示低 16 位携带序号）：


DWORD index = LOWORD(lpProcName) - ExportTable->Base;
if (index >= ExportTable->NumberOfFunctions) {
    return NULL;
}
return (FARPROC)((char*)hModule + AddressOfFunctions[index]);

按名称查询并处理转发：


for (DWORD i = 0; i < ExportTable->NumberOfNames; ++i) {
    const char* currentName = (char*)hModule + AddressOfNames[i];
    if (strcmp(currentName, lpProcName) != 0) {
        continue;
    }
    DWORD eatIndex = AddressOfNameOrdinals[i];
    DWORD functionRva = AddressOfFunctions[eatIndex];
    if (functionRva >= Directory->VirtualAddress &&
        functionRva < Directory->VirtualAddress + Directory->Size) {
        // 读取 "DLL.Function" 或 "DLL.#Ordinal"，加载目标 DLL 并递归解析
    } else {
        return (FARPROC)((char*)hModule + functionRva);
    }
}

转发字符串中 . 之后以 # 开头则按序号再次查询，否则按函数名再次查询：


if (*FuncName == '#') {
    DWORD order = strtoul(FuncName + 1, NULL, 10);
    return MyGetProcAddress(hDll, (LPCSTR)order);
}
return MyGetProcAddress(hDll, FuncName);

课堂代码的边界问题

1. LoadLibraryA 只负责获得目标模块，不能把转发字符串自动变成函数指针，仍需继续解析导出表。 2. 范围判断应用半开区间：课堂代码写 Rva <= ExportRVA + Size，严谨写法是 < ExportRVA + Size，末端地址不属于范围。 3. 课堂代码按序号分支没有处理转发：若按序号查到的 EAT 项指向转发字符串，直接返回 hModule + RVA 会把字符串地址当函数地址。完整实现应让两个分支最终进入统一的"普通 RVA / 转发 RVA"判断。 4. 转发链可能不止一层，甚至出现循环转发（A.Func → B.Func → A.Func）：防御性实现应考虑最大深度或已访问集合，课堂代码未实现。 5. 若最终仍调用系统 GetProcAddress，系统会处理许多兼容细节；课堂用递归 MyGetProcAddress 是为了演示自己完成解析。

HideApiCall 与 EAT Hook

课堂函数 HideApiCall() 的实质不是"让 API 从系统消失"，而是在当前进程内修改 USER32!MessageBoxA 的 EAT 项，使之后通过导出表解析得到的地址变成自定义 Show——这是 EAT Hook（修改提供方模块的 Export Address Table）。

| 项目 | EAT Hook | IAT Hook | |---|---|---| | 修改位置 | 导出模块的 EAT | 某个调用模块的 IAT | | 主要影响 | 后续按导出表解析的结果（如 GetProcAddress 查询） | 已通过该 IAT 槽调用的路径 | | 已保存的函数指针 | 通常不会自动改变 | 若调用走被改 IAT，则受影响 | | 作用范围 | 当前进程中该映像视图的解析路径 | 通常限于被修改的导入模块/槽位 | | 检测思路 | 内存 EAT 与可信 EAT 对比 | IAT 目标与预期模块/导出对比 |

EAT 保存 RVA，要让 GetProcAddress(user32, "MessageBoxA") 返回 Show，写入值为 Show 的 VA - user32 模块基址；解析时 基址 + (Show VA - 基址) = Show VA。VirtualProtect 暂时让 EAT 页可写，改完恢复原保护；g_OldRva 保存原值供 UnHideApiCall() 恢复现场。

核心流程：


HMODULE hModule = LoadLibraryA("USER32");
// 解析 user32 导出表，遍历名称表找到 "MessageBoxA"
DWORD* eatEntry = &AddressOfFunctions[AddressOfNameOrdinals[i]];

DWORD oldProtect = 0;
VirtualProtect(eatEntry, 0x1000, PAGE_READWRITE, &oldProtect);
g_OldRva = *eatEntry;
*eatEntry = (DWORD)Show - (DWORD)hModule;
VirtualProtect(eatEntry, 0x1000, oldProtect, &oldProtect);

注意：课堂代码中该指针变量名叫 Rva，它实际是"EAT 项在内存中的地址"（DWORD*），*Rva 才是 EAT 中保存的函数 RVA，命名容易误导。

恢复现场：


VirtualProtect(eatEntry, 0x1000, PAGE_READWRITE, &oldProtect);
*eatEntry = g_OldRva;
VirtualProtect(eatEntry, 0x1000, oldProtect, &oldProtect);

课堂 Show 原为 void __stdcall Show(int,int,int,int)，为匹配调用者声明的 int (__stdcall*)(int,int,int,int)，应改为返回 int 并 return 0。

IAT 反查

"已知函数地址，反向查找所属模块及函数名称"：


IAT 中的运行时地址 → 找地址落在哪个已加载模块 → 解析该模块导出表
→ 与普通导出函数地址匹配 → 得到候选模块名/函数名

函数转发、多个导出名称共享地址、Hook、导出变量、"地址落在函数中间而非入口"都会造成歧义。防守分析时应同时保留：原始导入名称（若还存在）、转发链、最终实现模块与地址。

易错点

| 说法 | 条件与修正 | |---|---| | HideApiCall 会隐藏所有 MessageBoxA 调用 | 不会。不改已填好的 IAT 或已保存的函数指针，只影响之后按 EAT 解析的路径 | | 它修改了系统磁盘 DLL | 课堂代码改的是当前进程内存映像，不改磁盘文件，其他进程不受影响 | | EAT Hook 等于 IAT Hook | 修改对象、作用范围和观察时机都不同 | | 返回地址在模块外就一定恶意 | 合法函数转发最终会落到其他模块，必须先识别转发链 | | 返回地址在模块内就一定正常 | 攻击者可能指向模块内部跳板或代码洞，简单范围检查会漏报 | | 导出表一定比导入表可靠 | 导入描述符可被擦除伪造，EAT 也可被改，二者都不是绝对可信，应建独立基线 |

分层检测思路


第 1 层：地址范围检查（返回地址是否落在预期模块）→ 发现明显重定向
第 2 层：内存 EAT 与可信 EAT 逐项比较 → 发现模块内部跳板型 EAT 修改
第 3 层：函数入口代码/最终控制流检查 → 发现 EAT 未改但入口被改的 Inline Hook

ASLR 通常不妨碍比较 EAT 原始 RVA，但转发项必须单独识别；热补丁、合法安全产品 Hook、磁盘文件是否可信都可能影响结论。

磁盘 PE 与内存映像的地址边界

| 地址 | 含义 | 使用场景 | |---|---|---| | RVA | 相对映像基址的偏移 | 数据目录、EAT、名称表、序号表中的地址 | | VA | 进程虚拟地址 | 已加载模块中访问结构和函数 | | FOA | 文件中的偏移 | 从磁盘文件字节中读取结构 |


VA  = 实际模块基址 + RVA
FOA = Section.PointerToRawData + (RVA - Section.VirtualAddress)
若 RVA < SizeOfHeaders，则 FOA = RVA

MyGetProcAddress 接收 HMODULE（已被加载器按内存布局映射），可直接 hModule + RVA；Qt 工具读的是 QByteArray m_fileData（磁盘原始布局），不能把 RVA 直接当下标，也不能用首选 ImageBase + RVA 构造可解引用指针——必须先转 FOA。

数值示例（示意）：导出目录 RVA 0x3000、Size 0x0200，.edata 节 VirtualAddress = 0x3000、PointerToRawData = 0x0A00，则导出表 FOA = 0x0A00 + (0x3000 - 0x3000) = 0x0A00，用 m_fileData.constData() + 0x0A00 读取。首选 ImageBase = 0x00400000 时首选 VA 为 0x00403000，但受 ASLR 影响，磁盘工具算出的首选 VA 不一定是实际运行时 VA。

转换函数核心思路：


if (rva < m_ntHander.OptionalHeader.SizeOfHeaders) {
    foa = rva;
    return true;
}
for (const auto& section : m_sections) {
    if (rva >= section.VirtualAddress &&
        rva < section.VirtualAddress + section.SizeOfRawData) {
        foa = section.PointerToRawData + (rva - section.VirtualAddress);
        return true;
    }
}
return false;

易错点

1. 字段名叫 VirtualAddress 不等于绝对 VA，数据目录中它保存 RVA。 2. ImageBase + RVA 只得到 VA，不得到文件指针；文件解析必须先得 FOA。 3. RvaToFov 中的 Fov 是项目命名，概念上指 FOA，建议统一命名。 4. 文件型解析节范围看 SizeOfRawData（文件中真实可读字节数），不能拿对齐值当文件长度。 5. 函数 RVA 不一定可转换为代码 FOA：转发导出指向字符串、0 是空洞、导出数据可能在非代码节。 6. RvaToFov 原为 void 时转换失败会留下旧值，用于导出解析前应改成 bool 并在失败时停止。

导出表解析流程与实测示例

解析顺序：


DataDirectory[0]
→ IMAGE_EXPORT_DIRECTORY
→ EAT（按 NumberOfFunctions 建全部结果）
→ Names + NameOrdinals（回填名称和名称 RVA）
→ 判断转发器

必须先遍历 EAT：NumberOfFunctions 决定完整 EAT 长度，名称表只覆盖部分导出；纯序号导出没有名称，但仍有 EAT 下标和导出序号。NameOrdinals 是 WORD，表示 EAT 下标而非最终序号；EAT target 可能是函数、变量、转发字符串或 0 空槽。

转发判断（AND 条件，缺一不可，不能写成 OR）：


functionRva != 0
&& functionRva >= ExportRVA
&& functionRva < ExportRVA + ExportSize

结果结构体：


struct ExportFunctionInfo
{
    DWORD eatIndex;
    DWORD eatEntryFoa;
    DWORD ordinal;
    DWORD functionRva;
    DWORD nameRva;
    QString name;
    QString forwarder;
};

读取字符串用 fileData.constData() + nameFoa，不能把 nameFoa 整数强转成 char*；nameRva 保存 Names 表中的原始 RVA，不保存转换后的 FOA。前端 EAT 下标和导出序号用十进制（QString::number），EAT 项 FOA、函数 RVA、名称 RVA 用十六进制。

注意：NameOrdinals 必须按 WORD 读取；QString 空值用空对象初始化，不要用整数 0；QVector 必须 resize 或 append 后才能按下标写入。

实测数据（样例 DLL，导出目录起点 FOA 0x41A0）：

| 字段 | FOA | 值 | |---|---:|---:| | Characteristics | 0x41A0 | 0 | | TimeDateStamp | 0x41A4 | 0x6A697AE9 | | MajorVersion | 0x41A8 | 0 | | MinorVersion | 0x41AA | 0 | | Name | 0x41AC | 0x57F8 | | Base | 0x41B0 | 0x3E8 | | NumberOfFunctions | 0x41B4 | 6 | | NumberOfNames | 0x41B8 | 4 | | AddressOfFunctions | 0x41BC | 0x57C8 | | AddressOfNames | 0x41C0 | 0x57E0 | | AddressOfNameOrdinals | 0x41C4 | 0x57F0 |

EAT 解析结果（Base = 0x3E8 = 1000）：

| EAT 下标 | EAT 项 FOA | 导出序号 | target RVA | 名称 RVA | 名称 | 转发器 | |---:|---:|---:|---:|---:|---|---| | 0 | 0x41C8 | 1000 | 0x1000 | 0x5836 | MyAdd | 空 | | 1 | 0x41CC | 1001 | 0x1011 | 无 | 空 | 空 | | 2 | 0x41D0 | 1002 | 0x6030 | 0x583C | g_num | 空 | | 3 | 0x41D4 | 1003 | 0x5823 | 0x581C | MsgBox | user32.MessageBoxA | | 4 | 0x41D8 | 1004 | 0 | 无 | 空 | 空 | | 5 | 0x41DC | 1005 | 0x580E | 0x5802 | ExitProcess | kernel32.#388 |

g_num 是导出变量；MsgBox 和 ExitProcess 是转发导出；EAT 下标 1 是仅序号导出，下标 4 是空槽。
