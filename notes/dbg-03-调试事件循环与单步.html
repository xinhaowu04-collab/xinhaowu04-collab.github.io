调试事件循环与单步

调试事件循环

用户态调试器的核心不是主动控制目标程序，而是反复接收调试事件：


WaitForDebugEvent
        ↓
根据 dwDebugEventCode 分发事件
        ↓
处理异常、线程、进程、DLL等事件
        ↓
ContinueDebugEvent
        ↓
等待下一个事件

异常事件主要通过 ExceptionCode 区分：

| ExceptionCode | 来源 | |---------------|------| | EXCEPTION_BREAKPOINT | 软件断点 INT3 | | EXCEPTION_SINGLE_STEP | TF 单步或硬件断点 | | EXCEPTION_ACCESS_VIOLATION | PAGE_NOACCESS 内存断点 |

DEBUG_EVENT.u 是联合体，只有当前事件类型对应的成员有效（CREATE_THREAD_DEBUG_EVENT 时 u.CreateThread 有效，EXCEPTION_DEBUG_EVENT 时 u.Exception 有效）。因此线程创建事件中的 TEB 地址必须当场保存，不能等断点异常发生后再从 u.CreateThread 读取。

T 单步步入与 P 单步步过

T：Trap Flag

设置 EFLAGS 的 TF（位 8）：


or [esi].regFlag, 100h

目标线程执行一条指令后，CPU 产生 EXCEPTION_SINGLE_STEP。T 的行为：普通指令执行一条后停止；call 指令进入被调用函数后停止。

P：遇到 call 时步过

单步步入（T 命令）会进入 call 内部，单步步过（P 命令）跨过 call，在 call 返回后停下。实现 DbgSetNext：先读取 EIP 处的机器码并反汇编当前指令：


DbgGetRegs → 获取当前 EIP
DbgReadProcessMemory(EIP, 16字节) → 读取当前指令
Decode2Asm → 反汇编，得到指令文本和长度

如果当前是 call：
    下一条地址 = EIP + 当前指令长度
    在下一条地址设置一次性软件断点（Type=0）
否则：
    设置 TF，执行一条普通指令

例如：


0040100E call 0040101A
00401013 push 00

在 0040100E 执行 P 时，临时断点设置在 00401013。被调用函数执行完毕后 ret 返回并命中该断点。一次性断点命中后不需要重新写入。

单步异常的状态分流

EXCEPTION_SINGLE_STEP 可能来自多种功能：用户执行 T/P、永久 BP 执行原指令后等待重新插入、BM 暂时恢复页面后等待重新保护、硬件断点 DR0～DR3、指令跟踪。因此 ExecStep 必须按状态变量和 DR6 判断异常来源，不能把所有单步异常都当作普通 T。

ExecStep 里通过两个标志位区分单步来源：

| 标志位 | 含义 | |--------|------| | g_IsBreakStep = TRUE | int3 永久断点恢复后单步，单步后重新写入 0xCC | | g_IsMemStep = TRUE | 内存断点恢复后单步，单步后重新设 PAGE_NOACCESS | | 两者都为 FALSE | 用户手动单步（T 命令），显示寄存器等命令 |

D 查看内存

命令格式：d 401000 20。当前参数转换函数按十六进制解析，因此 20 表示 20h，即 32 字节。

读取流程：把地址字符串和长度字符串用空格切开 → 分别使用 htodw 转换为数值 → 限制读取长度不超过本地缓冲区 → 调用 DbgReadProcessMemory → 每 16 字节显示一行。

本地缓冲区与取字节：


LOCAL Buffer[256]:BYTE
...
mov ecx, i
movzx eax, byte ptr Buffer[ecx]

显示格式：


szFmtDumpAddr db "%08X  ",0
szFmtDumpByte db "%02X ",0

验证输出：


00401000  6A 00 68 06 30 40 00 68 00 30 40 00 6A 00 E8 07
00401010  00 00 00 6A 00 E8 06 00 00 00 FF 25 08 20 40 00

注意：MASM 不能直接比较两个内存变量，.while i < Bytes 要先把一方取到寄存器：


.while TRUE
    mov eax, i
    .if eax >= Bytes
        .break
    .endif
    ; ...
.endw

wsprintf、StdOut 等调用可能破坏易失寄存器，跨函数调用的循环状态最好放在局部变量中。

LM 查看模块列表

通过 ToolHelp 快照枚举目标进程模块：CreateToolhelp32Snapshot → Module32FirstW → Module32NextW → CloseHandle。必须先设置：


mov Module.dwSize, SIZEOF MODULEENTRY32W

旧版 MASM32 的兼容问题

当前环境是 ASCII build，旧版 kernel32.lib 中没有 ANSI 的 Module32First/Module32Next 导入符号，但存在 W 版本，因此改用 Module32FirstW/Module32NextW。

旧 windows.inc 只有 ANSI 的 MODULEENTRY32，需要补宽字符结构，其中两个字符串字段必须是 WORD 数组：


szModule  WORD MAX_MODULE_NAME32+1 dup(?)
szExePath WORD MAX_PATH dup(?)

格式字符串使用 %ws，结构体字符串字段传地址（addr Module.szModule、addr Module.szExePath）。

已验证：LM 能显示主程序与已加载 DLL 的基址、映像大小、模块名和完整路径。

R 查看寄存器与 LastError

不能直接在调试器中调用 GetLastError，否则得到的是调试器线程自己的 LastError。32 位目标线程的 LastErrorValue 位于 TEB + 34h。

保存线程与 TEB 的对应关系：

| 事件 | 保存内容 | |------|----------| | CREATE_PROCESS_DEBUG_EVENT | 主线程 ID 与 CreateProcessInfo.lpThreadLocalBase | | CREATE_THREAD_DEBUG_EVENT | 新线程 ID 与 CreateThread.lpThreadLocalBase |

执行 R 时：当前 g_DbgEvent.dwThreadId → 查找对应线程记录 → 得到 TEB → 读取 TEB + 34h 的 DWORD。

已验证输出 LastError=000036B7，证明读取链路已经通畅。

指令跟踪与 WinDbg wt

连续单步与真正 wt 的区别

基础连续跟踪：设置 TF → 执行一条 → 输出 EIP 和反汇编 → 再次设置 TF。

真正接近 WinDbg wt 的功能还需要：确定跟踪结束位置、识别 call/ret、维护调用深度、生成缩进调用树、统计指令数和函数调用数。

call 指令与函数入口


0040100E call 0040101A
00401013 push 00
0040101A jmp [00402008]

执行 call 时把 00401013 压入栈并跳转到 0040101A。在被调用函数入口：EIP = 0040101A，[ESP] = 00401013。

从函数入口执行 wt 时，可以读取 [ESP] 作为当前函数的返回地址；从 call 指令处开始时，返回地址可由 EIP + 指令长度得到。

函数入口无法仅靠固定序言可靠识别

push ebp / mov ebp, esp / sub esp, xx 只是常见特征：优化后的函数可能没有标准序言，call 目标也可能只是导入跳板。可靠的函数边界通常来自 PDB 符号或其他函数元数据。

分阶段实现


第一阶段：连续 TF + 指令日志
第二阶段：跟踪到起始函数返回地址
第三阶段：call/ret 深度和调用树
第四阶段：模块过滤、异常终止和统计
