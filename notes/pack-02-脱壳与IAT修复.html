脱壳与 IAT 修复

脱壳的课堂主线是找到原程序入口点 OEP，并在原程序已经恢复到内存后进行 Dump；要得到能够独立运行的 PE，通常还需继续修复 PE 结构、导入表、重定位、资源或 TLS。本笔记只用于自有程序、课堂样本和明确授权的 PE32/x86 实验环境。

AEP、OEP 与地址体系

| 概念 | 含义 | 本次实验中的例子 | |---|---|---| | ImageBase | PE 希望或实际装载的模块基址；必须区分文件首选基址与进程实际基址 | 文件字段曾看到 0x00400000，Scylla 所附加进程曾实际位于 0x00030000 | | AddressOfEntryPoint / 入口 RVA | 可选头中记录的入口相对地址 | 原程序入口 RVA 为 0x1479 | | AEP | 当前磁盘 PE 的入口。加壳文件的 AEP 通常先进入壳 | PE-bear 的 UPX 文件显示入口位于 UPX1，工具中显示 EP = 1420 | | OEP | Original Entry Point，原程序入口 | 实际基址为 0x30000 时，OEP VA 为 0x31479 | | RVA | 相对于模块基址的地址 | OEP RVA = 0x1479，IAT RVA = 0x2000 | | VA | 进程中的虚拟地址 | VA = 实际模块基址 + RVA | | FOA | 文件中的偏移 | 文件解析时通过节表把 RVA 转成 FOA；不能直接用 ImageBase + RVA 索引文件字节 |

两个实际基址场景：


场景 A：进程实际基址 = 00030000
OEP VA = 00030000 + 00001479 = 00031479
IAT VA = 00030000 + 00002000 = 00032000

场景 B：关闭 ASLR 后按首选基址 00400000 装载
OEP VA = 00400000 + 00001479 = 00401479
IAT VA = 00400000 + 00002000 = 00402000

壳先让壳代码获得控制权，负责解压/解密原代码、加载依赖、修复 IAT、恢复寄存器和栈环境，最后才把控制流交给 OEP，因此壳的 AEP 和原程序 OEP 不是同一个入口：


Windows Loader 按加壳 PE 的 AEP 启动
  → 壳保存现场
  → 解压或解密原映像
  → 修复导入、重定位、内存属性等
  → 恢复寄存器和栈
  → 壳尾跳转
  → OEP：原程序入口
  → Dump 后继续修复 PE 结构

完整脱壳检查链：


找到 OEP
  → 在正确时机 Dump 内存
  → 修正入口 RVA
  → 重建导入表
  → 检查 ImageBase/ASLR/重定位
  → 检查节、资源、TLS 等
  → 从新进程验证能否独立运行

地址换算：


VA  = ActualImageBase + RVA
RVA = VA - ActualImageBase
FOA = PointerToRawData + (RVA - Section.VirtualAddress)

注意：

  • "找 OEP＋Dump"是核心起点，不等于得到可运行文件。本次先经历了 ?.DLL 导入错误，之后又经历了重定位/ASLR 崩溃。
  • AddressOfEntryPoint 是 RVA，不是 VA。Scylla 的 OEP 输入框本次用的是进程 VA；PE 可选头中写的是入口 RVA。
  • 文件中的 ImageBase=0x400000 与 Scylla 显示的实际基址 0x30000 可以同时为真：前者是文件首选基址，后者是当次进程的实际装载基址。对话早期曾把 0x30000 概括成"该文件 ImageBase"，后来查看字段发现当前文件为 0x400000；应按文件和进程分别确认，不能把一次运行的实际基址永久当作所有文件的首选基址。
  • "入口特征法"没有给出某个编译器的固定入口模板。当前只确认：跳转目标应位于原程序代码区、反汇编合理、控制流能够继续；具体入口特征待确认，不能凭一个常见函数序言认定 OEP。

实验观察：当前查看的 PE 字段显示 ImageBase = 400000h（文件偏移 12Ch，DWORD），小端序保存为 00 00 40 00；另一次观察到 00 00 03 00 → 0x00030000。两组字节很可能来自不同阶段的文件或不同观察对象，具体文件名当时没有再次确认，标记为对象待确认。

ESP 定律与 OEP 定位

"ESP 定律"不是 CPU 手册中的正式定律，而是脱壳中的经验方法：很多壳在入口保存原程序寄存器现场，在跳转 OEP 前恢复现场；对保存现场所在的栈内存下硬件访问断点，可以较快断在恢复现场附近。

典型壳结构：


pushad
call    UnpackOrDecrypt
; 修复环境
popad
jmp     OEP

PUSHAD 在 x86 中压入 8 个 32 位值，共占 8 × 4 = 32 = 20h 字节。例如 PUSHAD 前 ESP = 0019FF70，PUSHAD 后 ESP = 0019FF50，从新 ESP 开始的布局：

| 栈位置 | 保存内容 | |---|---| | [ESP] | EDI | | [ESP+4] | ESI | | [ESP+8] | EBP | | [ESP+0C] | PUSHAD 前的 ESP（POPAD 跳过该槽） | | [ESP+10] | EBX | | [ESP+14] | EDX | | [ESP+18] | ECX | | [ESP+1C] | EAX |

后面的 POPAD 必须读取这些栈内存，所以监视 [ESP] 所在地址可以在恢复现场时触发。

课堂操作（x32dbg/OllyDbg）：

1. 到壳入口附近，单步执行完 PUSHAD。 2. 记录此时 ESP，例如 ESP=0019FF50。 3. 在栈窗口选中地址 0019FF50。 4. 设置"硬件断点 → 访问 → DWORD"。 5. 按 F9 运行。 6. 命中后观察是否位于 POPAD、多个 POP 或其他恢复现场代码附近。 7. 继续单步，寻找从壳代码区转入原程序代码区的 JMP、PUSH OEP / RET 等控制转移。

关键区别：ESP = 0019FF50 是地址值，[ESP] 是该地址中保存的 DWORD。硬件访问断点监视的是 [ESP] 这块内存，不是把 0019FF50 当作代码执行地址下断点。

注意：

  • ESP 定律不是"只要看 ESP 就能直接得到 OEP"，它只是把分析者带到壳尾附近。
  • 断点触发只证明那块栈内存被访问，可能命中 POPAD、POP、MOV reg,[ESP] 或壳的临时访问。
  • 壳可以不使用 PUSHAD/POPAD、多次保存现场、分批恢复、切换栈或提前复用栈区，可能要在不同栈位置多次尝试。
  • 恢复现场后的跳转目标是 OEP 候选，还需确认它是否进入原程序代码区以及反汇编是否正常。

本次样本出现了非常典型的壳尾：


000371CE  61              popad
000371CF  8D4424 80       lea eax,dword ptr [esp-80]
000371D3  6A 00           push 0
000371D5  39C4            cmp esp,eax
000371D7  75 FA           jne 000371D3
000371D9  83EC 80         sub esp,FFFFFF80
000371DC  E9 98A2FFFF     jmp 00031479

逐步解释：


POPAD：恢复保存的通用寄存器
LEA EAX,[ESP-80h]：计算清零结束位置
PUSH 0 循环：每次 ESP-=4，共执行 80h/4=32 次，清零 0x80 字节栈空间
SUB ESP,FFFFFF80h：FFFFFF80h 是 -80h，因此等价于 ADD ESP,80h
JMP 31479：从壳尾跳入原程序入口

在该次进程实际基址 0x30000 下：OEP VA = 00031479，OEP RVA = 00031479 - 00030000 = 00001479。

API 断点辅助找 OEP

API 断点法是根据"壳会调用哪些 API"或"原程序启动后会调用哪些 API"设置断点，再利用 API 的返回地址判断调用者位于壳区还是原程序区。

在 32 位调用中，刚进入 API 时通常有：


[ESP]   = API 返回地址
[ESP+4] = 第一个参数
[ESP+8] = 第二个参数

API 命中本身不是 OEP；真正有价值的是 [ESP] 中的调用者返回位置。

按壳行为猜测：

| API | 可能用途 | |---|---| | VirtualAlloc | 为解压数据或临时代码申请空间 | | VirtualProtect | 修改解压后页面权限 | | LoadLibraryA/W | 加载原程序依赖 DLL | | GetProcAddress | 解析原程序使用的 API 地址 |

按原程序功能猜测：

| 程序现象 | 可尝试的 API | |---|---| | 弹消息框 | MessageBoxA/W | | 创建窗口 | CreateWindowExA/W | | 创建对话框 | DialogBoxParamA/W | | 查询模块 | GetModuleHandleA/W | | 获取命令行 | GetCommandLineA/W | | 控制台/文件输出 | WriteConsoleA/W、WriteFile | | 打开文件 | CreateFileA/W | | 网络初始化/连接 | WSAStartup、connect |

命中后查看返回地址：落在壳区则仍是壳调用；落在原 .text 区则原程序很可能已经开始执行。

注意：

  • API 地址不是 OEP；API 断点只是把分析带到 OEP 之后的原程序代码附近，或带到壳修复环境的位置。
  • GetProcAddress 可能连续命中很多次，因为壳正在批量修复导入，并不意味着每次都接近 OEP。
  • 壳可以自己遍历 DLL 导出表、按 HASH 解析函数、调用更底层接口或故意制造大量 API 调用，从而削弱 API 断点的效果。
  • 本次没有记录某个 API 断点命中时的实际 [ESP] 返回地址；老师只提到复杂壳可结合 GetModuleHandle 等 API 辅助定位，具体命中地址待确认。

第二代壳、反调试与 CloseHandle

课堂所说"第二代加密壳"，是在压缩/加密原程序的基础上加入反调试：检测调试器、改变控制流、退出、进入假解密流程或制造假 OEP。

常见检查面：


IsDebuggerPresent
CheckRemoteDebuggerPresent
NtQueryInformationProcess
PEB.BeingDebugged
PEB.NtGlobalFlag
软件断点字节 CC
硬件断点寄存器 DR0～DR3/DR7
EFLAGS.TF 与单步行为
时间差检测
异常分发差异

第一层保护让磁盘上的原代码不可直接阅读；第二层再干扰"调试壳 → 观察解密 → 观察恢复现场 → 看到跳转 → 找到 OEP"这条链。

CloseHandle 本身只是关闭句柄。反调试利用的是故意传入无效句柄、伪句柄或重复关闭句柄后产生的异常差异，相关异常通常为 STATUS_INVALID_HANDLE = C0000008。在调试器下，异常会先作为第一次机会异常交给调试器，再决定是否交还给程序自己的 SEH；壳可根据异常是否到达预期处理器来改变流程。

课堂检测思路：


__try {
    CloseHandle((HANDLE)1234); // 故意传非法句柄
}
__except (1) {
    ExitProcess(0);
}

在 x86 API 入口观察参数：[ESP] = 返回地址，[ESP+4] = hObject。若 hObject 为明显无效值，且调用周围存在 SEH/退出逻辑，才形成反调试证据链。

OEP 软件断点检查思路：


BYTE* pCode = ImageBase + AddressOfEntryPoint;
if (*pCode == 0xCC) {
    ExitProcess(0);
}

绕过思路包括在授权实验中 Hook 更底层的 NtClose，只过滤壳故意制造的无效句柄调用；OllyDbg/x32dbg 的反反调试插件则集中处理多种常见检测。

注意：

  • "第一代/第二代"是课程便于理解的分类，不是 Windows 或 PE 的正式代际标准。
  • 正常调用 CloseHandle(有效句柄) 没有反调试意义；"非法句柄＋异常控制流"才构成检测。
  • 不能简单把所有 NtClose/CloseHandle 调用强制改成成功，否则会破坏程序正常资源管理。
  • 软件断点把首字节改成 CC，所以字节校验可发现软件断点；硬件执行断点不修改代码字节，但壳还可能检查调试寄存器。
  • 看到 INT3 不等于看到反调试。编译器也会用 CC 作为函数间填充、不可达路径保护或调试陷阱。
  • 老师源码中的两段 AntiDebug 代码均被注释；按给出的源码直接编译时，这两项检测没有启用。
  • 对话讨论过 x32dbg 出现第一次机会 C0000008 的可能性，但没有该样本实际命中的日志，是否真的执行 CloseHandle 反调试待确认。
  • 反调试与反反调试是持续对抗：壳增加新检查，插件也需要更新策略；插件成功注入本身不等于已经绕过所有检查。

反内存 Dump、反 IAT 修复与偷代码

反内存 Dump 的目标通常不是绝对阻止读取，而是让某一时刻导出的内存不完整、不同步或无法重建成可运行 PE。反 IAT 修复则破坏"连续、稳定、明文、标准的 IAT"这一自动工具假设。

CPU 执行代码时，相关页最终必须在某个时刻以可执行形式存在；调用外部 API 时，控制流最终也必须到达真实 API 地址。因此用户态保护通常只能显著增加抓取和重建成本，不能从原理上让明文和真实调用目标永远不存在。

反 Dump 思路：

| 思路 | 效果 | 局限 | |---|---|---| | 按函数/按页临时解密，执行后重加密 | 任意时刻只有部分明文 | 执行窗口仍可被观察 | | PAGE_NOACCESS、PAGE_GUARD、动态切换权限 | 干扰扫描并感知访问 | 程序自己执行前也必须恢复权限；PAGE_GUARD 是一次性告警 | | 擦除或伪造 PE 头 | 工具难以确定模块、节和目录 | 代码仍存在，可人工重建头 | | 不保留稳定标准 IAT | Dump 后仍无法直接运行 | API 调用瞬间仍需得到目标 | | 把代码分散到多个私有内存区 | 只 Dump 主模块会漏数据 | 需要枚举并拼接多个区域 | | 限制进程句柄/读取权限 | 阻挡普通低权限读取 | 高权限、调试权限或内核工具仍可能读取 | | 自己生成 MiniDump 时过滤内存 | 控制自身崩溃转储内容 | 不能阻止其他有权限的读取工具 |

反 IAT 修复思路：


擦除 DLL/API 名称和导入描述符
把 IAT 打散到多个区域
调用前临时解析、调用后清除
保存编码后的函数地址
IAT → 本地跳板 → 真实 API
所有 API 进入统一调度器
自行遍历 DLL 导出表或按 HASH 解析
填入假 API、重复项、垃圾项干扰范围识别

"偷代码"则把 OEP 开头的关键指令移到壳中执行，随后跳到 OEP+N。分析者即使找到壳尾跳转，也可能缺少原入口的前几条初始化指令，需要把被偷指令恢复到可执行文件中。

注意：

  • 擦除字符串不能阻止所有工具。工具仍可用"IAT 目标 VA → 所属 DLL → EAT 导出"反查 API。
  • IAT 指向 EXE 自身地址不一定就是加密：也可能是回调、普通函数指针、IAT Hook、跳板或搜索越界后的相邻数据。
  • "IAT 加密"在课堂中可能泛指地址编码、跳板、动态解析或自定义指针表，不一定是把标准 IAT 整体当作一段密文。
  • 偷代码不是让调试器"看不见任何入口"，而是让真正的原始入口指令不再完整地位于原 OEP。
  • 完整修复的目标不必还原出与原文件字节完全相同的导入表；只要重建合法导入结构并让调用点使用它，文件也可能恢复运行。
  • 本次没有提供按页解密、PAGE_GUARD 命中或偷代码样本的实际地址；这些属于课堂原理，具体样本结果待确认。

UPX 样本与壳的最小导入表

PE-bear 打开磁盘上的 crackme1_pack.exe 时看到 UPX0、UPX1、.rsrc 三节，表明该样本是 UPX 风格的压缩壳。普通 UPX 主要是压缩壳，不能因为节名是 UPX 就直接称为"加密壳"。磁盘上的导入表主要服务于壳启动，不是 OEP 处原程序已经恢复好的完整导入表。

壳只需保留少量引导 API，就能在运行时加载其他 DLL、解析函数、改变内存属性并把原程序恢复出来。截图中的 KERNEL32.DLL 导入有 LoadLibraryA、ExitProcess、GetProcAddress、VirtualProtect，用途分别是加载依赖、退出、解析 API 和修改页面权限。

磁盘壳 IAT 与运行时原程序 IAT 是两套位置：

| 对象 | 地址范围/示例 | 用途 | |---|---|---| | 壳的磁盘导入 | FirstThunk RVA 827C、8284、828C… | 让 UPX 壳先运行 | | 原程序运行时 IAT | RVA 2000 附近 | OEP 后的原程序调用真实 API |

判断当前工具看到哪一张导入表：

1. PE-bear 直接打开原加壳文件：看到的是磁盘上的壳导入。 2. x32dbg 运行到 OEP：原程序代码和 IAT 已在内存中恢复。 3. Scylla 附加当前进程并扫描 RVA 2000 附近：重建的是原程序导入。 4. 修复后的文件再用 PE-bear 打开：应出现 Scylla 重建的新导入结构。

PE-bear 截图记录：

| DLL | 函数数 | NameRVA | FirstThunk RVA | |---|---:|---:|---:| | api-ms-win-crt-heap-l1-1-0.dll | 1 | 82C0 | 827C | | api-ms-win-crt-locale-l1-1-0.dll | 1 | 82DF | 8284 | | api-ms-win-crt-math-l1-1-0.dll | 1 | 8300 | 828C | | api-ms-win-crt-runtime-l1-1-0.dll | 1 | 831F | 8294 | | api-ms-win-crt-stdio-l1-1-0.dll | 1 | 8341 | 829C | | KERNEL32.DLL | 4 | 8361 | 82A4 | | VCRUNTIME140.dll | 1 | 836E | 82B8 |

截图中这些描述符的 OriginalFirstThunk 均显示为 0。

注意：

  • PE-bear 中壳导入少，不代表原程序只调用这几个 API。
  • PE-bear 中出现多个 api-ms-win-crt-* 名称，而 Scylla 将运行时目标归到 ucrtbase.dll，不一定是错误。API Set 名称可映射到实际承载模块。
  • OriginalFirstThunk=0 表示没有单独 INT 时可回退使用 FirstThunk 中的查找数据；它不是跳转指令，也不是"导入不存在"。
  • 原 UPX 文件中的壳 IAT 不能直接替代原程序完整 IAT。

Scylla 自动搜索缺陷与假 IAT 项

在实际基址 0x30000 的进程中，Scylla 自动搜索得到：


OEP      = 00031479
IAT VA   = 00032000
IAT Size = 000000D8
Imports  = 47
Invalid  = 1

正常识别的三组：


kernel32.dll      (12) FThunk RVA 00002000
vcruntime140.dll   (4) FThunk RVA 00002034
ucrtbase.dll      (30) FThunk RVA 00002048

错误组：


? (1) FThunk RVA 000020D4
rva: 000020D4  ptr: 000318CB

rva:20D4 是 IAT 槽候选的位置，ptr:318CB 是该槽中保存的目标地址：


槽VA = ActualImageBase + RVA = 00030000 + 000020D4 = 000320D4
[000320D4] = 000318CB
目标RVA = 000318CB - 00030000 = 000018CB

目标代码：


000318BE  85C0            test eax,eax
000318C0  75 01           jne 000318C3
000318C2  C3              ret
000318C3  6A 07           push 7
000318C5  E8 39000000     call 00031903
000318CA  CC              int3
000318CB  C2 0000         ret 0
000318CE  E8 2DF7FFFF     call 00031000

如果 CPU 从 0x318CB 进入，只执行 ret 0，不会倒退去执行前一字节 0x318CA 的 INT3。RET 0 弹出返回地址且额外清理 0 字节，效果基本等同普通 RET，只是编码不同。

正确的 IAT 边界计算：


kernel32：12项    2000 ～ 202C，2030 为终止 DWORD
vcruntime：4项    2034 ～ 2040，2044 为终止 DWORD
ucrtbase：30项    2048 ～ 20BC，20C0 为终止 DWORD

总范围：2000 ～ 20C3
Size = 20C4 - 2000 = C4

Scylla 操作：

1. 点击 Clear。 2. 手工输入与本次实际基址对应的值：OEP = 00031479、VA = 00032000、Size = 000000C4。 3. 不再点击 IAT Autosearch，否则它会重新扩展范围。 4. 点击 Get Imports。 5. 验证应为 Imports = 46、Invalid = 0。 6. 点击 Dump 生成新文件。 7. 点击 Fix Dump，选择刚刚生成的新 Dump。 8. 运行新生成的 *_SCY.exe，不要误运行旧版本。

一次重新自动搜索把范围改成 VA = 00031FFC、Size = 000000E4，结果为 46 valid、2 missed、Imports 48、Invalid 2——起点比真实 IAT 早 4 字节，终点又超过 0x320C0 终止项，反而多收了两个无效项。

保留红色 ? 组执行 Fix Dump 后，Windows 报错"由于找不到 ?.DLL，无法继续执行代码"。这证明 Scylla 把未知组真的写成了名为 ?.DLL 的导入描述符，Windows Loader 在进入 OEP 之前就尝试加载它并失败。这一现象不是反调试。

注意：

  • Import Rebuild success 只表示 Scylla 成功写出了重建结构，不保证 OEP、IAT 边界、重定位和最终运行都正确。
  • 0x320D4 → 0x318CB 只证明该 DWORD 指向 EXE 内部的空函数。它可能是普通回调数据、干扰项或搜索越界结果；单凭它不能判定反调试。
  • INT3 与 RET 0 在地址上相邻，不等于执行路径一定是"INT3 后再 RET"。函数边界和实际入口地址比反汇编窗口的连续显示更重要。
  • 验证槽是否被使用，应搜索对 0x320D4 的引用，例如 FF 15 D4 20 03 00（call dword ptr [000320D4]）或 FF 25 D4 20 03 00（jmp dword ptr [000320D4]）。没有引用更支持"相邻普通数据/假项"；有引用则要继续分析调用语义。
  • 删除 Scylla 树中的错误项不会自动修改之前已经生成的 *_SCY.exe，必须重新 Dump/Fix 或至少重新 Fix 新文件。

断点设置异常的诊断边界

分析 0x318CB 期间出现过"部分位置不能下断点，后来所有断点都不能下"的现象。该现象本身不足以证明样本存在反调试。

软件断点通常把目标首字节改成 CC。地址 0x318CA 原本已经是 CC int3，所以在那里再下软件断点不会产生新的字节变化。另一方面，0x318BE 与 0x318CB 仅相距 13 字节，处于同一 4KB 页；如果一个地址能写软件断点、另一个不能，仅凭页面权限解释不充分。

最小诊断顺序：

1. 查看调试状态是 Paused、Running 还是 Terminated。 2. 在当前 EIP 所在指令上测试 F2。 3. 检查是否仍在有效调试会话中，而不是查看已退出进程留下的反汇编。 4. 确认重新打开文件后的实际模块基址；不要继续在旧 VA 上下断点。 5. 尝试硬件执行断点，排除软件断点写入失败或代码自恢复。 6. 查看 x32dbg 日志中的具体错误，而不是只看有没有红点。

注意：

  • "断点没命中"和"断点设置不上"不是一回事。前者可能只是 CPU 从未执行该地址。
  • "断点设置后立即消失"才更像代码被覆盖、自校验恢复字节或壳主动清理；本次没有提供这一现象的日志。
  • 进程已经因 Loader 错误退出时，用户代码尚未执行，OEP 附近所有断点自然不可能命中。
  • 当时没有提供 x32dbg 按 F2 后的具体日志，"所有断点不能下"的最终原因待确认。后来发现修复文件存在 ?.DLL，至少能解释其中一次为何用户代码尚未开始执行。

Dump 重载崩溃、重定位与关闭随机基址

去掉 ?.DLL 后，新 Dump 进入程序但在以下位置崩溃：


001D1843  8B0D 04300300    mov ecx,dword ptr ds:[00033004]

x32dbg 状态：EIP = 001D1843，异常 C0000005 EXCEPTION_ACCESS_VIOLATION，实际模块基址 001D0000。

代码 RVA 仍为 001D1843 - 001D0000 = 00001843，但绝对操作数仍是旧运行基址 0x30000 下的地址：


旧地址 = 00030000 + RVA 3004 = 00033004
新地址 = 001D0000 + RVA 3004 = 001D3004
Delta  = 001D0000 - 00030000 = 001A0000
00033004 + 001A0000 = 001D3004

该绝对操作数未被重定位，访问未映射的 0x33004 导致 C0000005。

指令字节 8B 0D 04 30 03 00 中 DWORD 绝对地址 00033004 的起始位置对应代码 RVA 0x1845，完整重定位表中应有相应的 PE32 IMAGE_REL_BASED_HIGHLOW(3) 项。截图上方的 call dword ptr [0003202C] 同样是旧基址下的 IAT 绝对地址；若模块位于 0x1D0000，应对应 0x1D202C。

课堂最简单方案不是逐条改绝对地址，而是让修复后的 Dump 固定回捕获时的实际基址：


Dump 捕获时实际基址 = 00030000
修复后文件 ImageBase = 00030000
清除 DllCharacteristics 的 Dynamic Base 位 0x0040
入口 RVA 仍为 00001479

若 PE 工具只显示数值，则 新值 = 原 DllCharacteristics & ~0040h。位运算示例：8140h → 8100h、0140h → 0100h；实际值必须以目标文件当前字段为准，不能照抄示例。

另一条路线是在原文件仍以首选基址 0x400000 固定加载后重新完整脱壳：实际基址 00400000、OEP VA 00401479、IAT VA 00402000、IAT Size 000000C4。

两套合法但不能混用的输入：

| 实际基址 | OEP VA | IAT VA | IAT Size | |---:|---:|---:|---:| | 00030000 | 00031479 | 00032000 | 000000C4 | | 00400000 | 00401479 | 00402000 | 000000C4 |

先前成功流程按当时截图更接近第一套：在 0x30000 进程到达 OEP 后 Dump，Scylla 手填 31479/32000/C4，再让最终文件固定在 0x30000。但用户后来查看的当前文件字段为 0x400000，说明复现实验时必须再次确认打开的是原文件还是修复文件。

注意：

  • 关闭 ASLR 解决的是"避免再次换基址"，不是补齐重定位表。完整方案仍是恢复正确的 Base Relocation Table。
  • 不应只把当前一条 [33004] 改成 [1D3004]，因为代码和数据中可能存在许多绝对地址。
  • 如果 Dump 内容是在 0x30000 下完成重定位后捕获，就不能保留文件首选基址 0x400000 却继续使用 0x31479/0x32000 这组 VA；文件头、实际装载基址和 Scylla 输入必须一致。
  • "先用 PE 关随机基址，再手动输入 Dump 地址"的准确说法是：清除 Dynamic Base，然后在 Scylla 手动输入与本次实际基址对应的 OEP VA、IAT VA 和 IAT Size。

课程总结的四层保护框架

其他 AI 将老师课程总结为：压缩壳基础、ESP 定律、第二代反调试、Hook 绕过、IAT 加密、反 Dump、抹除特征和偷代码。主线正确，但作为复习笔记需要补充适用条件。

课程可按四层保护理解：


第一层：隐藏代码
压缩/加密 → 找 OEP → 内存 Dump

第二层：干扰观察
异常检测 → 断点检测 → 反调试 → Hook/插件对抗

第三层：破坏自动修复
IAT 跳板/动态解析 → 抹除名称 → 假 IAT 项

第四层：破坏程序重建
偷 OEP 代码 → 伪造 PE 头/目录 → 资源或重定位缺失

课堂结论的严谨化：

| 课堂表达 | 严谨补充 | |---|---| | 脱壳两步是找 OEP 和 Dump | 之后通常还要修复入口、导入、重定位、节、资源/TLS 并运行验证 | | 自动插件 Dump 后资源丢失是因为从文件读目录 | 这是特定插件/样本现象；还需确认资源数据、.rsrc 映射、目录 RVA/Size 和节大小都存在且一致 | | 第二代壳会反调试 | 这是课堂分类，不是统一行业标准 | | CloseHandle 可反调试 | 必须是非法/伪句柄加异常控制流；正常关闭有效句柄不是反调试 | | OEP 断点检测 | 本质是检查 CC 或做代码完整性校验，只直接覆盖软件断点 | | 抹除字符串可防 IAT 重建 | 只打击依赖字符串的方法；运行时地址仍可结合 DLL EAT 反查 | | 偷代码使调试器找不到入口 | 更准确是 OEP 前几条指令被移走，壳尾可能跳到 OEP+N，需要恢复被偷指令 |

注意：

  • 资源目录只改 DataDirectory[RESOURCE].VirtualAddress/Size 并不总能恢复图标；该实验能成功，说明对应资源数据和节布局仍可用。
  • 壳无法从原理上让 CPU 永远不执行明文，也无法让 API 调用永远没有最终目标；它主要增加自动化分析时间成本。
  • 插件绕过一个检测点不等于绕过所有反调试路径。

课堂曾演示 OllyDbg 自动脱壳插件生成的文件缺少图标/资源，通过手工纠正资源目录地址和大小后恢复图标并运行；具体 RVA、Size 或文件字节未提供，数值待确认。

LZMS 壳与 IAT 跳板加密

老师源码由三个主要部分组成（这是另一份三节实现，与前面的两节 Packer 不同）：

| 模块 | 责任 | |---|---| | CPeParse | 使用 ImageLoad 取得 DOS 头、NT 头、可选头、节表、文件大小和对齐结果 | | CPacker | 压缩整个原 PE、重建外壳文件、写入 PackInfo + 压缩数据 + Stub | | StubCode | 运行时找 API、解压、映射节、修复导入/重定位/权限/TLS，最后跳 OEP |

基础结构与 CPeParse 接口同前（PackInfo 三个 DWORD、GetDosHeader 等一组方法）。该实现首先是使用 Windows Compression API 和 COMPRESS_ALGORITHM_LZMS 的压缩壳；IAT 保护发生在 Stub 解压并恢复原映像之后。

BuildNewPe 建立三个节：

| 节 | Raw 数据 | 内存用途 | |---|---|---| | .old | PointerToRawData=0、SizeOfRawData=0 | 为原程序映像预留虚拟空间 | | .iat | Raw 大小为 0，VirtualSize=0x2000 | 运行时写入每个 API 的 12 字节跳板 | | .pack | 有 Raw 数据 | 保存 PackInfo、压缩数据和 hexData Stub |

外壳构建时 NumberOfRvaAndSizes = 0 并清零整个 DataDirectory，Windows Loader 因此看不到原程序的数据目录；Stub 通过 PEB 和自写导出解析器取得所需 API，再自行恢复原映像。

新 AEP 设置为 NewSections[2].VirtualAddress + sizeof(PackInfo) + m_PackInfo.dwComDataSize，即 .pack 中的 Stub 起点。

运行流程：


MainEntry: PUSHAD
  → Entry / InitEnv
  → 从 PEB 找模块并手工解析导出
  → 加载 Cabinet.dll 与解压 API
  → LZMS 解压完整原 PE 到临时缓冲区
  → FixSections 恢复头和节
  → FixImportTable 生成 .iat 跳板
  → FixRelTable 修复重定位
  → FixMemProto 与 FixTlsCallback
  → 返回 ImageBase + 原入口 RVA
  → 写入保存的 ECX / POPAD / JMP ECX

Stub 保存现场并跳 OEP


pushad
call Entry
xchg [esp+18h],eax
popad
jmp ecx

Entry 返回 OEP VA 到 EAX；PUSHAD 后的 [ESP+18h] 是保存的 ECX。交换后 POPAD 把 OEP 恢复进 ECX，最后 JMP ECX 进入 OEP。

初始化运行环境

RunEnv 保存：


ImageBase、pIat
LoadLibraryA、GetProcAddress
VirtualAlloc、VirtualFree、VirtualProtect
CreateDecompressor、Decompress、CloseDecompressor
CloseHandle、ExitProcess

Stub 通过 FS:[30h] 找到 PEB 和模块链，自写 MyGetProcAddress 解析 Kernel 模块导出，再解析其他 API 和 Cabinet.dll 中的解压函数。

恢复映像

FixSections 先令头部可写，将解压缓冲区中的原 PE 头复制回当前 ImageBase，再按"源 = DecompressedBuffer + Section.PointerToRawData，目标 = ImageBase + Section.VirtualAddress"复制各节。.iat 跳板起点在复制前由外壳第二节的 VirtualAddress 保存到 pEnv->pIat。

IAT 不写真实 API，而写跳板地址

正常加载是"原 IAT 槽 → 真实 API 地址"；老师代码执行 pImportAddressTable[i] = (DWORD)pIat;，变成"原 IAT 槽 → .iat 中的本地跳板"。

每个跳板固定 12 字节：


BYTE Code[] = {
    0xB8, 0x78, 0x56, 0x34, 0x12, // mov eax, encoded
    0x35, 0x90, 0x00, 0x00, 0x00, // xor eax,90h
    0xFF, 0xE0                    // jmp eax
};

*(DWORD*)(Code + 1) = (DWORD)Func ^ 0x90;

示例：真实 API 地址 75AB1234，编码值 75AB1234 XOR 00000090 = 75AB12A4。跳板执行：


mov eax,75AB12A4
xor eax,90
jmp eax             ; EAX 恢复为 75AB1234

完整调用链：


原程序 CALL [IAT]
  → IAT 槽中的 .iat 地址
  → MOV EAX,编码值
  → XOR EAX,90
  → JMP EAX
  → 真实 DLL API
  → API RET 回原程序

这里必须是 JMP EAX 而不是 CALL EAX，因为原程序的 CALL [IAT] 已经压入了返回地址。

抹除原导入特征

名称导入解析后 pName->Name[0] = '\0';。每个 DLL 描述符处理后：


pImportTable->Name = 0;
pImportTable->FirstThunk = 0;
pImportTable->OriginalFirstThunk = 0;

最终组合：DLL/API 名称被擦除、导入描述符关键字段归零、原 IAT 槽指向 EXE 自身 .iat 节、真实 API 地址以 XOR 值藏在跳板中。

注意：

  • 这不是把整个 IAT 结构一次性加密，而是"IAT 重定向＋逐 API 跳板＋地址异或＋抹除导入特征"。
  • 这份源码生成 .old/.iat/.pack，而此前实验文件是 UPX0/UPX1/.rsrc。因此 0x318CB RET 0 不是这份老师代码生成的 12 字节跳板。
  • Scylla 普通扫描期望 IAT 指向 DLL 导出；老师的 IAT 指向 EXE 自身 .iat，所以可能被标记为无效或可疑。只有继续跟踪 MOV/XOR/JMP 才能恢复真实目标。
  • 固定 XOR 0x90 和固定 12 字节模板特征明显，主要是课堂演示保护，不能视为强商业壳。
  • AntiDebug 中的非法 CloseHandle 和 OEP 首字节 CC 检测在给出的源码中被注释，不能把"设计存在"说成"当前构建已验证启用"。
  • 代码中 .iat 大小固定为 0x2000，每项跳板 12 字节，理论容量约 2000h / 0Ch = 682（向下取整）；源码没有检查跳板是否超过该区域。
  • 附件包含 4096 字节 hexData Stub 数组，但本次没有重新编译、反汇编和运行验证，机器码数组与源码是否完全匹配待确认。

源码问题与修正原则

老师代码能够清楚演示壳和 IAT 跳板原理，但存在若干边界或索引问题，应视为课堂实验代码，不应直接等同于经过完整健壮性验证的实现。

序号导入判断始终检查第一项


// 问题代码：循环变量是 i，判断却用 *pImportNameTable，等价于只检查第 0 项
if (*pImportNameTable & 0x80000000) {
    Func = pEnv->GetProcAddress(
        hDll,
        (LPCSTR)(LOWORD(pImportNameTable[i])));
}

混合名称导入与序号导入时可能判断错误。修正：if (pImportNameTable[i] & 0x80000000)，按当前 i 项处理。

重定位块头大小使用了指针大小


// 问题代码
int Count =
    (RelTable->SizeOfBlock - sizeof(PIMAGE_BASE_RELOCATION))
    / sizeof(WORD);

PIMAGE_BASE_RELOCATION 是指针，x86 中通常为 4 字节；IMAGE_BASE_RELOCATION 结构头实际为 8 字节（DWORD VirtualAddress; DWORD SizeOfBlock;）。

修正：EntryCount = (SizeOfBlock - sizeof(IMAGE_BASE_RELOCATION)) / sizeof(WORD);，同时使用重定位数据目录 Size 约束总遍历范围，拒绝 SizeOfBlock < 8、条目区字节数为奇数、SizeOfBlock 超过目录剩余大小的块；不能只依赖 SizeOfBlock==0 作为唯一终止条件。

MEM_RELEASE 的大小参数


// 问题代码
Env.VirtualFree(DecompressedBuffer, DecompressedDataSize, MEM_RELEASE);

// 修正：释放整个区域时 dwSize 为 0
Env.VirtualFree(DecompressedBuffer, 0, MEM_RELEASE);

固定 .iat 空间没有容量检查

代码每生成一个跳板执行 pIat += sizeof(Code);（12 字节），但没有在写入前验证 当前 pIat + 12 <= .iat 末尾。修正原则是按导入总数预计算空间，或每次写入前检查边界。

重复声明 CloseDecompressor 联合成员

RunEnv 里出现了两段同名 CloseDecompressor/pCloseDecompressor 联合声明，属于源码机械重复，应删除一份；具体编译器报错情况未重新编译验证。

审查课堂 Stub 时分别标记：


设计目标：源码想实现什么
已写代码：当前函数是否存在
编译验证：是否能成功生成匹配 Stub
运行验证：实际样本是否完成解压、修复并到达 OEP
边界验证：异常 PE、混合序号导入、大 IAT、畸形重定位是否安全

关键返回值也应检查：VirtualAlloc、CreateDecompressor / Decompress、FixImportTable、VirtualProtect、VirtualFree。

注意：

  • "函数已经写出来"不等于"已经编译运行验证"。本次附件只完成源码分析，没有在当前环境重新构建老师项目。
  • 修复一处当前崩溃不等于完成整个 Stub；后续仍可能遇到其他导入、重定位、TLS 或权限边界。
  • 源码中的 MyGetProcAddress 依赖课堂模块链假设；本次没有验证所有 Windows 版本、转发导出和异常模块布局，不能把它描述为完整系统加载器替代品。
  • 本次实际完成的是源码静态追踪与 UPX 样本脱壳排错；没有运行老师这份 .old/.iat/.pack 壳来记录其真实 OEP、IAT 跳板 VA 或动态解密结果，这些值均为待确认。
